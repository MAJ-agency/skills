## Le besoin

**Le défaut.** La garde de commandes refuse `--no-verify` par des motifs (`COMMANDES_INTERDITES`, `regles.mjs:80-90`) qui exigent la sous-commande juste après `git`. Une option globale de git placée avant elle (`-C`, `-c`, `--git-dir`, `--config-env`…) la cache. Et rien ne refuse les autres façons de sauter les hooks git : `HUSKY=0`, `core.hooksPath` posé par `-c`, par `GIT_CONFIG_*` ou par `git config`, un `include.path`.

**Rejoué sur 7.15.0** (`decisionCommande` de `4a45634`, branche courante `feat/x`, branche par défaut `develop`) :

- les cinq contournements de la spec **passent** : `git -C . commit --no-verify -m x`, `git -c core.hooksPath=/dev/null commit -m x`, `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.hooksPath GIT_CONFIG_VALUE_0=/dev/null git commit -m x`, `git config core.hooksPath /dev/null`, `git --config-env core.hooksPath=VIDE commit -m x` ;
- sur 72 commandes « à refuser » (les tests du ticket 34, ses refs de suivi, son push « matching », et les refus des bancs d'Iroki #652), **60 passent**. Seules 12 sont refusées, dont `git --git-dir .git push --no-verify …` par hasard : le motif lit `git` dans `.git` ;
- `git --config-env user.name=HOME push origin HEAD:sujet/demo` passe le refus des sujets : `--config-env` n'est pas une option à valeur (`OPTIONS_GIT_A_VALEUR`, `regles.mjs:1809`), et sa valeur est prise pour la sous-commande (ticket 34, constaté sur un dépôt jouet) ;
- `git push origin :` passe, alors qu'il pousse toute branche de même nom, `develop` comprise (ticket 34, joué) ;
- sur 37 commandes « à laisser », 35 passent ; les deux faux refus connus (`git commit -m "--no-verify"`, `git commit -mn`) sont toujours là.

Iroki l'a corrigé chez lui (`SPEC_ALL_SOC-4.70`, #652), sur sa garde à expressions. Le plugin lit les commandes par jetons depuis 7.12.0 (ticket 33, PR #98) : le correctif se **réécrit** sur ce lecteur.

**Quand le ticket est fait :**

1. Chaque appel de git se lit par ses mots : options globales (avec leurs valeurs, opaques ou non), puis sous-commande, puis arguments. Une seule fonction, partagée par la lecture des `git push` existante et par les refus nouveaux. Les arguments se lisent sur les mots exacts de la commande : un message de commit (`git commit -m "fix -n option"`) n'est jamais lu comme des options. Une expansion n'est admise que dans une valeur (Décision 0).
2. Sont refusés, sous un seul message « hooks git » : `--no-verify` (et ses abréviations) et `-n` derrière n'importe quelles options globales ; `git pull --no-verify` et `git am -n` ; `core.hooksPath`, les `include` et tout `alias.*` posés par `-c` ou `--config-env`, écrits ou retirés par `git config` (renommage de section compris) ; `HUSKY`, `GIT_CONFIG_PARAMETERS` et `GIT_CONFIG_COUNT` affectés ou exportés.
3. `git update-ref` vers `refs/remotes/` est refusé, sous son propre message.
4. `--config-env` est une option globale à valeur : un push vers un sujet derrière lui est refusé.
5. Le push « matching » (`git push <distant> :`) est refusé comme une destination illisible, comme un push dont la destination est portée par la configuration (`-c remote.origin.push=…`, `-c push.default=…`, ou la même clé écrite par `git config`).
6. Rien de ce que 7.15.0 refuse ne passe, et les commandes ordinaires de la chaîne passent toujours.
7. Le plugin prend une version, et `NOTES-DE-VERSION.md` dit ce qu'un projet repose.

## Décisions

Tenues : `A-28` (le ticket 34 repris ici, les cas d'Iroki et les cinq contournements comme bancs, réécrit sur la lecture par jetons) ; les Décisions 1 à 4 du ticket 34. Le ticket tranche ses questions ouvertes (« À trancher au triage ») ci-dessous.

0. **Le principe : une expansion n'est admise que dans une valeur** (décision de l'architecte `A-39`, qui ferme la famille des contournements par expansion au lieu de la colmater cas par cas). Une expansion, c'est un mot qui porte `$` ou un accent grave dans les **mots exacts** de la commande simple (Décision 1) ; la lecture où une variable vaut son affectation (`K=core.hooksPath; git -c $K=/x …`) n'y change rien : le refus se décide sur le mot exact.
   - **Admise dans une valeur** : la valeur séparée d'une option à valeur (`-m "$msg"`, `-F "$f"`, `-C "$(pwd)"`), et tout ce qui suit le `=` d'une forme collée (`--message="$m"`, `--author="$a"`, `--gpg-sign="$k"`, `-c user.name="$n"`, `--config-env user.name="$V"`).
   - **Refusée dans un nom**, c'est-à-dire dans tout mot que git lit comme un nom : nom d'option, globale ou de sous-commande (`--$(echo no-verify)`, le nom avant le `=` d'une forme collée) ; sous-commande (`git $(echo commit)`) ; clé de `-c` ou de `--config-env`, avant le premier `=`, ou le mot entier s'il n'a pas de `=` (`-c "$(echo core.hooksPath=/dev/null)"`, `-c "core.$(echo hooksPath)=/x"`) ; clé positionnelle de `git config` ; section de `--rename-section`, `--remove-section` et de leurs formes nues ; alias. L'appel est alors illisible : refus `RAISON_HOOKS_GIT`, ou `RAISON_PUSH_ILLISIBLE` quand la sous-commande est `push`.
   - **Exception de lecture** : derrière une action de lecture de `git config` placée avant la clé (`--get`, `--get-all`, `--get-regexp`, `--get-urlmatch`, `--list`, `-l`, `get`, `list`), une clé à expansion passe (`git config --get "$k"`).
   - **Un positionnel à expansion** de `commit`, `am`, `merge`, `rebase` ou `pull` (un mot qui n'est ni une option ni la valeur sautée d'une option à valeur : `git commit $X -m x`, `git merge "$b"`) reste refusé (`A-38`) : git peut le lire comme une option. Sa raison est `RAISON_ARGUMENT_ILLISIBLE` (Décision 6), pas « hooks git ». Pour `push`, `lirePushs` le refuse déjà (`RAISON_PUSH_ILLISIBLE`).

1. **`appelsGit(lectures)`**, sur les mots de chaque lecture, comme `lirePushs` :
   - après le mot de programme, tant qu'un mot commence par `-` : c'est une option globale. Une option de `OPTIONS_GIT_A_VALEUR` (avec `--config-env`) prend le mot suivant pour valeur, quel qu'il soit, opaque compris (`$SUBSTITUTION`) ; `--opt=valeur` est une option à valeur collée ; toute autre est sans valeur (`-p`, `-P`, `--bare`, `--no-pager`, `--paginate`, `--no-replace-objects`, `--literal-pathspecs`, `--no-optional-locks`, et une option inconnue, que git refusera de toute façon) ;
   - le mot suivant est la sous-commande, en minuscules ; s'il porte `$` ou un accent grave, elle est **illisible** (`git $(echo commit) …`) ;
   - le reste, ce sont les arguments.

   **Quelle lecture porte quoi** (décision `A-37`, B1) :
   - les **options globales** et la **sous-commande** se lisent sur toutes les lectures (L1 et L2) ; un refus sur l'une suffit : `/tmp/mon dossier`, entier en L1, se lit juste au moins une fois ;
   - les **arguments** de la sous-commande se lisent sur les **mots exacts** de la commande simple appariée à la lecture. Une lecture est **appariée** à une commande de `lu.commandes` quand elles ont le même `debut` **et le même mot `git`** (`A-38`) : lus par `appelsGit`, le mot de programme est au même rang, précédé des mêmes mots, avec les mêmes options globales et la même sous-commande. Une lecture L2 qui coupe une valeur, ou qui commence après un séparateur porté par un texte cité (`git commit -m "x; git -C . config core.hooksPath /x"` rend la lecture `git -C . config core.hooksPath /x`, de même `debut`, mais de sous-commande `config`), n'est pas appariée : elle se lit comme un texte cité (Décision 6 bis). Toutes les origines de la commande comptent (tête, corps donné à un shell, chaîne de `sh -c`, substitution, `eval`). Relevé sur `4a45634` : pour `git commit -m "fix -n option"`, L2 rend `git commit -m fix -n option`, et les mots exacts rendent `git commit -m` puis le seul mot `fix -n option` ;
   - dans ces mots exacts, la **valeur d'une option à valeur** de la sous-commande est sautée, jamais lue comme une option. `commit` : `-m`, `--message`, `-F`, `--file`, `-C`, `--reuse-message`, `-c`, `--reedit-message`, `-t`, `--template`, `--author`, `--date`, `--fixup`, `--squash`, `--cleanup`, `--trailer`, `--pathspec-from-file` ; `am` : `--directory`, `--exclude`, `--include`, `--whitespace`, `--patch-format`, `--resolvemsg` ; `merge` et `pull` : `-m`, `--message`, `-F`, `--file`, `-s`, `--strategy`, `-X`, `--strategy-option`, `--cleanup`, `--into-name` ; `rebase` : `--onto`, `-s`, `--strategy`, `-X`, `--strategy-option`, `-x`, `--exec` ; `push` : `OPTIONS_PUSH_A_VALEUR` (l. 1811). La forme collée (`--message=…`) est un seul mot. Dans un groupe d'options courtes, une lettre à valeur prend le reste du groupe ou le mot suivant (`-am x`, `-mn` : le message est `n`) ;
   - dans ces mots exacts, **un argument qui porte une expansion** (`$`, accent grave : `$SUBSTITUTION`, `$X`, `-$(echo n)`), hors valeur sautée d'une option à valeur, **rend l'appel illisible** (`A-38`, puis Décision 0). Pour `commit`, `am`, `merge`, `rebase` et `pull`, c'est un refus `RAISON_ARGUMENT_ILLISIBLE` : le lecteur ne sait pas ce que l'argument vaudra (`X=--no-verify; git -C . commit $X -m x`). Pour `push`, c'est déjà la règle de `lirePushs` (l. 1869 : tout mot à `$` ou accent grave rend le push illisible), qui reste avec sa raison, `RAISON_PUSH_ILLISIBLE`. Une valeur sautée garde son expansion sans refus : `git commit -m "$msg"`, `git commit -F "$f"` passent ;
   - **sans commande simple qui porte ce git** (un texte que le lecteur ne découpe pas en commandes : here-string ou corps donné à un shell par un détour, `cat <<< '…' | bash`, `sh -c "$(cat <<< '…')"`, `eval "$(cat <<< '…')"`, corps relu par prudence, texte cité d'un autre programme), les arguments se lisent sur les mots de la lecture elle-même, valeurs d'options sautées de la même façon. C'est la prudence : un faux refus y reste possible, un contournement non.

   Seul le premier `git` d'un segment compte, comme pour `pushs` : `git commit -m "… git config core.hooksPath x"`, sans séparateur dans le texte cité, n'est pas un `git config`.
2. **`sauteLesHooks`** est vrai si un appel de git :
   - a pour sous-commande `commit`, `push`, `merge`, `am`, `rebase` ou `pull`, ou une sous-commande illisible, et un argument qui est `--no-verify` ou l'une de ses abréviations (`a.length >= 9 && '--no-verify'.startsWith(a.toLowerCase())`) ; `--no-verify-signatures` passe ;
   - a pour sous-commande `commit`, `am` ou une sous-commande illisible, et un groupe d'options courtes qui porte `n` avant la première lettre à valeur (`commit` : `mFcCtuS` ; `am` : `CpS`) : `-n`, `-nm`, `-anm`, `-qn` refusés ; `-am x` et `-mn` passent ici (le second reste refusé par l'union, voir Hors périmètre) ; `git push -n` (`--dry-run`) passe ;
   - porte une option globale `-c` ou `--config-env` dont la clé (avant le premier `=`, comparée sans casse) est `core.hookspath`, `include.path`, `includeif.<…>.path` ou **toute clé `alias.*`**, **quelle que soit la sous-commande** (décision 2 du ticket 34 ; `A-37`, B3 : `git -c alias.ci='commit --no-verify' ci` saute les hooks sans nommer `commit`) ;
   - est un `git config` qui écrit, vide ou retire l'une de ces clés (`alias.*` compris), ou qui retire ou renomme une section dont la **source ou la cible** est `core`, `include` ou `includeif.<…>`, sans casse (`A-37`, B2 : `git config hacks.hooksPath /dev/null`, puis `git config --rename-section hacks core`, pose `core.hooksPath` sans le nommer). Lecture des arguments, guillemets déjà retirés par le lecteur :
     - lecture, qui passe : une action de lecture **avant** la clé (`--get`, `--get-all`, `--get-regexp`, `--get-urlmatch`, `--list`, `-l`, ou les formes `get`, `list`), ou la clé seule ;
     - options neutres, qui ne changent rien : `--global`, `--local`, `--system`, `--worktree`, `--show-origin`, `--show-scope`, `--null`, `-z`, `--name-only`, `--includes`, `--no-includes`, et, avec leur valeur, `--file`, `-f`, `--blob`, `--type`, `--default`, `--comment`, séparée ou collée (`--file=x.cfg`, `--type=bool`, `--default=x`, `--blob=…`, `--comment=…`) ;
     - écriture, qui est refusée : `--add`, `--replace-all`, `--unset`, `--unset-all`, `--remove-section <section gardée>`, `--rename-section <a> <b>` dès que `a` ou `b` est une section gardée, `-e`, `--edit`, les formes `set`, `unset`, `remove-section`, `rename-section` (mêmes règles), deux positionnels ou plus (clé et valeur, vide comprise : `""`), et **toute option inconnue** devant la clé, qui ferme l'exemption de lecture (`git config --comment get core.hooksPath /x` est une écriture) ;
   - ou si une commande simple de `lireCommande(commande).commandes` affecte ou exporte `HUSKY`, `GIT_CONFIG_PARAMETERS` ou `GIT_CONFIG_COUNT`, quelle que soit la valeur :
     - en position d'affectation (`HUSKY=0 git commit`, `HUSKY=0` seul sur sa ligne) ;
     - en mot `NOM=…` derrière les préfixes tenus, avant le programme qu'ils lancent : `env`, `sudo`, `doas`, `nohup`, `exec` (`sudo HUSKY=0 git commit -m x`) ;
     - en mot `NOM=…` ou en **nom nu** comme argument de `export`, `declare`, `typeset`, `readonly`, `local` (`export HUSKY`, `declare -x HUSKY`, `typeset -x HUSKY`), de `read` (`read HUSKY`) ou de `printf -v` (`printf -v HUSKY 0`) ; un nom nu qui commence par `GIT_CONFIG_` compte aussi (`export GIT_CONFIG_COUNT`).

     En argument d'un autre programme, ces mots passent (`echo HUSKY=0`, `grep -rn HUSKY=0 .husky`, `git log --grep HUSKY=0`).
3. **`ecritUneRefDeSuivi`** est vrai pour un `git update-ref` dont la première ref positionnelle (après `-d`, `-m <msg>`, `--no-deref`, `--create-reflog`) commence par `refs/remotes/`, et pour tout `git update-ref --stdin` : son entrée ne se lit pas (décision 1 du ticket 34 ; question « refus utile ? » tranchée : oui, `ticket-libre.mjs`, `next-id-branches.mjs` et `coverage-diff --base-auto` lisent encore ces refs). `git update-ref -d refs/heads/tmp` passe.
4. **`--config-env`** : dans `OPTIONS_GIT_A_VALEUR`, donc lu par `pushs` aussi. `git --config-env user.name=HOME push origin HEAD:sujet/demo` est refusé par la raison des sujets.
5. **Le push « matching » et la destination portée par la configuration** entrent dans ce ticket (question tranchée ; `A-37`, B3) :
   - un refspec `:` ou `+:` rend `pushIllisible` vrai (`RAISON_PUSH_ILLISIBLE`, inchangée) ;
   - un `git push` précédé d'une option globale `-c` ou `--config-env` dont la clé, sans casse, est `push.default`, `remote.<…>.push`, `remote.pushdefault` ou `branch.<…>.pushremote` rend aussi `pushIllisible` vrai : la destination n'est plus écrite dans la commande (`git -c remote.origin.push=HEAD:sujet/demo push origin` écrit un sujet) ;
   - un `git config` qui écrit l'une de ces clés (mêmes règles d'écriture qu'en Décision 2) est refusé par `RAISON_PUSH_ILLISIBLE`, quelle que soit la commande qui suit : le push qui la lira viendra plus tard.

   Coût nul : aucun skill ni script ne fait taper ces formes à une session.
