## Le besoin

Règle du produit, redite le 2026-11-14 : **jamais `--no-verify`**. Le socle la pose dans chaque projet : le hook d'agent refuse `git commit|push … --no-verify` tapé par une session (`skills/chaine/socle-chaine-de-production/references/agent/regles.mjs:72`, « les hooks git sont le pare-feu local »). Mais les scripts que le plugin pose dans ces mêmes projets sautent les hooks : le capitaine de fusion (`passer.sh`), le skill `sujet` (`sujet.sh`) et la création de `develop` (`develop.sh`). Un script lancé par la session échappe au hook d'agent, qui ne lit que la commande tapée : la règle n'est tenue que par la consigne, et le plugin la contredit.

Cas vécu le 2026-11-13, remonté du projet Fedora : la session qui devait fusionner une PR a refusé de jouer `passer.sh` à cause de ce `--no-verify`, puis a fusionné par l'outil GitHub, hors de la procédure (ni mise à jour avec develop, ni index régénérés, ni arbre vérifié).

Quand le ticket est fait, aucun script du plugin ne saute un hook git ; un banc du dépôt échoue dès qu'un script en réintroduit un ; un refus de hook se lit, sa sortie visible, et ne passe plus pour « la branche a bougé » ; les hooks du socle rendent ces passages sûrs (un worktree n'est plus corrompu par le pre-push) et ne font pas payer de contrôle à un push qui n'apporte rien de neuf ; le plugin est en 6.1.1.

### Où le capitaine travaille

Dans un **`git worktree`** du dépôt du projet, pas dans un clone isolé : `skills/chaine/fusionner/SKILL.md:34` (`git worktree add <scratchpad>/capitaine --detach origin/develop`, puis `pnpm install`). Aucun `git-isole.mjs` ni équivalent dans le plugin. `pnpm install` joue `prepare: husky` (`M/racine/package.json:21`), qui règle `core.hooksPath=.husky/_` dans la config partagée et crée `.husky/_` dans le worktree : **les hooks du projet y sont installés et actifs**. Retirer `--no-verify` change donc vraiment ce qui tourne.

Or `R/docs-agents/pieges.md:8` dit : « **Ne jamais pousser depuis un `git worktree`** : le pre-push lance `pnpm check`, dont les tests des scripts de chaîne écrivent dans la config git partagée (`core.bare=true`, HEAD déplacé, commits « jouet » dans le worktree) ». **Reproduit le 2026-11-14** (dépôt jetable) : sous un worktree, git exporte `GIT_DIR` au pre-push, et `GIT_DIR` plus `GIT_INDEX_FILE` au pre-commit ; dans un clone normal, le pre-push n'a pas `GIT_DIR`. Un pre-push qui fait `git init` puis `git -C <jouet> commit` écrit le commit « jouet » sur la branche du worktree et pose `core.bare=true` dans la config partagée. Avec `unset GIT_DIR GIT_INDEX_FILE` en tête du hook, rien n'est écrit et `git rev-parse --show-toplevel` rend bien le worktree. `skills/chaine/sujet/scripts/depot-jouet.mjs:29-32` et `develop.test.mjs:14-23` retirent déjà les `GIT_*` pour leurs propres jouets, mais d'autres bancs posés dans les projets ne le font pas : `R/agent/fin-de-tour.test.mjs:14-25` (`git init`, `add -A`, `commit` sous `process.env`), `M/scripts/verify/references-agent.test.mjs:167-178`. Le saut de hook protégeait donc aussi, sans le dire, le worktree du capitaine.

## Décisions

1. **Pourquoi ces sauts existaient, et ce que coûte leur retrait.** Ils évitaient trois choses : rejouer `pnpm check` au pre-push (et `check:commit` au pre-commit) alors que la CI exigée le rejoue et que `passer.sh` l'attend (étape 5) ; un pre-push qui vérifie l'arbre de travail et non ce qui part, inutile quand le push n'apporte rien de neuf (`ouvrir`, `livrer` intermédiaire, `develop.sh`) et qui refuse la création de `develop` (`coverage-diff` cherche `origin/develop`, la branche que le push crée : sortie 2, vu le 2026-11-09) ; et, sans le dire, la corruption du worktree (ci-dessus). Le retrait coûte, à chaque mise à jour d'une PR par le capitaine, un `pnpm check` local plus la couverture du diff (et, sur le chemin du conflit d'index, lint-staged et `check:commit`), soit quelques minutes par PR, que le cache Turborepo réduit quand le pre-commit a déjà joué typecheck et tests. **La procédure du capitaine ne rejoue pas ces contrôles elle-même** : elle attend la CI. Son seul contrôle local est `regenerer_index` (`skills/chaine/fusionner/scripts/github.sh:60`), qui joue les commandes et les `verification` de `scripts/docs/index-generes.json` : quelques secondes, avant le commit, et c'est lui qui donne la sortie 3 avec la commande en échec. **On le garde** : le retirer transformerait un refus précis en échec du pre-push. Le doublon réel est entre le pre-push et la CI ; le socle l'assume (`M/husky/pre-push:4-6` : un hook se contourne, la CI rejoue). Recommandation : les hooks font foi, aucun saut ne reste, aucune étape de la procédure n'est retirée.

2. **Le pre-push ne vérifie rien quand rien de neuf ne part** (`M/husky/pre-push`, qui lit désormais son entrée lui-même). Le critère, exact :
   - Le hook lit toute son entrée une fois, en tête : `PRE_PUSH_REFS=$(cat)`, puis `export PRE_PUSH_REFS` (que `coverage-diff --base-auto` relit). Chaque ligne est `<ref locale> <sha local> <ref distante> <sha distant>`.
   - Pour chaque ligne : si le sha local n'est fait que de zéros (suppression d'une branche distante, 40 ou 64 caractères), la ligne n'apporte rien et est ignorée. Sinon, le sha doit nommer un commit (`git cat-file -e "<sha>^{commit}"`) et `git rev-list -n 1 <sha> --not --remotes` doit rendre une sortie vide : aucun commit atteignable depuis ce sha qui ne soit déjà atteignable depuis une ref de suivi distant (`refs/remotes/*`, tous distants, toutes branches). C'est cette commande, et elle seule, qui décide qu'un commit est déjà sur le distant.
   - Le hook sort 0 sans rien lancer **seulement** si l'entrée a au moins une ligne lisible et que chaque ligne non ignorée remplit ce critère. Dans tous les autres cas il vérifie : entrée vide, ligne illisible (moins de quatre champs, sha qui ne nomme pas de commit), `git rev-list` en échec, au moins un commit neuf. **Jamais de sortie 0 par défaut.**
   - La sortie anticipée se fait avant `pnpm run check` **et** avant `pnpm run check:coverage --base-auto` que `socle-tests` fait ajouter : un `exit 0` en tête de hook ne laisse rien jouer après lui.
   - Ce n'est pas un saut : le hook tourne et conclut qu'il n'a rien à contrôler. Cela règle `develop.sh` (il ne pousse que `origin/main`), `sujet.sh ouvrir` (`origin/develop`) et `livrer` intermédiaire (`origin/sujet/<nom>`).
   - **Limite assumée** : un commit déjà présent sur n'importe quelle branche suivie du distant (y compris la branche de travail d'une autre session, jamais vérifiée, ou une ref de suivi périmée faute de `fetch --prune`) passe sans contrôle local, sous quelque nom qu'on le pousse. La CI exigée reste le contrôle : elle rejoue tout sur la PR, et c'est elle que la protection de `develop` exige.
   - `socle-tests/SKILL.md:31` ne fait plus ajouter la lecture de l'entrée (une seconde lecture rendrait une entrée vide) : seulement `pnpm run check:coverage --base-auto` après `pnpm run check`.

3. **Les hooks lancent leurs contrôles sans `GIT_DIR` ni `GIT_INDEX_FILE`, et seulement eux.** Formes exactes (POSIX `sh`, ce que Husky lance ; pas de `env -u`, que tous les `sh` ne garantissent pas) :
   - `M/husky/pre-push` : la lecture de l'entrée et la décision de la décision 2 gardent l'environnement de git ; juste après la sortie anticipée, une ligne `unset GIT_DIR GIT_INDEX_FILE`, avec un commentaire qui renvoie à `pieges.md`, puis `pnpm run check` (et, dans le projet, `check:coverage`, qui joue `git` dans le dossier courant et retrouve le worktree sans `GIT_DIR`).
   - `M/husky/pre-commit` : `.husky/pre-commit.local` et `npx --no -- lint-staged` restent en l'état, sous l'environnement de git (lint-staged lit l'index du commit en cours ; `.husky/pre-commit.local` est la garde de la machine du dev et n'a pas à changer de contexte) ; entre `npx --no -- lint-staged || exit 1` et `pnpm run check:commit`, la ligne `unset GIT_DIR GIT_INDEX_FILE`. `check:commit` est la dernière commande : son code est celui du hook.
   - Le capitaine **reste dans son worktree** : la cause du piège est traitée dans le hook, une fois pour tous les bancs du projet, au lieu d'un clone isolé qui casserait `proprietaire.sh` (il lit `git worktree list`) et le verrou de la boucle (`<git-common-dir>`). Aucune installation de hook à ajouter au clone ou au worktree : `pnpm install`, déjà dans la mise en place, les installe. `pieges.md:8` est réécrit : la cause, le remède posé par les hooks du socle, et le piège qui demeure pour un projet dont `.husky/` est antérieur au socle 6.1.1 (ne pas y pousser depuis un worktree tant qu'il n'a pas reposé ses hooks).

4. **Les commits de fusion passent `commit-msg` tels quels.** Le message par défaut de `git commit --no-edit` après `git merge origin/develop` est « Merge remote-tracking branch 'origin/develop' into capitaine/<n> » (`sujet.sh` : `… 'origin/sujet/<nom>' …` ou `'origin/develop' into …`) : `ignores` de `M/racine/commitlint.config.mjs` le laisse passer, et le `git merge` sans conflit de `passer.sh:149` passe déjà sous `commit-msg` aujourd'hui. Aucun message à fabriquer : `--no-edit` reste, seul `--no-verify` part. Le pre-commit joue alors lint-staged sur les fichiers apportés par develop (déjà conformes) et `check:commit`.

5. **Un refus de hook n'est pas « la branche a bougé ».** Règle commune à tous les push, commits et merges de `passer.sh` et `sujet.sh` :
   - **La sortie du hook reste visible.** Chaque push passe par `jouer_ou_dire` (`github.sh:73`, déjà sourcé par les deux scripts) : en échec, sa sortie part sur stderr, chaque ligne préfixée de la commande. Plus aucun `2>/dev/null` ni `>/dev/null 2>&1` sur un push ou un commit (`sujet.sh:276`, `439`). Les `git merge` (`passer.sh:149`, `sujet.sh:417`, `516`, `593`) gardent leur sortie dans une variable et la rendent sur stderr quand ils échouent sans fichier en conflit.
   - **La relecture après un push en échec** : `git ls-remote origin "refs/heads/<branche>"`. En échec (distant injoignable) → « la branche a bougé, relancer » (le code de « bougé » du cas, ci-dessous). Sinon, si le sha rendu diffère du sommet lu avant le push (vide pour une branche à créer) → la branche a bougé. S'il est égal → **le push a été refusé** par le pre-push (ou par le distant), sortie 3, avec la ligne « push refusé par le hook pre-push (ou le distant) : sortie ci-dessus ; corriger, jamais --no-verify ».
   - **Un `git merge` en échec sans aucun fichier en conflit** (`git diff --name-only --diff-filter=U` vide) est un refus (hook `commit-msg`, ou fichier non suivi écrasé) : `git merge --abort` si `MERGE_HEAD` existe, worktree remis comme avant, sortie 3. Jamais 2 (conflit) ni une fusion conclue à l'aveugle.
   - **Un `git commit` refusé** (pre-commit ou commit-msg) : fusion annulée (`git merge --abort`, sinon `git reset -q --hard`), sortie 3.

6. **Le commit de gel passe sous le pre-push, avec son contrôle complet.** `ecrire_gel` construit par `commit-tree` (ligne 275) un commit neuf, parent `origin/sujet/<nom>`, qui ne change que la ligne `Gel:` d'une carte. Le critère de la décision 2 **ne le couvre pas** : ce commit n'est sur aucun distant, le pre-push joue donc `pnpm check` (et la couverture du diff) **sur l'arbre de travail de la session**, sans rapport avec le gel. On l'accepte, sans exception dans le hook : c'est déjà le sort de `carte` (`sujet.sh:868`), qui pousse sous le hook des commits ne touchant qu'une carte ; et une exception « commit qui ne touche qu'une carte » ferait du pre-push un juge du contenu poussé, qu'il ne contrôle pas aujourd'hui (il contrôle l'arbre). Le contenu du gel est déjà contrôlé par `ecrire_gel` (une ligne, Prettier). Conséquence assumée : un arbre de travail rouge empêche de geler ; le refus sort en 3 au premier essai, la sortie du hook visible, avec le remède « le pre-push a contrôlé l'arbre de travail, pas le gel : relancer depuis un arbre vert (un worktree détaché sur `origin/develop`, après `pnpm install`), jamais --no-verify ». L'en-tête de `geler` (ligne 55) remplace « sans hook » par « sous le hook pre-push, qui contrôle l'arbre de travail ».

7. **`develop.sh` passe sous le hook.** Ligne 43 sans `--no-verify` ; l'en-tête (lignes 11-17) dit pourquoi le push passe : rien de neuf ne part (décision 2). 8. **6.1.1** (`.claude-plugin/plugin.json:3`, aujourd'hui `6.1.0`). `README.md:180` : « Patch pour une correction, mineure pour un skill ou un gabarit ajouté, majeure quand un skill existant change de contrat ».
