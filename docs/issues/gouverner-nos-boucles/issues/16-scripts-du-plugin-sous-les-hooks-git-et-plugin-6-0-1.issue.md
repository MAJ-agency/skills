## Le besoin

Règle du produit, redite le 2026-11-14 : **jamais `--no-verify`**. Le socle la pose dans chaque projet : le hook d'agent refuse `git commit|push … --no-verify` tapé par une session (`skills/chaine/socle-chaine-de-production/references/agent/regles.mjs:72`, « les hooks git sont le pare-feu local »). Mais les scripts que le plugin pose dans ces mêmes projets sautent les hooks : le capitaine de fusion (`passer.sh`), le skill `sujet` (`sujet.sh`) et la création de `develop` (`develop.sh`). Un script lancé par la session échappe au hook d'agent, qui ne lit que la commande tapée : la règle n'est tenue que par la consigne, et le plugin la contredit.

Cas vécu le 2026-11-13, remonté du projet Fedora : la session qui devait fusionner une PR a refusé de jouer `passer.sh` à cause de ce `--no-verify`, puis a fusionné par l'outil GitHub, hors de la procédure (ni mise à jour avec develop, ni index régénérés, ni arbre vérifié).

Quand le ticket est fait, aucun script du plugin ne saute un hook git ; un banc du dépôt échoue dès qu'un script en réintroduit un ; les hooks du socle rendent ces passages sûrs (un worktree n'est plus corrompu par le pre-push) et ne font pas payer de contrôle à un push qui n'apporte rien de neuf ; le plugin est en 6.0.1.

### Les hooks que le socle pose — `M/husky/`

- `commit-msg` : `npx --no -- commitlint --edit "$1"`. `M/racine/commitlint.config.mjs`, `ignores` : `/^Merge (pull request|branch|remote-tracking branch)/`.
- `pre-commit` (lignes 11-16) : `.husky/pre-commit.local`, `npx --no -- lint-staged`, puis `pnpm run check:commit` (`turbo run typecheck test`).
- `pre-push` (ligne 7) : `pnpm run check`. Le skill `socle-tests` (`SKILL.md:31`) y fait ajouter, **avant** `pnpm run check`, `PRE_PUSH_REFS=$(cat)` puis `export PRE_PUSH_REFS`, et après, `pnpm run check:coverage --base-auto`.

### Où le capitaine travaille

Dans un **`git worktree`** du dépôt du projet, pas dans un clone isolé : `skills/chaine/fusionner/SKILL.md`, « Mise en place » (`git worktree add <scratchpad>/capitaine --detach origin/develop`, puis `pnpm install`). Aucun `git-isole.mjs` ni équivalent dans le plugin. `pnpm install` joue `prepare: husky` (`M/racine/package.json:21`), qui règle `core.hooksPath=.husky/_` dans la config partagée et crée `.husky/_` dans le worktree : **les hooks du projet y sont installés et actifs**. Retirer `--no-verify` change donc vraiment ce qui tourne.

Or `R/docs-agents/pieges.md:8` dit : « **Ne jamais pousser depuis un `git worktree`** : le pre-push lance `pnpm check`, dont les tests des scripts de chaîne écrivent dans la config git partagée (`core.bare=true`, HEAD déplacé, commits « jouet » dans le worktree) ». **Reproduit le 2026-11-14** (dépôt jetable) : sous un worktree, git exporte `GIT_DIR` au pre-push, et `GIT_DIR` plus `GIT_INDEX_FILE` au pre-commit ; dans un clone normal, le pre-push n'a pas `GIT_DIR`. Un pre-push qui fait `git init` puis `git -C <jouet> commit` écrit le commit « jouet » sur la branche du worktree et pose `core.bare=true` dans la config partagée. Avec `unset GIT_DIR GIT_INDEX_FILE` en tête du hook, rien n'est écrit et `git rev-parse --show-toplevel` rend bien le worktree. `skills/chaine/sujet/scripts/depot-jouet.mjs:29-32` retire déjà les `GIT_*` pour ses propres jouets, mais d'autres bancs posés dans les projets ne le font pas : `R/agent/fin-de-tour.test.mjs:14-25` (`git init`, `add -A`, `commit` sous `process.env`), `M/scripts/verify/references-agent.test.mjs:167-178`. Le saut de hook protégeait donc aussi, sans le dire, le worktree du capitaine.

## Décisions

1. **Pourquoi ces sauts existaient, et ce que coûte leur retrait.** Ils évitaient trois choses : rejouer `pnpm check` au pre-push (et `check:commit` au pre-commit) alors que la CI exigée le rejoue et que `passer.sh` l'attend (étape 5) ; un pre-push qui vérifie l'arbre de travail et non ce qui part, inutile quand le push n'apporte rien de neuf (`ouvrir`, `livrer` intermédiaire, `develop.sh`) et qui refuse la création de `develop` (`coverage-diff` cherche `origin/develop`, la branche que le push crée : sortie 2, vu le 2026-11-09) ; et, sans le dire, la corruption du worktree (ci-dessus). Le retrait coûte, à chaque mise à jour d'une PR par le capitaine, un `pnpm check` local plus la couverture du diff (et, sur le chemin du conflit d'index, lint-staged et `check:commit`), soit quelques minutes par PR, que le cache Turborepo réduit quand le pre-commit a déjà joué typecheck et tests. **La procédure du capitaine ne rejoue pas ces contrôles elle-même** : elle attend la CI. Son seul contrôle local est `regenerer_index` (`skills/chaine/fusionner/scripts/github.sh:60`), qui joue les commandes et les `verification` de `scripts/docs/index-generes.json` : quelques secondes, avant le commit, et c'est lui qui donne la sortie 3 avec la commande en échec. **On le garde** : le retirer transformerait un refus précis en échec du pre-push. Le doublon réel est entre le pre-push et la CI ; le socle l'assume (`M/husky/pre-push:4-6` : un hook se contourne, la CI rejoue). Recommandation : les hooks font foi, aucun saut ne reste, aucune étape de la procédure n'est retirée.
2. **Le pre-push ne vérifie rien quand rien de neuf ne part** (`M/husky/pre-push`). Il lit son entrée (`PRE_PUSH_REFS=$(cat)`, exportée, comme le demande déjà `socle-tests`), puis sort 0 si chaque sommet poussé (hors suppression, sha nul) est déjà sur un distant : `git rev-list -n 1 <sha> --not --remotes` vide pour chaque ligne. Ce n'est pas un saut : le hook tourne et conclut qu'il n'a rien à contrôler, la vérification a eu lieu au push qui a apporté ces commits. Cela règle `develop.sh` (il ne pousse que `origin/main`), `sujet.sh ouvrir` (`origin/develop`) et `livrer` intermédiaire (`origin/sujet/<nom>`). `socle-tests/SKILL.md:31` ne fait plus ajouter la lecture de l'entrée (une seconde lecture rendrait une entrée vide) : seulement `pnpm run check:coverage --base-auto` après `pnpm run check`.
3. **Les hooks lancent leurs contrôles sans `GIT_DIR` ni `GIT_INDEX_FILE`.** `M/husky/pre-push` : `unset GIT_DIR GIT_INDEX_FILE` avant `pnpm run check` (et donc avant `check:coverage`) ; `M/husky/pre-commit` : `( unset GIT_DIR GIT_INDEX_FILE; pnpm run check:commit )`, lint-staged gardant l'environnement de git (il lit l'index du commit en cours). Le capitaine **reste dans son worktree** : la cause du piège est traitée dans le hook, une fois pour tous les bancs du projet, au lieu d'un clone isolé qui casserait `proprietaire.sh` (il lit `git worktree list`) et le verrou de la boucle (`<git-common-dir>`). Aucune installation de hook à ajouter au clone ou au worktree : `pnpm install`, déjà dans la mise en place, les installe. `pieges.md:8` est réécrit : la cause, le remède posé par les hooks du socle, et le piège qui demeure pour un projet dont `.husky/` est antérieur (ne pas y pousser depuis un worktree tant qu'il n'a pas reposé ses hooks).
4. **Les commits de fusion passent `commit-msg` tels quels.** Le message par défaut de `git commit --no-edit` après `git merge origin/develop` est « Merge remote-tracking branch 'origin/develop' into capitaine/<n> » (`sujet.sh` : `… 'origin/sujet/<nom>' …` ou `'origin/develop' into …`) : `ignores` de `M/racine/commitlint.config.mjs` le laisse passer, et le `git merge` sans conflit de `passer.sh:148` passe déjà sous `commit-msg` aujourd'hui. Aucun message à fabriquer : `--no-edit` reste, seul `--no-verify` part. Le pre-commit joue alors lint-staged sur les fichiers apportés par develop (déjà conformes) et `check:commit`.
5. **Un refus de hook n'est pas « la branche a bougé ».** `passer.sh:208` et `sujet.sh:439` sortent aujourd'hui en 5 sur tout échec du push. Après le retrait, un échec se relit : `git ls-remote origin "refs/heads/$tete"` différent du sommet lu (`$origine`) → 5, comme avant ; sinon le push a été refusé par le pre-push (ou par le distant) → sortie 3, sa sortie sur stderr, préfixée `[pre-push]` comme `jouer_ou_dire`, worktree remis propre (`git switch -q --detach origin/develop`). Un refus du `git commit` (pre-commit ou commit-msg) : même sortie 3, fusion annulée (`git merge --abort`). `rafraichir` (`sujet.sh:542-548`) : même relecture, sortie 3 par `abandonner`. Les sorties gardent leur sens (3 : gates ou checks rouges, à lire avant de renvoyer) : la boucle n'a rien à changer.
6. **`develop.sh` passe sous le hook.** Ligne 43 sans `--no-verify` ; l'en-tête (lignes 11 et suivantes) dit pourquoi le push passe : rien de neuf ne part (décision 2). Push refusé : sortie 5 comme aujourd'hui, avec une ligne de plus : un `.husky/pre-push` antérieur au socle 6.0.1 refuse ce push ; reposer le hook (`M/husky/pre-push`), jamais `--no-verify`. `socle-chaine-de-production/SKILL.md:41` et `R/CONTENU.md:25` le disent ; le passage « Jamais `git push origin origin/main:refs/heads/develop` à la main » reste, au motif que le script est idempotent, rapatrie `origin/develop` et donne ses sorties.
7. **6.0.1** (`.claude-plugin/plugin.json:3`). `README.md:180` : « Patch pour une correction, mineure pour un skill ou un gabarit ajouté, majeure quand un skill existant change de contrat ». C'est une correction : les scripts rejoignent la règle que le socle pose déjà ; aucune commande, aucun argument, aucun code de sortie ne change de sens, aucun skill ni gabarit n'est ajouté. Si la session devait créer un code de sortie nouveau, elle le dit à l'architecte avant de choisir la version.
8. Aucune dépendance nouvelle ; `package.json` ne change pas.
