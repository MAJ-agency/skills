# La relecture que l'auteur ne contrôle pas — spec du chantier 3

Programme : [`map.md`](map.md) (« gouverner nos boucles »). Décisions du produit : `P-47` à `P-53` et `P-55` à `P-58` de la carte, prises le 2026-11-18 dans le grilling du chantier 3. Elles amendent `P-6` et `P-38` et remplacent `P-41`. État : **quatrième version**, reprise sur trois relectures par des agents neufs ([première](relecture-independante.relecture-1.md), [deuxième](relecture-independante.relecture-2.md), [troisième](relecture-independante.relecture-3.md)). Les lots 1 et 2 sont prêts à découper ; les autres attendent une quatrième relecture. Cinq points sont à dire au produit (fin de ce document).

## Le problème

Aujourd'hui, la session qui code un ticket lance elle-même ses relecteurs, trie leurs constats et écrit la section de revue de sa PR (`revue-de-ticket/SKILL.md`, étapes 2 à 5). Le capitaine vérifie, pour les chemins que `revue-exigee.mjs` désigne (`cheminExige`), la présence d'un titre « Revue… » dans le corps de la PR. Le conducteur contre-relit les PR à chemin sensible par un sous-agent (`chantier/SKILL.md` § 6, point 5), dans son propre contexte, et il a écrit le ticket contre lequel il juge. Les PR de documentation du conducteur et de l'architecte (tickets, règles, specs) ne sont relues par personne d'indépendant.

Le fichier CODEOWNERS ferait dépendre chaque PR sensible d'une seconde personne : toutes les sessions écrivent sous le compte du produit, et GitHub refuse qu'un auteur approuve sa propre PR.

## Ce qui change, vu par le produit

- **Fichiers sensibles** (`P-47`, `P-48`, `P-49`) : l'accord du produit est demandé **avant** d'y toucher, une fois, quand il valide le découpage d'un chantier. Le conducteur dit quels fichiers, pourquoi, et ce qui va y changer. Sans l'accord noté, la machine refuse la modification. Aucun blocage par GitHub ; le fichier CODEOWNERS disparaît.
- **Toute PR a une relecture indépendante** (`P-51`), quel que soit son auteur. **La session qui code ne se relit plus** (`P-52`).
- **Un Relecteur par dépôt** (`P-55`) aiguille : il lance une session de relecture par PR. Il ne transporte jamais les constats, ne les résume pas, n'arbitre rien. Le verdict s'écrit sur la PR.
- **Un skill unique de relecture** (`P-55`) choisit les contrôles selon ce que la PR contient.
- **Le capitaine ne relit rien** (`P-50`) : son script vérifie que le verdict porte sur ce qu'il fusionne.
- **Trois allers-retours au plus** (`P-53`) : au-delà, l'architecte tranche si la cause est technique et informe le produit ; il ne lui pose une question que si elle est métier.
- **Règle de criticité haute** (`P-56`) : deux relectures indépendantes, et un message d'information au produit, sans que la PR l'attende.
- **Le bilan de fin de chantier est supprimé** (`P-57`).
- **Le signal d'un verdict** (`P-58`) : une étiquette sur la PR, un message d'une ligne à l'auteur et au conducteur (où lire, jamais le contenu), un réveil de secours chez l'auteur.

## Vocabulaire

Un mot, un sens. Ces termes entrent dans `CONTEXT.md` avec le lot 3.

| Terme | Sens | Ne pas dire |
| --- | --- | --- |
| **Relecteur** | la session qui aiguille les relectures d'un dépôt ; elle ne relit rien | « relecteur » pour autre chose |
| **session de relecture** | la session lancée par le Relecteur pour relire une PR | relecteur |
| **axe** | un sous-agent en contexte vierge lancé par la session de relecture, avec une liste fermée de critères | relecteur, revue |
| **constat** | ce qu'un axe relève. Deux gravités : **bloquant** (un écart à un critère écrit : il se corrige, ou se conteste) et **doute** (une question, sans obligation) | défaut, « à corriger », mineur |
| **verdict** | le commentaire de la session de relecture ; il vaut **validé** (aucun bloquant) ou **refusé** | « à corriger » |
| **tour** | une demande de relecture d'une PR et le ou les verdicts qui y répondent | aller-retour |
| **même contenu propre** | deux versions d'une PR dont le diff propre ne diffère que par des index générés (`A-81`) | « aux index près » sans définition |
| **contestation**, **arbitrage** | l'auteur conteste un bloquant ; un arbitre le maintient ou l'écarte | — |
| **décision de plafond** | ce que décide l'architecte après le troisième tour refusé | arbitrage |
| **étiquette** | un label GitHub | label, dans la prose |
| **auteur** | la session qui a écrit la PR | propriétaire |

## Décisions de conception (architecte)

Numérotées dans la suite de la carte ; elles remplacent celles des deux premières versions.

### Fichiers sensibles

- `A-73` — **Sur un dépôt en régime 8 (`A-97`), un chemin sensible ne se modifie que sur la branche d'un ticket.** La pose d'un socle sur un dépôt qui n'a pas la chaîne, et la repose du plugin, sont des gestes que le produit demande lui-même : la première n'a ni ticket ni garde, la seconde a son ticket, dont la ligne `Sensibles:` nomme par motifs les chemins posés. Il n'y a pas d'exception pour la branche de cadrage : ce que le plugin fait aujourd'hui écrire au cadrage sur un chemin sensible (ajouter le dossier d'un module à `cheminsSensibles`, poser un socle) devient un ticket du chantier, le premier quand d'autres en dépendent. `chantier/SKILL.md` et `chaine-de-production.md` § 3 le disent à la place de « dans la même PR de cadrage ».
- `A-74` — **La ligne `Sensibles:` du ticket.** Elle nomme des chemins exacts ou des motifs, puis qui a accordé et quand (le gate vérifie la forme, pas que le chemin est déjà sensible : un ticket peut nommer le dossier qu'un ticket précédent rendra sensible) : `Sensibles: scripts/chaine/passer.sh, scripts/chaine/passer*.test.mjs — accord de <nom>, 2026-11-18`, ou `Sensibles: —`. Elle se lit sur `origin/sujet/*`, comme `Dépendances:` (`agent/garde-commandes.mjs`), jamais dans l'arbre de travail ni sur la branche de la session ; pour un ticket sans sujet, sur `origin/develop`, où le ticket entre d'abord par sa propre PR de documentation. Une branche de mise à jour d'un sujet (`maj/<nom>`) est couverte par l'union des lignes des tickets de ce sujet.
- `A-75` — **La demande d'accord est un tableau de la carte**, section `## Fichiers sensibles` : une ligne par fichier (ticket, chemin, pourquoi, ce qui y change). Le conducteur l'écrit au découpage ; l'architecte la soumet au produit avec le découpage (sans programme, le conducteur la soumet lui-même) ; les lignes `Sensibles:` des tickets ne sont remplies qu'après l'accord, dans la PR de cadrage, qui est relue. Un fichier découvert en route : la session s'arrête et l'écrit au conducteur, qui obtient l'accord par la même voie, puis ajoute le chemin au ticket par une PR de documentation vers le sujet, relue comme les autres.
- `A-76` — **Trois gardes mécaniques**, qui lisent la même ligne et ne s'activent que sur un dépôt en régime 8 (`A-97`) : le hook d'édition (`agent/garde-fichiers.mjs`, `regles.mjs`) refuse l'écriture d'un chemin sensible que la ligne ne couvre pas ; `sujet.sh fusionner` (sous-PR) et `passer.sh` (PR vers `develop`) renvoient une PR dont le diff touche un chemin sensible non couvert. Une livraison de sujet n'y repasse pas. Une PR sans ticket qui touche un chemin sensible est renvoyée. Le hook lit le sujet par le réseau, comme `garde-commandes` ; il ne voit pas une écriture faite par une commande, que les deux autres gardes rattrapent.
- `A-77` — **CODEOWNERS sort du plugin.** Retirés : `scripts/github/codeowners.mjs` et son test, son gate et l'entrée de `gatesRapides`, la clé `proprietaires`, le refus d'éditer CODEOWNERS dans `regles.mjs`, les états « attend un propriétaire » et « attend un humain » qui en viennent (`fusionner/scripts/github.sh`, `file.sh`, `passer.sh`, `boucle.sh` et leurs tests), la case correspondante d'`admin.md` — ses sous-règles (pas de push forcé, pas de suppression de branche, aucune liste de contournement) restent, dans la protection de branche. **`proprietaire.sh` reste** : il retrouve la session auteur d'une PR. L'ADR « CODEOWNERS » est marquée remplacée. La repose retire `.github/CODEOWNERS` quand il porte l'en-tête du générateur.

### Le skill `relecture`, le verdict, les deux calculs partagés

- `A-78` — **Un skill `relecture`** (`skills/chaine/relecture/`), joué par une session de relecture, jamais par l'auteur. La session de relecture est créée sur **la base** de la PR, pas sur sa tête : elle ne charge ni le `CLAUDE.md` ni les hooks que la PR modifie. Elle extrait la tête de la PR dans un arbre de travail à part et y joue les scripts de relecture (`diff-revue.sh`, `contexte-ticket.mjs`, `/security-review`, les gates des index générés), qui lisent `HEAD` et le disque. Elle lit le diff de la PR contre sa base et choisit ses axes :

  | Le diff contient | Axes |
  | --- | --- |
  | un chemin que `revue-exigee.mjs` désigne (`cheminExige`), avec un ticket | Règles, Ticket, Documentation |
  | un tel chemin, sans ticket | Règles |
  | un chemin sensible | en plus : la ligne `Sensibles:` couvre chaque chemin touché ; `/security-review`, comme `revue-adversariale` aujourd'hui |
  | des tickets, une spec, une carte | Tickets : format prêt pour agent, paraphrase de la spec, décision laissée ouverte, référence morte, surface sans preuve, fichier chaud en double dans une vague |
  | une règle métier, une criticité, le glossaire | Règles métier : critère `D8`, cas et familles, criticité et sa raison, vocabulaire |
  | toute autre documentation (ADR, README, méthode, planches) | Documentation |

  Un diff qui relève de plusieurs lignes reçoit l'union de leurs axes ; un ticket dont seules la ligne `Status:` et la section `## Comments` changent ne déclenche pas l'axe « Tickets ». Pour une PR de mise à jour d'un sujet, le diff relu est celui que le capitaine juge : la résolution du conflit et les retouches, rendues par une commande nouvelle, `sujet.sh a-juger <n>`, qui expose les listes que `verifier_mise_a_jour` calcule aujourd'hui pour lui seul. `relecture` a ses propres prompts et critères, repris de ceux de `revue-de-ticket` et de `revue-adversariale` et récrits avec les deux gravités ; ces deux skills restent tels quels pour le régime 7, jusqu'au nettoyage (`A-102`). Les scripts qu'ils posent (`diff-revue.sh`, `chemins-sensibles.mjs`, `contexte-ticket.mjs`) et le fichier de critères servent aux deux régimes ; `relecture poser` les pose aussi. En régime 8, `T3` est joué par la session de relecture pour toutes les criticités : la précision provisoire de `P-38` ne vaut plus que pour le régime 7.
- `A-79` — **La session de relecture trie avant d'écrire.** Elle relit chaque constat d'un axe dans le code, ligne ouverte : sans critère cité, ou faux, il est écarté, et le verdict dit combien et pourquoi en une phrase chacun. Elle ne modifie aucun fichier et ne pousse rien.
- `A-80` — **Le verdict est un commentaire de la PR**, de forme fixe, que la machine lit : une marque invisible ; `Sommet relu:` (sha de 40 caractères) ; `Tour:` (le numéro que le Relecteur lui a donné) ; `Verdict:` (`validé` ou `refusé`) ; `Bloquants:` (nombre) ; `Session:` (son identifiant) ; puis les constats (gravité, critère, fichier et ligne, constat, et pour un bloquant le test qui l'aurait attrapé). Un axe en échec s'écrit « non exécuté » et le verdict est `refusé`. Le lecteur tolère le pied de page des sessions cloud, et ignore un commentaire modifié après sa création (`updated_at` différent de `created_at`), comme la procédure de `skills` le fait déjà.
- `A-81` — **« Même contenu propre », un seul calcul**, écrit une fois (`relecture/scripts/`), posé dans `scripts/chaine/`, appelé par le Relecteur et par le capitaine sur des objets git, sans arbre de travail. Entrées : V (le sommet relu), T (la tête), B (la branche de base **de la PR**, sujet ou `develop`). Il répond « même » quand V est un ancêtre de T, que T et `origin/B` n'ont qu'une base de fusion M, et que l'arbre de T égale la fusion recalculée (`git merge-tree`) de V avec M, hors index générés. Dans tout autre cas (V introuvable après une réécriture, plusieurs bases de fusion, fusion recalculée en conflit) il répond « différent », et la PR se relit. Un index généré n'est dispensé que selon les trois classes que `passer.sh` (`livraison_intermediaire`) applique déjà : régénéré par une commande ; sans commande, seulement si son contenu est celui de la base ; déclaré par motif, seulement sur un contenu déjà connu. La liste des index se lit dans `origin/B:scripts/docs/index-generes.json`, jamais dans un arbre de travail : les deux appelants ont la même réponse. Une PR dont le capitaine a résolu un conflit par règle est donc relue.
- `A-82` — **« Double relecture exigée », un seul calcul**, de même. Une PR l'exige quand son ticket porte la ligne `Relecture: double`, ou quand son diff touche le fichier d'une règle de criticité haute ou un fichier que le champ `code:` de cette règle nomme. Le niveau se lit sur la base **et** sur la tête de la PR (une PR qui monte elle-même une règle à haute est vue) : dans l'index Anchorpost du dépôt quand il en a un, qui porte le niveau effectif, criticité reçue d'une feature comprise — le ticket nomme le champ après lecture du schéma pivot, aucun lecteur n'existe aujourd'hui dans le plugin ; sinon dans l'en-tête des fichiers de règle (`criticality`, valeur `high`, sous ses deux formes), qui ne voit pas une criticité reçue d'une feature. `code:` est facultatif : une PR sans ticket qui touche le code d'une règle haute sans champ `code:` n'est pas vue, c'est écrit dans les limites.

### Le Relecteur et les étiquettes

- `A-83` — **Un rôle, un skill, une session par dépôt.** Skill `skills/chaine/relecteur/`, lancé par une commande en première ligne et jamais par le modèle, comme `chantier`. L'architecte le lance en même temps que le capitaine (gabarit dans `architecte/references/lancement.md`), l'inscrit sur la ligne `Relecteurs:` de la carte du programme comme il le fait pour `Capitaines:`, et n'en lance pas un second tant que `get_session` dit vivante la session que cette ligne nomme. Sans programme : le conducteur, au lancement de son chantier, s'il n'y en a pas pour le dépôt ; chaque carte de chantier nomme le Relecteur du dépôt sur une ligne `Relecteur:` de sa fiche. `chantier` vérifie qu'il tourne par cette ligne et `get_session`, sans filtre par tag. Sa consigne vient du gabarit mot pour mot. Il lit et écrit GitHub par les fonctions de `fusionner/scripts/github.sh`, comme le capitaine.
- `A-84` — **Les étiquettes.** Deux nouvelles, `à-relire` et `à-reprendre`, ajoutées à `labels.sh` et à `admin.md` (un administrateur les crée avant la repose). Une PR en relecture garde `à-relire`. Qui change une étiquette **pose la nouvelle avant de retirer l'ancienne** : une PR peut en porter deux un instant, jamais aucune.

  | État de la PR | Étiquette | Qui la pose |
  | --- | --- | --- |
  | à relire, puis en relecture | `à-relire` | **l'auteur**, à chaque demande, avec un commentaire `À relire — sommet <sha> — Session: <la sienne, ou —> — Conducteur: <celle du conducteur, ou —>` |
  | tour refusé, ou plafond atteint, ou poussée après un verdict validé | `à-reprendre` | **le Relecteur** |
  | relue et validée | `à-fusionner` | **le Relecteur** ; et `sujet.sh livrer` pour la livraison d'un sujet, comme aujourd'hui (`A-92`) |
  | renvoyée par le capitaine | `fusion-bloquée` | **le capitaine** |

  L'auteur ne pose jamais `à-fusionner`. L'auteur écrit la liste entière des étiquettes (`issue_write`) : son réveil de secours (`A-86`) répare une étiquette qu'une écriture croisée aurait effacée.
- `A-85` — **La décision du Relecteur est une fonction pure, écrite et testée avant le skill** (lot 3) : elle reçoit les étiquettes d'une PR, ses commentaires à marque, sa tête et l'état des sessions nommées, et rend un seul geste. Les mêmes définitions servent au capitaine.
  - **La distribution d'un tour** est le commentaire du Relecteur `Relecture — tour k — sommet <sha> — sessions <…> — verdicts exigés <1 ou 2>`, avec ses variantes `(redistribué)`, `(remplace <identifiant>)`, `après arbitrage`. La dernière distribution d'un tour k fait foi.
  - **Les verdicts d'un tour** sont les commentaires de verdict dont `Tour:` vaut k, dont `Sommet relu:` est le sommet de la dernière distribution de ce tour, et dont `Session:` est l'une des sessions qu'elle nomme ; le dernier par session. Tout autre verdict (session remplacée ou orpheline, ancien sommet) est ignoré.
  - **Un tour est validé** quand il a tous ses verdicts exigés et qu'ils sont `validé` ; **refusé** quand il les a tous et que l'un est `refusé` ; sinon il est **en cours**. Un tour repris après arbitrage se juge sur ses derniers verdicts.
  - Le Relecteur liste, à chaque réveil de sa veille, les PR ouvertes qui portent `à-relire` ou `à-fusionner`, dont la base est en régime 8, hors sujet gelé et hors livraison de sujet (tête `sujet/*` ou `livraison/*`). Pour chacune, **la première règle qui s'applique** :
    1. un commentaire `Plafond — décision attendue` plus récent que toute `Décision de plafond` : `à-reprendre`, rien d'autre ;
    2. un tour validé dont le sommet a le même contenu propre que la tête (`A-81`) : `à-fusionner` (cela couvre la PR renvoyée pour un contrôle instable ou mise à jour par le capitaine, sans nouveau tour) ;
    3. la PR porte `à-fusionner` sans tour validé pour ce contenu (poussée après le verdict) : `à-reprendre`, et une ligne « poussée après le verdict : redemander la relecture » ;
    4. le dernier tour distribué porte sur le contenu de la tête et il est refusé : un `Arbitrage — … — écarté` plus récent que ses verdicts, le Relecteur renvoie la PR aux mêmes sessions (`Relecture — tour k, après arbitrage`) ; sinon `à-reprendre`, puis une ligne à l'auteur et au conducteur ;
    5. le dernier tour distribué porte sur le contenu de la tête et il est en cours : la session attendue est vivante et la distribution a moins d'une heure (`relecture.delai`), il attend ; sinon il la remplace (`… (remplace <identifiant>)`) et le dit au conducteur ;
    6. sinon, la tête n'a pas de tour : trois tours refusés depuis la dernière décision de plafond, il écrit `Plafond — décision attendue`, pose `à-reprendre`, écrit une ligne au conducteur et à l'architecte ; moins de trois, il distribue le tour suivant — **aux mêmes sessions qu'au tour précédent quand elles vivent et ne sont pas au plafond de contexte** (`P-52`), à des sessions neuves sinon — en créant les sessions puis en écrivant la distribution.
  - À chaque `à-reprendre` ou `à-fusionner` posée, il écrit une ligne à l'auteur et au conducteur nommés par le dernier commentaire `À relire` : « verdict écrit sur la PR n : refusé » ou « validé », avec « double » quand deux verdicts étaient exigés. Jamais un constat, jamais un résumé. Il n'arbitre rien.
  - La session de relecture, son verdict écrit, lui écrit une ligne : ce message ne fait que hâter le réveil ; perdu, le passage suivant de la veille fait le même travail.
- `A-86` — **Le réveil de secours de l'auteur**, armé à chaque demande : si la PR porte `à-reprendre`, lire le verdict et corriger ; si elle ne porte aucune des quatre étiquettes, reposer `à-relire` ; si elle porte `à-relire` depuis plus de deux heures sans distribution pour son sommet, l'écrire au conducteur (un Relecteur arrêté) ; sinon rien, et le réarmer une fois.
- `A-87` — **Le coût et l'archivage.** Une session de relecture a le rôle `relecture` dans `## Coût` (gate `tickets`, `couts.mjs`). Qui archive l'auteur archive aussi les sessions de relecture de la PR, lues sur elle, et note leur coût : le conducteur pour ses filles, l'auteur lui-même pour une PR du conducteur ou de l'architecte. Le modèle d'une session de relecture est celui de la clé `relecture.modele` de `chaine.json`. Une session de relecture remplacée au plafond de contexte se signale au conducteur, comme tout plafond.

### Contester, plafonner

- `A-88` — **Contester.** L'auteur répond sur la PR, `Contesté — <critère, fichier et ligne> — <raison>`, et écrit une ligne à l'arbitre. L'arbitre écrit `Arbitrage — <critère, fichier et ligne> — maintenu` ou `écarté — <raison>`. L'auteur redemande la relecture ; la règle 4 de `A-85` renvoie la PR aux mêmes sessions, qui rendent un verdict où un bloquant écarté ne compte plus, reconnu par son critère et son lieu. Cette reprise appartient au même tour. L'arbitre n'est jamais l'auteur : pour une PR d'une fille, le conducteur ; pour une PR du conducteur, l'architecte (sans programme, le produit) ; pour une PR de l'architecte, **le produit**.
- `A-89` — **Le plafond.** Les tours refusés se comptent selon les définitions de `A-85`, depuis la dernière `Décision de plafond` : un tour redistribué ou repris après arbitrage ne compte qu'une fois, sur son dernier état ; un tour validé puis renvoyé par le capitaine ne compte pas. Au troisième, la règle 6 arrête la distribution. La décision de plafond revient à qui arbitrerait (`A-88`) : l'architecte pour une PR d'une fille ou du conducteur, **le produit** pour une PR de l'architecte ou, sans programme, du conducteur. Elle s'écrit `Décision de plafond — …` (ticket récrit ou découpé, désaccord tranché), et porte ses lignes `Arbitrage — … — écarté` quand elle écarte un bloquant ; le compte repart de zéro. Ce plafond n'est pas celui des renvois du capitaine (`renvoisParPR`), qui reste tel quel.

### Criticité haute

- `A-90` — **Deux sessions de relecture** quand le calcul de `A-82` le dit. Le Relecteur en lance deux, écrit « verdicts exigés 2 » ; chacune a pour consigne de ne pas lire le verdict de l'autre. Le capitaine ne se fie pas à ce commentaire : il refait le calcul et exige lui-même deux verdicts validés de deux sessions distinctes. Le gate `tickets` exige en outre, en régime 8, la ligne `Relecture: double` sur un ticket ouvert qui cite une règle haute, pour que le conducteur le sache au découpage (lot 5, partie c). Le message d'information au produit part du conducteur, qui connaît le ticket, par l'architecte : la règle, ce qui change, les deux verdicts.

### Le capitaine

- `A-91` — **Le capitaine juge l'éligibilité par les verdicts**, pour une PR dont la base est en régime 8, au moment où il la juge aujourd'hui, avant sa propre mise à jour. `revue-exigee.mjs` reçoit les commentaires de la PR en plus du corps, du titre et de la base. Il veut un tour validé au sens de `A-85` — le nombre de verdicts que le calcul de `A-82` exige, des sessions nommées par la dernière distribution de ce tour — dont le sommet a le même contenu propre que la tête (`A-81`). Sinon : renvoi, avec le motif ; `renvoyer.sh` dit alors « corriger, puis poser `à-relire` ». Toute PR est concernée, documentation comprise. Pour une base en régime 7, il juge comme aujourd'hui.
- `A-92` — **Deux gestes ne demandent pas de verdict.** Le report de `develop` dans un sujet par le capitaine (`sujet.sh rafraichir`, un push sans PR). Et la livraison d'un sujet, **quand chaque commit du sujet est l'un de ceux que `sujet.sh` sait y écrire** : le squash d'une sous-PR fusionnée dans ce sujet (son numéro, sa base et son commit de fusion lus sur GitHub), un commit qui ne touche que la carte (`carte`, `geler`, `degeler`), ou une fusion dont le second parent est sur `develop` (`rafraichir`, mise à jour). Cette preuve par la forme des commits remplace, pour la livraison finale, la dispense sur le seul nom `sujet/*` ; la livraison intermédiaire (`livraison/*`) garde en plus sa preuve actuelle. Une livraison qui échoue à cette preuve est renvoyée avec le commit en cause et attend l'architecte. Une livraison renvoyée pour un conflit ou un contrôle revient comme aujourd'hui : qui livre repose `à-fusionner`, le Relecteur ne s'en occupe pas. **La PR de mise à jour d'un sujet, ouverte par une session, n'est pas exemptée.**

### Les sessions qui codent, le conducteur, l'architecte

- `A-93` — **La session qui code**, en régime 8 (`chaine-de-production.md` § 5, le document posé par la repose) : l'étape « revue de ticket » devient « demander la relecture » — dernier push, PR hors brouillon, commentaire `À relire` et étiquette, une ligne au conducteur, le réveil de secours. Sur `à-reprendre` : lire le verdict sur la PR, corriger chaque bloquant avec son test ou le contester, pousser, reposer `à-relire`. Elle ne lance aucun relecteur et ne pose jamais `à-fusionner`.
- `A-94` — **Le conducteur**, en régime 8, ne contre-relit plus et ne relaie aucun constat. Il arbitre les contestations de ses filles et reçoit les plafonds. En régime 8, `Label: contre-revue` n'a plus d'effet : le gate cesse de l'exiger et garde la valeur lisible sur les tickets existants ; `lancement.md` ne fait plus livrer « selon la ligne `Label:` » qu'en régime 7. Ses propres PR passent par `à-relire`. La carte, qu'il tient à jour sur le sujet sans PR (`sujet.sh carte`), reste hors relecture : c'est un journal, et elle ne porte plus aucun accord (`A-73`).
- `A-95` — **Le bilan sort du plugin** : l'obligation d'une section `## Rétro` non vide pour passer une carte à `fini` est retirée du gate, de `chantier/SKILL.md`, des gabarits, de `pieges.md`, du `README.md` et de leurs tests. Un incident donne un ticket au moment où il arrive.
- `A-96` — **Une ADR « relecture indépendante et accord des fichiers sensibles »** remplace l'ADR « CODEOWNERS » et amende les points de l'ADR de la chaîne qui décrivent la revue par l'auteur et la contre-revue. Elle est écrite avec la bascule, pas avant : elle décrirait sinon un régime qui n'est pas encore là.

### Passage de la 7 à la 8

- `A-97` — **Le régime d'une PR est celui de sa base.** La clé `relecture` de `.claude/chaine.json`, lue sur la branche de base de la PR (`origin/sujet/<nom>` ou `origin/develop`), dit le régime 8 ; son absence, le régime 7. Tout ce qui est mécanique la lit là : `revue-exigee.mjs`, `passer.sh`, `sujet.sh`, le gate `tickets`, le Relecteur. Le hook d'édition la lit dans l'arbre de travail, qui vient de cette base. Un dépôt sans `.claude/chaine.json` n'a pas la chaîne : rien ne change pour lui (c'est le cas de `skills`).
- `A-98` — **Le plugin porte les deux régimes jusqu'au nettoyage.** Les scripts gardent leur branche 7 à côté de la branche 8. Les skills que les sessions lisent dans le marketplace (`chantier`, `architecte`, `fusionner`, `sujet`) disent en tête de lire la clé sur la base, puis décrivent le régime 8 ; ce qui est propre au régime 7 (la contre-revue du conducteur, la livraison selon `Label:`) part dans une référence `regime-7.md` qu'ils citent. `revue-de-ticket` et `revue-adversariale` restent des points d'entrée tant que le régime 7 existe. Rien n'est retiré à la bascule : personne ne s'arrête, aucun projet n'est gelé.
- `A-99` — **La repose d'un dépôt** pose d'un coup, par une PR vers `develop`, la clé, les scripts à deux régimes et les documents du régime 8 (`chaine-de-production.md`, fragments). Cette PR a pour base un `develop` sans la clé : elle est relue et fusionnée selon le régime 7. Ensuite `develop` est en 8. Un sujet ouvert reste en 7 tant que le capitaine n'y a pas reporté `develop`, ce qu'il ne fait que sans sous-PR ouverte : ses PR en vol finissent donc en 7, sur les documents de leur branche. Au report, le sujet passe en 8 ; le capitaine l'écrit au conducteur, qui demande sa relève, parce que sa session a lu le skill avant la bascule. Après la repose, l'architecte du projet relance le capitaine et lance le Relecteur.
- `A-100` — **La bascule est le lot qui rend le régime 8 posable** : les documents du régime 8, les skills des rôles à deux régimes, la clé dans le gabarit `chaine.json`, la version 8.0.0. C'est une seule PR dans `skills`, qui n'a ni `develop` ni sujet. Elle reste en brouillon jusqu'au bout ; des sessions s'y relaient, une par partie, sans jamais ordonner la fusion ; l'architecte fait contre-relire chaque partie par un agent neuf, puis l'ensemble, joue l'essai réel, et écrit seul l'ordre au sommet relu. Pendant ce lot, aucun autre ticket du plugin ne touche `passer.sh`, `sujet.sh`, `chantier/SKILL.md` ni `lancement.md`.
- `A-101` — **Le dépôt `skills`** garde sa procédure actuelle jusqu'à son propre lot : dans `lancement.md`, la phrase qui porte à la fois le régime des dépôts à chaîne et la procédure de `skills` est coupée en deux, et seule la première moitié change à la bascule. Son lot lui donne un Relecteur, par une procédure dans les prompts, et l'ordre `à-fusionner au sommet <sha>` est alors écrit par le Relecteur quand le verdict est validé.
- `A-102` — **Le nettoyage**, dernier lot : quand plus aucun sujet des trois projets n'est en régime 7, la branche 7 des scripts, `regime-7.md`, les deux anciens skills de revue comme points d'entrée et `Label: contre-revue` sortent du plugin.

## Ce que cette spec ne ferme pas

- **Toutes les sessions écrivent sous le compte du produit.** Une étiquette, un verdict, une ligne `Sensibles:` peuvent être écrits par n'importe quelle session : ces gardes tiennent face à une session de bonne foi qui suit son skill, pas face à une PR hostile. Le retrait de CODEOWNERS retire la seule protection de GitHub qui visait ce cas ; il reste la protection de branche.
- **C'est un agent qui écrit le nom de qui a accordé** un fichier sensible. Rien ne prouve l'accord, sinon la conversation du produit.
- **Le Relecteur est un point de passage** : arrêté, plus aucune PR n'est relue. Il se relance sans rien perdre ; le réveil de secours de l'auteur le signale (`A-86`).
- **Le coût** : une session de relecture par PR, deux pour une règle haute ; chaque correction rouvre la CI entière, la PR n'étant plus en brouillon.
- **Deux sessions de relecture d'une même PR peuvent lire le verdict l'une de l'autre** : la consigne l'interdit, rien ne l'empêche.
- **Une PR écrite par un humain ou par un outil**, sans session auteur : le commentaire `À relire` porte `Session: —`, la relecture se fait, personne n'est sonné.
- **Une règle haute sans champ `code:`**, touchée par une PR sans ticket, n'a qu'une relecture ; et sans index Anchorpost, une criticité reçue d'une feature n'est pas vue (`A-82`).
- **Deux gravités seulement** : ce qui était « à corriger » devient bloquant. Il y aura plus de tours refusés, et le plafond de trois sera atteint plus souvent.
- **Un index généré modifié à la main** entre aujourd'hui tel quel dans un sujet quand la fusion est propre ; la relecture ne lit pas les index. Ce n'est pas nouveau, et ce chantier ne le ferme pas.
- **À sonder avant le lot 4** : qu'une session réveillée par le message d'une autre accepte d'écrire une étiquette. Le dessin n'en dépend plus (`A-85` passe par la veille), le message ne fait que hâter.

## Hors périmètre

Deux défauts de la chaîne relevés le 2026-11-18, qui ont leurs tickets à part : `chantier` § 6 donne `sujet.sh rafraichir` au conducteur alors que c'est le geste du capitaine (`A-69`) ; une PR en retard dont seul un index généré est périmé une fois fusionnée avec la base part au renvoi alors que `passer.sh` sait la réparer. Et un compte propre aux agents, écarté par le produit comme trop compliqué.

## À dire au produit

1. **Une PR de l'architecte** : l'arbitre d'un bloquant contesté, et qui décide au plafond, c'est le produit (`A-88`, `A-89`). De même, sans programme, pour une PR du conducteur. À confirmer.
2. **La livraison d'un sujet n'a pas de relecture propre** quand chaque commit du sujet est une sous-PR déjà relue, une mise à jour de la carte ou un report de `develop` (`A-92`). La carte du chantier, que le conducteur tient sans PR, entre donc sans relecture : c'est un journal. À confirmer.
3. **Chaque repose du plugin touche des fichiers sensibles** : elle lui demandera son accord, une fois, sur la liste de ces fichiers (`P-47`). Pour information.
4. **Le passage à la 8 n'arrête aucun projet** : un chantier ouvert finit sous l'ancien régime, et passe au nouveau quand le capitaine y reporte `develop` (`A-99`). Pour information.
5. **Le coût** : une session de relecture par PR, documentation comprise, et tout écart à un critère écrit devient bloquant. Pour information.

## Vérification d'ensemble

Partie 6c, sur un dépôt jouet monté avec les vrais outils et, pour ce qui demande de vraies sessions, sur une copie d'un dépôt réel : une PR de code avec un bloquant planté reçoit `à-reprendre`, puis `à-fusionner` après correction, sans que son auteur ait lancé un relecteur ; le message de la session de relecture au Relecteur est supprimé exprès, et l'étiquette arrive quand même au passage suivant ; le capitaine refuse une PR sans verdict, une PR dont le contenu propre a changé depuis le verdict, et passe une PR qu'il a lui-même mise à jour ; une sous-PR qui touche un chemin sensible hors de sa ligne `Sensibles:` est refusée par le hook et par `sujet.sh fusionner` ; trois tours refusés arrêtent la distribution ; une PR qui touche le code d'une règle haute n'entre pas avec un seul verdict validé, même si le commentaire du Relecteur dit « 1 » ; une PR de tickets passe par l'axe « Tickets » ; un Relecteur relancé à neuf en plein tour reprend la file ; sur un dépôt sans la clé, tout se passe comme en 7 ; un sujet en 7 reçoit `develop` reposé et sa PR suivante est jugée en 8 ; une livraison finale dont le sujet porte un commit poussé à la main est renvoyée.
