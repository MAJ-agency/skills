# Hexagonal Architecture — {{TITRE}} Backend Guide

This guide describes how the project backend is structured following hexagonal (ports & adapters) architecture principles. It is **not** limited to HTTP endpoints: an endpoint is just one kind of inbound adapter among several. The guide is organized **domain-first** — we start from the business core and work outward toward the technical adapters.

> **Mental model.** Think of the application as a walled city (the domain). _Ports_ are the gates in the wall — they define who is allowed to pass and in which direction. _Adapters_ are the roads outside the gates: HTTP, a database driver, an upstream API, an identity provider. The city does not know or care which road you took; it only knows the gate. Swap any road and the city is unchanged.

**Stack.** Kysely, not an ORM · Zod / `nestjs-zod` for validation, not `class-validator` · UUID v7 minted app-side · Vitest · pnpm. Domain vocabulary is **French**.

The binding, machine-readable rules are in [`../CLAUDE.md`](../CLAUDE.md). This document is the _why_ — read it when a rule is unclear. The ADRs ([`../../../docs/adr/`](../../../docs/adr/)) are the ultimate authority on the decisions cited throughout.

> **Provenance & placeholders.** Generated by the `socle-nest-hexagonal` skill. Examples use a **deliberately neutral placeholder domain** (`Demande`, `Ressource`) — they illustrate _shape_, not this project's domain, which is not modelled yet. Kept in English so it stays diffable against the upstream template.

## Architecture Overview

The backend separates **business logic** from **technical concerns** through explicitly defined interfaces (ports).

- **Domain Layer** — pure business logic. Models, value objects, domain services, domain events, domain errors. Zero framework or infrastructure dependency.
- **Application Layer** — use cases orchestrating the domain. Depends only on ports (interfaces), never on concrete adapters.
- **Infrastructure Layer** — the technical world: inbound adapters (controllers, webhook handlers, cron, CLI) and outbound adapters (Kysely repositories, HTTP clients, config).

Two families of ports:

- **API ports** (inbound / driving): the contract an inbound adapter uses to _drive_ the application. Implemented by use cases.
- **SPI ports** (outbound / driven): the contract the application uses to reach the outside world. Implemented by outbound adapters.

> A cron job that syncs an upstream referential and an HTTP controller that creates a record both call the same kind of API port. The transport differs; the use case underneath is the same.

## The Dependency Rule

Dependencies always point **inward**:

```
Inbound Adapter ─▶ API Port ─▶ Use Case ─▶ SPI Port ◀─ Outbound Adapter
  (controller,      (inbound    (application  (outbound    (Kysely repo,
   webhook,          port)       layer)        port)        HTTP client,
   cron, cli)                                               object storage…)
```

- The domain depends on nothing.
- The application depends only on the domain and on port interfaces.
- Infrastructure depends on the application and domain — never the reverse.
- Concrete adapters are wired to ports **only** in the module (composition root), via string tokens. No layer imports a concrete adapter class except the module that registers it.

**Litmus test:** if you deleted the entire `infrastructure/` folder, `domain/` and `application/` must still compile. If they don't, a dependency is pointing the wrong way. `check:arch` enforces this in CI.

## Layer & Folder Structure

```
src/
├── domain/                              # innermost — pure business
│   ├── shared/                          # value objects, DomainError, shared SPIs (IClock…)
│   └── <domain>/
│       ├── models/<entity>/             # entities, value objects, output DTOs
│       ├── services/                    # domain services (multi-entity logic)
│       ├── events/                      # domain events
│       ├── errors/                      # domain error types
│       ├── api/<feature>/               # API ports (inbound)
│       └── spi/                         # SPI ports (outbound)
│
├── application/                         # use cases, application services, mappers
│   └── <domain>/
│       ├── <feature>/<action>/
│       │   ├── <action>.use-case.ts
│       │   ├── <action>.zod.ts          # internal validation (optional)
│       │   └── ports/ + mappers/        # mapper INTERFACE (ports/) + impl (mappers/)
│       └── services/                    # shared application services
│           └── <name>.service.ts
│
└── infrastructure/                      # outermost — technical
    ├── app/app.module.ts                # composition root + routing
    ├── <domain>/<domain>.module.ts      # feature module (wiring)
    ├── <domain>/<feature>/
    │   ├── controller/                  # HTTP inbound adapter
    │   ├── webhook/                     # webhook inbound adapter
    │   ├── scheduler/                   # cron inbound adapter
    │   └── dto/                         # input DTOs (createZodDto)
    └── providers/
        ├── persistence/postgres/        # Kysely outbound adapters
        │   ├── repositories/            # SPI implementations
        │   └── unit-of-work/            # transaction boundary
        ├── http/                        # upstream API clients
        ├── config/                      # typed config port backed by env
        └── logger/
```

> Data-row types are **generated** by `kysely-codegen` into `src/db/types.ts` and consumed only inside repositories. There is no `entities/` folder with decorated classes — Kysely has no entity objects.

## Domain Layer

### Domain Models & Entities

Plain TypeScript classes representing business concepts. They **carry behavior**, not just data — resist the anemic model where every model is a struct with a `mapToOutput()` and nothing else.

```typescript
// domain/demande/models/demande/demande.ts   (placeholder domain — illustrative only)
export type EtatDemande = "acceptee" | "en_attente";

export class Demande {
  private constructor(
    readonly id: string,
    readonly ressourceId: string,
    readonly titulaireId: string,
    readonly etat: EtatDemande,
    readonly idempotencyKey: string,
  ) {}

  // Factory enforces the invariant at construction time.
  static creer(params: {
    id: string;
    ressourceId: string;
    titulaireId: string;
    placeObtenue: boolean;
    idempotencyKey: string;
  }): Demande {
    if (params.idempotencyKey.length < 8) {
      throw new IdempotencyKeyInvalideError(params.idempotencyKey);
    }
    return new Demande(
      params.id,
      params.ressourceId,
      params.titulaireId,
      params.placeObtenue ? "acceptee" : "en_attente",
      params.idempotencyKey,
    );
  }

  estEnAttente(): boolean {
    return this.etat === "en_attente";
  }
}
```

**Key points:**

- Enforce invariants in the model (constructor / factory), not in the use case.
- Behavior that operates on a single entity's data belongs on that entity.
- No `nestjs-zod`, no Kysely types, no NestJS decorators here.
- Identifiers are UUID v7, minted app-side — the model receives the `id`, it doesn't ask the database for one.

### Value Objects

Immutable, equality-by-value, self-validating. `Montant` (money in cents), `Email`, `Periode`. They eliminate primitive obsession and centralize validation.

```typescript
// domain/shared/value-objects/montant.ts
export class Montant {
  private constructor(private readonly cents: number) {} // integer, ≥ 0

  static enCents(value: number): Montant {
    if (!Number.isInteger(value) || value < 0) throw new MontantInvalideError(value);
    return new Montant(value);
  }

  plus(other: Montant): Montant {
    return new Montant(this.cents + other.cents);
  }
  enCentimes(): number {
    return this.cents;
  }
  equals(other: Montant): boolean {
    return this.cents === other.cents;
  }
}
```

> **Analogy.** A value object is like a banknote: two 10 € notes are interchangeable (equality by value, no identity), and you can't have a −3 € note (invariant enforced on creation). An entity is like a person holding the notes: it _has_ an identity that persists even as its attributes change.

### Domain Services

For logic that spans **several entities** and therefore doesn't naturally belong to any single one. Pure, no infrastructure.

```typescript
// domain/demande/services/eligibilite.service.ts
export class EligibiliteService {
  // A policy spanning two entities belongs to neither alone.
  evaluer(ressource: Ressource, statut: StatutTitulaire): DecisionEligibilite {
    /* multi-entity coordination */
  }
}
```

Register it as a provider by token like everything else. Keep it stateless.

### Domain Events

Something meaningful happened in the domain. Emitted by the domain/application, handled by subscribers (which may themselves be use cases behind inbound adapters).

```typescript
export class DemandeAccepteeEvent {
  constructor(
    readonly demandeId: string,
    readonly occurredAt: Date,
  ) {}
}
```

Publishing goes through an SPI port (`IEventPublisher`) so the domain stays ignorant of NestJS `EventEmitter`, a queue, or an audit sink.

### Domain Errors

Typed business errors, distinct from technical errors. They carry meaning; the mapping to HTTP status codes happens later in an exception filter (infrastructure), so the domain never mentions HTTP.

```typescript
// domain/shared/errors/domain.error.ts
export abstract class DomainError extends Error {
  abstract readonly code: string;
}

export class RessourceIntrouvableError extends DomainError {
  readonly code = "RESSOURCE_INTROUVABLE";
}
```

## Ports

### API Ports (inbound)

Contract that inbound adapters use to drive a use case. One port per use case, single `execute()`.

```typescript
export interface ICreerDemandeUseCaseParams {
  accountId: string; // identity, from the session — never a client-supplied field
  ressourceId: string;
  titulaireId: string;
  idempotencyKey: string;
}
export interface ICreerDemandeUseCase {
  execute(params: ICreerDemandeUseCaseParams): Promise<DemandeDto>;
}
```

Naming: `I{Action}{Entity}UseCase`. Return type is an **output DTO** (a Zod-inferred contract type), not a domain model.

### SPI Ports (outbound)

Contract the application uses to reach anything external. **Persistence is only one kind** — an SPI can be an HTTP client, a clock, a publisher, the unit of work.

```typescript
export interface IDemandeRepository {
  parIdempotencyKey(key: string): Promise<Demande | null>;
  // Atomic conditional claim: true if capacity was secured.
  reserverPlace(ressourceId: string): Promise<boolean>;
  enregistrer(demande: Demande): Promise<Demande>;
}

export interface IUnitOfWork {
  run<T>(work: () => Promise<T>): Promise<T>;
}

export interface IClock {
  now(): Date;
}

export interface IEventPublisher {
  publish(event: object): Promise<void>;
}
```

Methods take and return **domain models / value objects**, never Kysely row types or external DTOs.

> **Analogy.** SPI ports are wall sockets. The application "plugs into" a gateway port without knowing whether the wall is wired to the real upstream service or a local mock. Change the wiring behind the socket; the appliance is unaffected.

## Application Layer (Use Cases)

A use case implements one API port, depends only on SPI ports (injected by token), holds business orchestration, and returns an output DTO.

> **Use case vs. service — the discriminator.** A **use case** is business logic that **answers a user/business request**. A **service** is a compartmentalized internal _tool_ used by business logic or by the infrastructure — shared across use cases or not. The discriminator is **"does it answer a business request?"**, not "is it shared?". Tools come in three shapes depending on what they touch: a **domain service** (pure, `domain/<domain>/services/`), an **application service** (orchestrates SPI ports, `application/<domain>/services/`), or an **SPI port + adapter** (touches concrete tech, `infrastructure/`). **Do NOT wrap a tool in an empty use case.** A "use case" that only forwards to one SPI port with no business logic is a smell — the tool already exists; expose it directly. Example: issuing a CSRF token is a security _tool_ (`ICsrfService`), not a business request, so the controller calls `ICsrfService.emettre` directly (exactly like `CsrfGuard` does) — there is no `IssueCsrfUseCase`.

```typescript
export class CreerDemandeUseCase implements ICreerDemandeUseCase {
  constructor(
    @Inject("IUnitOfWork") private readonly uow: IUnitOfWork,
    @Inject("IDemandeRepository") private readonly demandes: IDemandeRepository,
    @Inject("IEventPublisher") private readonly events: IEventPublisher,
    @Inject("IDemandeMapper") private readonly mapper: IDemandeMapper,
    @Inject("IClock") private readonly clock: IClock,
  ) {}

  execute(params: ICreerDemandeUseCaseParams): Promise<DemandeDto> {
    // One transaction: the ownership check, the atomic claim and the insert
    // commit or roll back together.
    return this.uow.run(async () => {
      const existant = await this.demandes.parIdempotencyKey(params.idempotencyKey);
      if (existant) return this.mapper.toOutput(existant); // idempotent replay

      const placeObtenue = await this.demandes.reserverPlace(params.ressourceId);

      const demande = Demande.creer({
        id: uuidv7(),
        ressourceId: params.ressourceId,
        titulaireId: params.titulaireId,
        placeObtenue,
        idempotencyKey: params.idempotencyKey,
      });
      const enregistree = await this.demandes.enregistrer(demande);

      await this.events.publish(new DemandeAccepteeEvent(enregistree.id, this.clock.now()));
      return this.mapper.toOutput(enregistree);
    });
  }
}
```

- No `@Injectable()` on use cases (registered manually by token in the module).
- Throw **domain errors**; let the exception filter translate them.
- The use case never imports Kysely (`db`, `sql`, `Transaction`). The transaction is opened by the `IUnitOfWork` port; the atomic UPDATE lives inside the repository.

### Orchestration & composition

- A use case may call **several SPI ports**. That's normal orchestration.
- **Use case calling another use case: forbidden.** Shared logic goes into a collaborator injected by token into both use cases. Chaining couples two entry points; a collaborator stays reusable and testable. **Which kind of collaborator depends on whether the shared logic does I/O:**
  - **pure** shared logic (spans entities, no I/O) → a **domain service**.
  - shared logic that **orchestrates SPI ports** (persistence, crypto, HTTP…) → an **application service**. It cannot be a domain service — a domain service is pure and may not touch I/O, even through a port.

### Application services

A shared collaborator that is **neither a use case** (not driven by an inbound API port) **nor a domain service** (it orchestrates SPI ports, so it isn't pure) **nor a mapper**. Example: `EmetteurSession` — issuing a session (persist a refresh token + sign the access JWT + compute the CSRF token) is needed by both `Login` and `RefreshSession`.

- Lives in `application/<domain>/services/` and is named `<name>.service.ts` — the location and name must announce what it is.
- Depends **only on SPI ports** (like a use case). Never imports concrete infrastructure — `check:arch` proves it stays in the application layer.
- Registered by token and injected into the use cases that share it.

### Transactions & the Unit of Work

A use case that writes more than one row wraps its work in `IUnitOfWork.run`. Either everything commits, or nothing does.

> In a multi-tenant service the primitive would be `runInTenant(tenantId, work)`, because there a transaction is also the tenant boundary — Row-Level Security reads the tenant from a per-transaction setting. **This service is single-tenant (`ARC-2`)**, so the primitive is just `run(work)`: a transaction, and nothing else.

```typescript
await this.uow.run(async () => {
  const place = await this.demandes.reserverPlace(ressourceId); // atomic
  await this.demandes.enregistrer(demande); // same tx
});
```

The transaction is stashed in a **continuation-local store** (`nestjs-cls`, backed by `AsyncLocalStorage`) so repositories pick it up ambiently — no `trx` parameter on any port method. That matters for the hexagon: a port signature must stay expressible without naming the database.

```typescript
export interface TrxStore extends ClsStore {
  trx: Transaction<DB>;
}

@Injectable()
export class KyselyUnitOfWork implements IUnitOfWork {
  constructor(private readonly cls: ClsService<TrxStore>) {}

  run<T>(work: () => Promise<T>): Promise<T> {
    // cls.run() guarantees a context even outside an HTTP request (cron/CLI).
    return this.cls.run(() =>
      db.transaction().execute((trx) => {
        this.cls.set("trx", trx);
        return work();
      }),
    );
  }
}
```

`nestjs-cls` is imported **only** in the infrastructure layer — never in `domain/`/`application/`; `check:arch` + `no-restricted-imports` enforce it. `ClsModule.forRoot()` is registered once in the infrastructure module.

### Mappers

A mapper translates a domain model into an **output DTO** (a contract type). It lives in the application layer — never on the domain entity (an entity method returning a contract type would drag the outer-layer contract into the domain). Keep it **pure and synchronous** — no I/O.

Two acceptable forms, by complexity:

**1. Trivial, dependency-free mapping → a pure function.** For a field-for-field projection, a plain exported function is the right weight. No class, no token, no wiring.

```typescript
export function accountVersPublic(account: Account): AccountPublicDto {
  return { id: account.id, email: account.email };
}
```

**2. Needs (or will need) a dependency → an injectable mapper behind a real interface.** When the mapping must receive something injected (a URL signer's inputs, a config, a locale), define the **interface in `ports/`** and the impl in `mappers/`, wired by token.

```typescript
export const DEMANDE_MAPPER = "IDemandeMapper";
export interface IDemandeMapper {
  toOutput(model: Demande): DemandeDto;
}

@Injectable()
export class DefaultDemandeMapper implements IDemandeMapper {
  /* … */
}
// module: { provide: DEMANDE_MAPPER, useClass: DefaultDemandeMapper }
```

> **No lying tokens.** A DI token named `"IXxxMapper"` **MUST** have a matching interface `IXxxMapper` that the injected field is typed by. An injectable class + an `"IXxx"` token _without_ the interface is the worst of both worlds (ceremony **and** dishonest coupling) — use the pure function (form 1) instead. This rule applies to every port token, not just mappers: the token name promises an interface; the interface must exist.

Persistence mapping (domain model ↔ Kysely row) stays **private inside the repository** and never leaks into the application.

## Ownership & isolation

This service is **single-tenant, with no role catalogue** (`ARC-2`). There is no `tenant_id`, no Row-Level Security, no `runInTenant`.

**That removes a safety net, and the consequence is the whole point of this section.** With RLS, a forgotten `WHERE` turns a query into an empty result, not a leak. Here there is nothing behind you — **the explicit check IS the protection**.

- **MUST**: a use case touching a resource that belongs to someone proves that ownership **explicitly**, inside the transaction, before acting. Identity comes from the session (`req.session.sub`), never from a client-supplied field.
- **A foreign key is not a proof of ownership.** It proves a row exists, not that it is yours. `WHERE id = :id` alone is a leak waiting for its first URL guess.
- **Prefer `404` to `403`** when the existence of the resource is itself information the caller should not have.
- **MUST**: every route reading or writing an owned resource carries a test proving another account is refused. With no RLS backstop, that suite _is_ the isolation proof — treat it as a blocking gate (`docs/methode/pare-feu-ci.md`).

Should the project ever need real multi-tenancy, that is a reopening of `ARC-2` — a migration plus a review of every data access, not a flag to flip.

## Inbound Adapters

All inbound adapters do the same three things: (1) translate transport input into a port param object, (2) call `execute()` on the API port, (3) translate the result/exception back to the transport. They contain **no business logic**.

> **Exception — pure infra/security tools.** When a route exposes an infrastructure/security _tool_ rather than a business capability (e.g. re-issuing a CSRF token), there is no use case: the controller calls the relevant **SPI service directly**, exactly as a guard does. This is not a business request, so wrapping it in a use case would be empty ceremony.

### HTTP Controllers

```typescript
// AuthGuard and CsrfGuard are global (APP_GUARD): no @UseGuards needed —
// every route is authenticated by default, every mutation requires
// Origin + CSRF. Opt-out is explicit via @Public().
@Controller("ressources/:ressourceId/demandes")
export class DemandeController {
  constructor(@Inject("ICreerDemandeUseCase") private readonly creer: ICreerDemandeUseCase) {}

  @Post()
  creerDemande(
    @Param("ressourceId") ressourceId: string,
    @Req() req: AuthedRequest,
    @Body() body: CreerDemandeDto, // createZodDto(CreerDemandeInput)
  ): Promise<DemandeDto> {
    return this.creer.execute({
      ressourceId,
      titulaireId: body.titulaireId,
      idempotencyKey: body.idempotencyKey,
      accountId: req.session.sub, // identity from the session
    });
  }
}
```

Input DTOs are built with `createZodDto(SomeSchema)` and live in `infrastructure/<domain>/<feature>/dto/`. They are validated by the **global `ZodValidationPipe`** (wired in `main.ts`). Swagger is generated from the Zod schema via `nestjs-zod` — there is no `@ApiProperty`, no `class-validator`.

### Webhook handlers

A webhook is just another inbound adapter driving a use case. It owns transport concerns only: signature verification over the **raw body**, replay window, idempotent acknowledgement. The business effect lives in the use case.

```typescript
@Controller("webhooks/<vendor>")
export class VendorWebhookController {
  constructor(
    @Inject("ITraiterEvenementUseCase") private readonly traiter: ITraiterEvenementUseCase,
  ) {}

  @Post()
  async handle(@Req() req: RawBodyRequest<Request>): Promise<void> {
    const evt = verifierSignature(req.rawBody, req.headers); // timingSafeEqual, ±5 min
    await this.traiter.execute({ reference: evt.reference });
  }
}
```

### Scheduled Jobs (Cron)

```typescript
@Injectable()
export class SyncScheduler {
  constructor(@Inject("ISyncUseCase") private readonly sync: ISyncUseCase) {}

  @Cron(CronExpression.EVERY_HOUR)
```

### CLI Commands

Using `nest-commander`, a command is an inbound adapter for one-off/admin operations (a manual re-sync, a backfill), again delegating to a use case.

## Outbound Adapters

### Persistence (Kysely repositories)

Implements a persistence SPI with Kysely. Reads the ambient `Transaction<DB>` (set by the unit of work), maps row↔model **privately**, returns domain models, logs and rethrows on error. Row types come from `kysely-codegen` (`src/db/types.ts`) and **never** leave the repository.

```typescript
@Injectable()
export class DemandeRepository implements IDemandeRepository {
  constructor(
    private readonly cls: ClsService<TrxStore>,
    @Inject("IAppLoggerService") private readonly logger: IAppLoggerService,
  ) {}

  private get trx(): Transaction<DB> {
    const trx = this.cls.get("trx");
    if (!trx) throw new Error("Repository used outside a unit of work (no transaction)");
    return trx;
  }

  // Atomic conditional claim — one statement, impossible to exceed capacity.
  async reserverPlace(ressourceId: string): Promise<boolean> {
    const res = await sql<{ id: string }>`
      UPDATE ressource SET places_prises = places_prises + 1
      WHERE id = ${ressourceId} AND places_prises + 1 <= capacite
      RETURNING id`.execute(this.trx);
    return res.rows.length > 0;
  }

  async parIdempotencyKey(key: string): Promise<Demande | null> {
    try {
      const row = await this.trx
        .selectFrom("demande")
        .selectAll()
        .where("idempotency_key", "=", key)
        .executeTakeFirst();
      return row ? this.toModel(row) : null;
    } catch (error) {
      this.logger.error(DemandeRepository.name, error, { handler: "parIdempotencyKey" });
      throw error;
    }
  }

  private toModel(row: Selectable<DB["demande"]>): Demande {
    /* map Kysely row → domain model (private, never leaks) */
  }
}
```

Schema changes go through a hand-written Kysely migration in `src/db/migrations/` (run by the owner role), after which `src/db/types.ts` is regenerated by `kysely-codegen`. The anti-drift CI gate (`git diff --exit-code` on generated types) fails if a migration wasn't reflected.

### External HTTP clients

An adapter for an upstream API implements a port declared in the domain, so the application never knows the vendor or the wire format. Swapping a mock for the real gateway means writing a new adapter and changing one line in the module — the use cases don't move.

```typescript
@Injectable()
export class UpstreamClient implements IUpstreamPort {
  constructor(
    private readonly http: HttpService,
    @Inject("IAppLoggerService") private readonly logger: IAppLoggerService,
  ) {}
  async statut(reference: string): Promise<StatutRef> {
    /* call upstream, map external DTO → internal type at the edge */
  }
}
// module: { provide: UPSTREAM_PORT, useClass: UpstreamClient }
```

In local dev these ports are backed by **Prism mocks** served from OpenAPI specs (mocks-first: a contract that exists before the real endpoint does). Decide per integration whether a failure is **blocking or degrading** — and make it explicit in the port's contract, not implicit in the adapter.

### Configuration as a port

Don't reach for `process.env` or NestJS `ConfigService` inside a use case — that couples the application to a framework/runtime detail. Validate the environment once at boot into a typed `env` object (Zod, fail-fast). Expose a typed config **port** and back it with `env` in the adapter.

```typescript
export interface I{{TITRE}}Config {
  get modeEmission(): "mock" | "reel";
}
// infrastructure adapter reads `env` and implements it; wired by token
```

## Cross-Cutting Concerns

### Error handling & exception filters

Domain errors are thrown deep inside; a single global **exception filter** maps them to HTTP status codes. This keeps status codes out of the domain.

```typescript
@Catch(DomainError)
export class DomainErrorFilter implements ExceptionFilter {
  private readonly status: Record<string, number> = {
    RESSOURCE_INTROUVABLE: HttpStatus.NOT_FOUND,
    TITRE_INVALIDE: HttpStatus.UNPROCESSABLE_ENTITY,
  };
  catch(err: DomainError, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    res
      .status(this.status[err.code] ?? HttpStatus.BAD_REQUEST)
      .json({ code: err.code, message: err.message });
  }
}
```

Distinguish **domain errors** (expected business outcomes) from **technical errors** (DB down, timeout) — the latter are logged and surfaced as 5xx.

### Auth guards, interceptors, middleware

These are infrastructure inbound concerns and must not contain business logic. A guard decides _who may drive_ a use case; it never decides _what the use case does_.

- `AuthGuard` verifies the short access JWT from the `__Host-` cookie and populates `req.session`.
- `CsrfGuard` validates the signed double-submit token (`X-CSRF-Token`) against `req.session.sid` and checks `Origin`; safe methods (`GET`/`HEAD`/`OPTIONS`) are exempt.
- Both are registered **globally** (`APP_GUARD`, declaration order = execution order: `AuthGuard` then `CsrfGuard`). Every route is authenticated by default; opt-out is explicit via `@Public()` and reserved for truly anonymous routes (login, refresh, health).
- The session carries **identity** (`sub`, `sid`) and nothing more. Ownership of a resource is proven in the use case, explicitly — see [Ownership & isolation](#ownership--isolation).

### Contract boundaries (sealed universes)

Enforced by lint (`no-restricted-imports` / `eslint-plugin-boundaries`) and replayed in CI:

- **Internal API** = Zod contract schemas. A client imports **only** the contracts — never a DB row type, never an external DTO.
- **Data** = `kysely-codegen` types in `src/db/types.ts` — never leave the repository layer.
- **External APIs** = OpenAPI DTOs confined to adapters, mapped to internal types at the edge.

### Logging

Logging is an SPI (`IAppLoggerService`) injected by token — **never** a `new Logger()` instantiated in a use case or application service (that couples the layer to the NestJS runtime, exactly like `ConfigService`). Only the infrastructure adapter touches the concrete framework logger.

```typescript
// ❌ never — concrete framework service hard-instantiated (blocked by no-restricted-imports)
private readonly logger = new Logger(MyUseCase.name);

// ✅ inject the port
constructor(@Inject("IAppLoggerService") private readonly logger: IAppLoggerService) {}
this.logger.error(MyUseCase.name, "message", { handler, data });
```

Log at inbound entry points, outbound operations, and error scenarios. Keep it structured (`{ handler, data }`).

**Severity → channel.** A technical log (`IAppLoggerService` → pino) is ephemeral diagnostics. A **sensitive business event** — a state transition carrying money, identity or entitlement — is business traceability and belongs in the immutable append-only `audit_log` via the `IAuditLog` port, not just a `logger.error`.

## Dependency Injection Pattern

Interface-based DI with **string tokens** for loose coupling. (`Symbol` tokens are equally valid; keep a token style consistent within a module.)

```typescript
// registration (module)
{ provide: 'IDemandeRepository', useClass: DemandeRepository }
{ provide: 'ICreerDemandeUseCase', useClass: CreerDemandeUseCase }

// injection (use case / adapter)
constructor(@Inject('IDemandeRepository') private readonly demandes: IDemandeRepository) {}
```

Rules: token = interface name; the field is typed by the **interface**, never the implementation; **the interface named by the token must actually exist** (no lying tokens); every provider is registered in a module; the module is the only place that references concrete classes. Application services are the one tolerated exception typed by their concrete class — they have no boundary to invert; still, place them in `application/<domain>/services/*.service.ts`.

Common tokens: `'IAppLoggerService'`, `'IUnitOfWork'`, `'IEventPublisher'`, `'IClock'`, `'IAuditLog'`, each repository, plus the integration ports.

---

## Module Organization & Bootstrap

- **Feature modules** (`<domain>.module.ts`) wire controllers/webhooks/schedulers with their use cases, repositories, mappers, and domain services — all by token.
- **Shared/infrastructure modules**: logger, the Kysely connection + `ClsModule.forRoot()` + the unit of work, auth, config.
- **Root module** (`app.module.ts`) imports feature modules.
- **`main.ts`** applies `cookieParser`, the global `ZodValidationPipe`, the `DomainErrorFilter`, CORS (`credentials: true`), then `listen()`.

```typescript
@Module({
  controllers: [DemandeController],
  providers: [
    { provide: "IDemandeRepository", useClass: DemandeRepository },
    { provide: "IDemandeMapper", useClass: DefaultDemandeMapper },
    { provide: "ICreerDemandeUseCase", useClass: CreerDemandeUseCase },
    EligibiliteService,
  ],
})
export class DemandeModule {}
```

---

## Inter-module Communication

When module A needs domain B, do **not** import B's repository or reach into its row types. Depend on a **port B exposes** (its API use case or a dedicated SPI), wired in A's module. This keeps domains decoupled and their internals substitutable. If two domains constantly need each other's internals, that's a signal the boundary is drawn in the wrong place.

For asynchronous decoupling, communicate via **domain events**: A publishes, B subscribes through its own inbound adapter. No direct call, no shared transaction.

## Testing Strategy

Test every layer; mock at the port boundary. **Vitest** (`vitest run`), not Jest.

- **Domain models / value objects / services** — pure unit tests, no NestJS. Target ~100% on invariants and behavior.
- **Use cases** — `Test.createTestingModule` with **mocked SPI ports** (typed mocks provided as `useValue`). Cover happy path, domain-error paths, idempotent replay, edge cases. Assert ports are called with the right params. The use case has no `@Injectable()` — provide it as a class + its ports as mocks.
- **Repositories / outbound adapters** — **integration tests against a real Postgres** (the transaction boundary cannot be meaningfully mocked). Verify row↔model mapping, atomic-claim behavior under contention, and idempotency. External HTTP clients: verify external-DTO → domain mapping and error handling.
- **Ownership** — every route touching an owned resource is tested against another account, and refused. With no RLS backstop this suite is the isolation proof: blocking.
- **Inbound adapters** — controller e2e-style with `supertest` (override guards/config, apply the real global `ZodValidationPipe` + `DomainErrorFilter`) to assert status codes, response shape, validation (400) and error mapping (5xx). For webhooks/cron/CLI, unit-test that the adapter deserializes/verifies input and calls `execute()` correctly.

Shared mocks live in `src/utils/tests/mocks/` (`@test/mocks/`). Use AAA (Arrange-Act-Assert), fresh mocks per test (`afterEach(() => vi.clearAllMocks())`), one concern per test, descriptive names (`should [behavior] when [condition]`). Tests covering a registered rule carry its ID in the name. Test behavior, not implementation.

## Checklists

### New domain concept

- [ ] Model / value object with invariants enforced at construction (UUID v7 minted app-side)
- [ ] Domain service if logic spans entities
- [ ] Domain error type(s) extending `DomainError`
- [ ] Domain event(s) if state change matters to others
- [ ] Unit tests for behavior & invariants

### New use case

- [ ] API port (`I{Action}{Entity}UseCase`), identity sourced from the session
- [ ] SPI port(s) needed (repo / gateway / clock / publisher …)
- [ ] Use case implementation (throws domain errors, wraps multi-write work in `IUnitOfWork.run`, proves ownership explicitly)
- [ ] Mapper — pure function (trivial mapping) **or** injectable behind a real `IXxxMapper` interface (never a token without its interface); output DTO from the contracts
- [ ] Internal Zod schema if needed
- [ ] Use case tests with mocked SPIs (incl. idempotent replay)
- [ ] Register use case, ports, mapper in module

### New inbound adapter

- [ ] Controller / webhook / scheduler / command
- [ ] Input DTO via `createZodDto` (for HTTP)
- [ ] Guards global by default; any `@Public()` justified
- [ ] Delegates to API port only — no business logic
- [ ] Adapter tests (supertest for HTTP; unit for others)
- [ ] Registered in module

### New outbound adapter

- [ ] SPI port defined in domain
- [ ] Kysely repository reads ambient `trx`, maps to/from domain, logs & rethrows
- [ ] Migration (if persistence) + regenerated `src/db/types.ts`
- [ ] Row types never leak past the repository
- [ ] Adapter/integration tests (real Postgres for repos)
- [ ] Wired by token in module (single line to swap implementations)

### Always

- [ ] `domain/` + `application/` still compile without `infrastructure/` (`check:arch`)
- [ ] No multi-write path outside `IUnitOfWork.run` ; every owned resource access proves ownership
- [ ] `test` green (ownership-refusal cases included), coverage acceptable
- [ ] Contracts updated if the internal contract changed; Swagger reflects it

## Recipes

### Recipe: HTTP endpoint (end to end)

The most common path, expressed with the layers above. Order — **domain-first**:

1. **Domain** — model/value objects, output DTO, domain errors; API port; SPI port(s). _(+ tests)_
2. **Application** — use case implementing the API port; mapper; optional internal Zod schema. _(+ tests)_
3. **Infrastructure (outbound)** — Kysely repository implementing the SPI (+ migration + regenerated types if the schema changes). _(+ tests)_
4. **Infrastructure (inbound)** — input DTO (`createZodDto`); controller delegating to the API port. _(+ tests)_
5. **Wiring** — register repository, use case, mapper in the feature module.

Runtime flow:

```
HTTP POST /ressources/:ressourceId/demandes
  → AuthGuard (JWT cookie) → CsrfGuard (signed double-submit)
  → ZodValidationPipe validates input DTO (createZodDto)
  → Controller reads identity from req.session, builds param object
  → API port .execute()
  → Use case: uow.run() → { one transaction }
       → ownership proven explicitly (no RLS backstop)
       → repo.reserverPlace (atomic UPDATE)
       → repo.enregistrer → event publish
  → domain error? → DomainErrorFilter → HTTP status
  → success → mapper → DemandeDto → JSON
```

Everything a "create an endpoint" task needs is just this recipe; everything _else_ in the backend (webhooks, cron, CLI, external gateways, events) reuses the exact same ports and use cases underneath.
