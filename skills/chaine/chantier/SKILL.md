# Chantier : le conducteur de bout en bout

Mode d'emploi de fond : `docs/agents/chaine-de-production.md` (rôles § 1, cycle § 2, ticket prêt § 3, fichiers chauds § 4, consignes des filles § 5, économie de tokens § 6), posé par `socle-chaine-de-production`. Cette skill l'exécute dans l'ordre. **Cette session ne tient que ce rôle** : tout autre livrable (deck, étude, recette) part dans une autre session. Contrat du projet : `.claude/chaine.json` (`fillesParVague`).

**Deux régimes, jusqu'au nettoyage du plugin.** Une PR est en **régime 8** (relecture indépendante) quand sa base, `origin/develop` ou `origin/sujet/<nom>` et celle-là seule, porte la clé `relecture` dans `.claude/chaine.json` **et** qu'elle a été ouverte après `relecture.depuis` ; sinon en **régime 7**. Une fille le lit dans la sortie de `sujet.sh demarrer` (la ligne `régime 8 : relecture indépendante ; …`) ; un chantier ouvert avant la repose change de régime ticket par ticket. Ce skill décrit le régime 8 ; ce qui ne vaut qu'en régime 7 (la ligne `Label: contre-revue`, la contre-revue du conducteur, la livraison selon `Label:`) est dans [`references/regime-7.md`](references/regime-7.md), à suivre pour toute PR en régime 7.

**Où commence ce skill, à qui parle cette session.** Elle est le **conducteur de chantier** : elle fait tourner un chantier à partir d'une spec validée. Deux cas, à reconnaître avant tout :

- **Dans un programme** : la fiche de la carte porte une ligne `Architecte:` remplie, ou le prompt de lancement nomme un architecte (une carte sans ligne `Responsable:` date d'avant ces rôles : son `Architecte:` y nomme la session du chantier, pas un architecte de programme). La spec est validée : le skill commence au découpage (`Phase: 2-decoupage`), sans grilling. L'architecte est seul à parler au produit : cette session ne s'adresse jamais au produit. Partout où ce skill dit « le produit » ou `AskUserQuestion`, le même contenu part à **l'architecte**, par `send_message`, et sa réponse arrive comme un tour.
- **Sans programme** : aucun architecte. Cette session parle au produit, par `AskUserQuestion`. Elle mène le grilling court ou aucun (§ 2) ; un grilling complet est le travail d'un architecte : elle le dit au produit, qui ouvre une session d'architecte, et le chantier reprend au découpage, spec validée.

## 0. Reprendre ou démarrer

1. `git fetch origin develop` puis cherche le chantier : argument = nom de sujet → `git ls-remote origin "sujet/<nom>"` et la carte `docs/**/*.map.md` dont la ligne `Sujet:` le cite (sur `origin/sujet/<nom>`, sinon sur `origin/develop`).
2. **Carte trouvée** : lis sa section `## Fiche` (§ 1) et va à la phase indiquée par sa ligne `Phase:`. Ne repose aucune question déjà répondue.
3. **Rien trouvé** : setup (§ 1).
4. **Le terrain.** `.claude/chaine.json` absent → invoquer `/maj-skills:socle-chaine-de-production` (il pose aussi `tickets`) ; `scripts/verify/coverage-diff.mjs` absent → invoquer `/maj-skills:socle-tests`. Chacun ouvre une PR, et **aucune autre fille ne part avant sa fusion** — un chantier sans gates fait coder des filles que rien ne relit. La pose de `socle-chaine-de-production` sur un dépôt qui n'a pas la chaîne n'a ni ticket ni garde : le conducteur la fait lui-même, et sa PR, dont la base n'a pas encore la clé `relecture`, est en régime 7 : elle passe au capitaine comme une PR de cadrage de ce régime, `à-fusionner` posé par le conducteur. En régime 8, un socle posé ensuite (`socle-tests`) touche des chemins sensibles : c'est un ticket du chantier, le premier, avec sa ligne `Sensibles:` (§ 3, point 2), relu comme les autres.
5. Vérifie qu'un capitaine tourne : `list_sessions` sans `tags`, puis garder les lignes dont `tags` contient `role:capitaine` (jamais par le titre ; le filtre `tags` est refusé à une session : « tags filter is not currently available »), au moins une session active (plusieurs sont permises). Sinon, dis-le au produit (il en ouvre une avec le skill `fusionner`) ; on peut avancer jusqu'à la phase 3 sans lui.
6. Vérifie que le **Relecteur** du dépôt tourne (régime 8), quand `.claude/chaine.json` d'`origin/develop` porte la clé `relecture` (sans elle, aucun Relecteur : la ligne `Relecteur:` vaut « absent ») : la ligne `Relecteur:` de la fiche, puis `get_session` sur l'identifiant qu'elle nomme, sans filtre par tag ; dans un programme, l'architecte le lance et te le nomme ; sans programme, s'il n'y en a pas pour le dépôt, le conducteur le lance au lancement de son chantier, par le gabarit de `architecte/references/lancement.md` (« Le Relecteur d'un dépôt »), et inscrit sa session sur la ligne `Relecteur:`. Sans Relecteur, aucune PR en régime 8 n'est relue.

## 1. Setup : les questions

Ne demander que ce que l'argument, le prompt et la spec ne donnent pas, **en une fois**. D'abord en texte libre si absents : l'objectif en une phrase (« ce qu'on doit pouvoir montrer ») et le **responsable**, la personne qui répond du chantier. Puis, pour les seules questions restantes, un seul appel `AskUserQuestion`. **Dans un programme**, ni grilling ni `AskUserQuestion` : la spec validée vaut « grilling : aucun », une vague donnée dans le prompt est **validée**, les défauts du tableau s'appliquent sans demander, et ce qui manque encore (le responsable, une échéance) se demande à l'architecte en un seul `send_message`. Une session lancée par une autre session qui n'est pas un architecte n'a pas non plus de produit devant `AskUserQuestion` : mêmes défauts.

| Question                          | Options (la première est recommandée)                                                                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Échéance ?                        | Démo ou recette datée (la date en « Autre ») · Pas d'échéance                                                                                                |
| Grilling ?                        | Court : je ne tranche que les points ouverts · Aucun : la spec existe (chemin en « Autre ») · Complet : une session d'architecte le mène, le chantier attend |
| Parallélisme : filles par vague ? | la valeur de `.claude/chaine.json` · 3 · 10                                                                                                                  |

Le **modèle des filles** ne se demande pas : il se lit sur la ligne `Modèle:` de chaque ticket.

Puis :

- **Nom du sujet** : `sujet/<chantier>` en kebab-case, proposé et confirmé dans le même message que le récapitulatif.
- **Fiche** : crée la carte **à côté de sa spec, sous le même identifiant** (`<ID>-<slug>.map.md` ; sans spec encore, `node scripts/docs/next-id.mjs SPEC <CTX> <TRI>` donne l'identifiant de la spec à venir), dans `docs/features/<feature>/<ctx>/`. Gabarit : `docs/agents/gabarits/carte.map.md` ; elle commence par la section `## Fiche` (`Phase: 1-grilling`, ou `2-decoupage` dans un programme ; `Responsable:` la personne, jamais un identifiant de session ; `Architecte:` l'id de l'architecte du programme, ligne retirée sans programme ; `Conducteur:` l'id de cette session par `get_session` ; `Objectif:`, `Échéance:`, `Grilling:`, `Filles par vague:`, `Capitaine:`, `Relecteur:`). Une carte déjà ouverte par l'architecte reçoit ici sa ligne `Conducteur:`.
- **Sujet et PR de cadrage** : `bash scripts/chaine/sujet.sh ouvrir <nom>`, branche `docs/<nom>-cadrage` depuis `origin/sujet/<nom>`, commit de la carte, PR **brouillon** vers `sujet/<nom>` par l'outil GitHub MCP (`create_pull_request`, `draft: true`). Elle porte la carte, puis les specs et les tickets ; c'est la réservation visible du chantier.

Chaque changement de phase met à jour la ligne `Phase:` et se pousse : c'est ce qui rend le skill reprenable sans relire la conversation. **Après la PR de cadrage**, une mise à jour de la carte (phase, sessions d'une vague, coût, incidents) se pousse **directement sur `sujet/<nom>`**, sans PR : un **clone normal** sur `origin/sujet/<nom>` (jamais un `git worktree` : le pre-push y lance des tests qui corrompent la config git partagée, `docs/agents/pieges.md`), le seul fichier `*.map.md` dans le commit, modifié en place (`docs(<scope>): carte … (<identifiant>)`), Prettier, puis `bash scripts/chaine/sujet.sh carte <nom>`, qui rattrape le sujet par avance rapide, vérifie chaque commit et pousse sans force (sortie 9 sur tout autre fichier, une carte créée, renommée ou d'un autre sujet, un historique divergent). Jamais `git push origin HEAD:sujet/<nom>` : le hook d'agent refuse tout push vers un sujet. Reste une PR : le cadrage (specs et tickets dont les filles dépendent) et la ligne `Phase: fini`, qui va dans develop.

## 2. Phase 1 — grilling (`Phase: 1-grilling`), sans programme seulement

Dans un programme, cette phase n'existe pas : l'architecte a mené le grilling, la carte commence à `2-decoupage`.

- **Court** : la liste des points ouverts en un message, chacun avec sa recommandation ; le produit répond en bloc.
- **Aucun** : lire la spec donnée, relever ses trous en un message.
- **Complet** : pas ici. Le grilling complet (une question à la fois, recherche avant chaque question, skills `grilling` puis `domain-modeling`) appartient à l'architecte. Le dire au produit, noter `Grilling: complet — architecte` dans la fiche, et s'arrêter là : relancée avec le nom du sujet une fois la spec validée, cette session reprend au découpage.

**Chaque question au produit suit la forme de `chaine-de-production.md` § 2** (« Une question au produit ») : elle n'arrive au produit que si elle change ce que voit un utilisateur, un coût ou un délai ; elle part du besoin, décrit les options par leurs conséquences, recommandation d'abord, sans terme technique. Un choix technique, le conducteur le tranche seul et l'écrit (`A-n`, avec sa raison).

Chaque décision va dans `## Decisions-so-far` de la carte (`A-1`, `A-2`…), ce qui reste flou dans `## Fog`. Une décision qui fixe un terme du domaine est marquée `[terme]` (`docs/agents/domain.md`). Rien d'autre dans le dépôt pendant le grilling. Fin : `Phase: 2-decoupage`.

## 3. Phase 2 — specs, tickets, découpage (`Phase: 2-decoupage`)

0. Specs déjà dans le sujet (`origin/sujet/<nom>`) : noter « phase 3 sautée » dans la fiche ; la PR de cadrage (carte seule) ne bloque alors aucune fille.
1. Specs (`docs/agents/issue-tracker.md`, gabarit `docs/agents/gabarits/spec.spec.md`), `Sujet: sujet/<nom>` en tête. Les décisions `[terme]` deviennent des lignes de `GLOSSARY.md` dans la même PR de cadrage ; une spec n'emploie que des termes du glossaire, et cite les règles métier du registre sans les formuler. Une règle qu'elle porte et que le registre n'a pas encore, le conducteur en écrit le fichier, `candidate`, dans la même PR de cadrage, avant tout code (gabarit `docs/agents/gabarits/regle.md`, fiche d'écriture `.claude/rules/anchorpost.md`), puis lance lui-même le skill `criticite` sur chaque règle : si l'index du projet est au pivot 3, il la classe, écrit le niveau rendu ou un plus haut, et porte la commande jouée et chaque sortie brute dans la section `## Criticité` de la PR de cadrage ; sinon le skill s'arrête. Dans un programme, la spec validée est donnée : ne pas la réécrire, relever ses trous à l'architecte.
2. Tickets **prêts pour agent** au format de `docs/agents/chaine-de-production.md` § 3 (gabarit `docs/agents/gabarits/ticket.issue.md`) : `Blocked by:`, `Modèle:`, `Fichiers chauds:`, `Dépendances:` (chaque paquet que le ticket ajoute, nom sans version, ou `—` : le hook d'agent le laisse passer sans question une fois la ligne fusionnée dans le sujet ; une dépendance hors de cette ligne est un blocage pour la fille, pas un contournement), `Maquette:` (l'artefact et la planche de tout écran touché ; sans planche validée par le produit, le ticket reste `needs-info` et l'écran se dessine d'abord avec lui), sections `Où` / `Décisions` / `Surfaces` / `Vérification`. Toute fonction citée dans `Où` vient avec son **appelant réel** (route, listener, cron). **Fichiers sensibles : l'accord avant le code.** En régime 8, un ticket qui touche un chemin de `cheminsSensibles` porte la ligne `Sensibles:` en tête, qui nomme ces chemins (exacts ou par motifs) puis qui a accordé et quand : `Sensibles: scripts/chaine/passer.sh — accord de <nom>, <AAAA-MM-JJ>`, ou `Sensibles: —`. Sans elle, le hook d'édition refuse l'écriture et le capitaine renvoie la PR. Le conducteur écrit d'abord la demande dans la section `## Fichiers sensibles` de la carte, une ligne par fichier (ticket, chemin, pourquoi, ce qui y change) ; elle part avec le découpage (point 4) ; les lignes `Sensibles:` ne se remplissent qu'après l'accord, dans la PR de cadrage. En régime 8, un ticket qui cite sur sa ligne `Règles:` une règle de criticité haute porte `Relecture: double` (le gate `tickets` l'exige alors d'un ticket ouvert) : deux sessions de relecture. Un ticket ≤ 1 jour. Beaucoup de tickets sur le schéma → un ticket « socle » en vague 1 qui pose tout le schéma et les migrations (horodatages réservés dans le brief). En régime 8, un ticket qui crée un module d'authentification, de droits, de chiffrement, de paiement ou d'export fait ajouter son dossier à `cheminsSensibles` de `.claude/chaine.json` par **un ticket du chantier**, le premier quand d'autres en dépendent, dont la ligne `Sensibles:` nomme `.claude/chaine.json` : un chemin sensible ne se modifie que sur la branche d'un ticket, la PR de cadrage comprise. Un ticket d'écran a sa planche **dans le dépôt** : le conducteur lit l'artefact de maquette et le recopie sous `docs/design/planches/<id>.html` (une fille ne peut pas ouvrir un artefact) ; la ligne `Maquette:` désigne ce fichier.
3. Vagues : `node scripts/docs/vagues.mjs <spec> --max <Filles par vague>` propose les vagues (bloquants faits, fichiers chauds disjoints) ; le conducteur les relit (une raison écrite pour s'en écarter) et les copie dans la carte, section `## Vagues`.
4. **Validation** par `AskUserQuestion` au produit (un seul point de contrôle) ; dans un programme, par `send_message` à l'architecte : le tableau des vagues (ticket, objet, modèle, fichiers chauds) en aperçu, en régime 8 avec la section `## Fichiers sensibles` de la carte, dont l'accord se donne là, une fois (dans un programme, l'architecte la soumet au produit avec le découpage) ; options « Lancer » · « Modifier » (dire quoi) · « Arrêter ici ».
5. « Lancer » : PR de cadrage hors brouillon (`update_pull_request`). En régime 8 (la clé `relecture` dans `.claude/chaine.json` de `origin/sujet/<nom>`), sa relecture se demande comme celle d'une fille (`chaine-de-production.md` § 5, étape 5 : le commentaire `À relire — sommet <sha> — Session: <la sienne> — Conducteur: —`, puis `à-relire` par `issue_write`), jamais `à-fusionner` ; en régime 7, label `à-fusionner` (`issue_write`). `Phase: 3-specs-en-fusion`.

## 4. Phase 3 — specs dans le sujet (`Phase: 3-specs-en-fusion`)

Le capitaine squashe la PR de cadrage dans le sujet dès sa CI légère verte, et, en régime 8, son tour de relecture validé ; sur `à-reprendre`, le conducteur lit le verdict, corrige ou conteste (l'architecte arbitre ; sans programme, le produit) et redemande la relecture (`chaine-de-production.md` § 5, étape 6). **Aucune fille avant** (sauf si les specs sont déjà dans le sujet : phase sautée, § 3 point 0 ; cas vécu : douze PR en conflit). Ne pas sonder : `send_later` à 20 min, puis vérifier que les tickets sont sur `origin/sujet/<nom>`. Fait : `Phase: 4-vague-1`.

## 5. Phase 4 — vagues (`Phase: 4-vague-<k>`)

Pour chaque ticket de la vague, `create_session` :

- `title` : `<Projet> <chantier> — <identifiant> <objet court>` ; `tags` : `["chantier:<nom>"]` ; `source_url` : le dépôt ; `source_revision` : `sujet/<nom>` ; `model` : celui du ticket ; `permission_mode` : `"auto"`.
- `prompt` : le gabarit de `docs/agents/chaine-de-production.md` § 5, cité par renvoi et non recopié, et qui ne commence jamais par « / » (`create_session` refuse un tel prompt ; cas vécu le 2026-11-23). La ligne de situation particulière n'y figure que s'il y en a une, et **ne redit jamais une règle** : le régime se lit dans la sortie de `sujet.sh demarrer`, jamais sur le prompt.

Chaque fille écrit au conducteur (`send_message`) si elle est bloquée, et dès sa relecture demandée, sans attendre ni le verdict, ni les contrôles, ni la fusion : ses cinq lignes de rendu, avec les décisions qu'elle attend de lui (ADR proposée, dépendance, règle à trancher), aussi écrites sous `## Comments` du ticket et dans la PR.

Puis : la vague dans la carte (ticket → session), `/compact`, et `send_later` à 45 min. **Pas d'attente active**, pas de réponse aux fins de session.

**Dernière vague**, si le projet a des E2E joués au passage seulement : poser `ci-complète` sur la première PR qu'une fille ouvre, puis, au réveil qui suit sa sortie du brouillon, relancer son dernier run CI (`actions_list`, puis `actions_run_trigger` `rerun_workflow_run`) : les E2E n'ont tourné sur aucune sous-PR, et le develop reçu par le sujet a pu les casser.

## 6. Suivi (à chaque réveil)

0. **Lire le gel d'abord.** `bash scripts/chaine/sujet.sh gel <nom>` (sortie 0 et la ligne `Gel:` : gelé ; sortie 1 : libre) se lit avant tout, y compris avant de réarmer. **Gelé : ni vague, ni réarmement** : exécuter « Arrêter un chantier » ci-dessous (ce qui n'est pas encore fait), puis s'arrêter sans réveil, pour ne rien coûter. Le produit peut avoir écrit la ligne à la main sur GitHub.
0 bis. **Réarmer.** Première action du réveil libre : `send_later` à 45 min ; dernière action : le remplacer si la suite a changé (vague finie, livraison). Un conteneur redémarré au milieu d'un tour, sans réveil armé, a coûté six heures.
1. `node scripts/docs/avancement.mjs sujet/<nom>` (et `bash scripts/chaine/sujet.sh etat` pour le sujet lui-même) : tickets faits, PR renvoyées (`fusion-bloquée`), sessions bloquées (`list_sessions` sans `tags`, puis les lignes dont `tags` contient `chantier:<nom>` ; `get_session` : `status_bucket` working, blocked, review_ready, completed ou failed, lu préfixé `SESSION_STATUS_BUCKET_` ; `blocked` et `failed` demandent une action). **Contrôle de vie** : le même relevé s'étend aux capitaines du dépôt (mêmes lignes, `tags` contenant `role:capitaine` ; dans un programme, aussi les identifiants de la ligne `Capitaines:` de la carte du programme) et, en régime 8, au Relecteur du dépôt (l'identifiant de la ligne `Relecteur:` de la fiche ; une ligne d'une fille, « `à-relire` depuis plus de trois heures sans distribution », le fait relever aussitôt) et cherche quatre signes dans la réponse de `get_session` : `status_bucket` qui finit par `FAILED` ; `connection_status` égal à `disconnected` ; `external_metadata.rate_limit_info.status` autre que `allowed`, `allowed_warning` compris ; `session_status` qui finit par `RUNNING` avec `updated_at` vieux de plus de 60 minutes (un tour qui ne produit plus rien ; jamais le bucket `WORKING`, où une session qui attend une réponse figure aussi). Le réveil de 45 minutes (point 0 bis) tient sous les 60. Chaque signe va en une ligne au journal de la carte (date, session, rôle, signe), puis au produit (dans un programme, à l'architecte, qui le prévient), dans la forme de `chaine-de-production.md` § 2 pour une coupure (`FAILED`, `disconnected`, silence d'une heure) ; une alerte d'usage se dit en une ligne, une fois par couple (`rateLimitType`, `resetsAt`, en secondes depuis l'époque Unix), car la limite est celle du compte. Rien n'est relancé sans le produit, et une session coupée par la limite d'usage ne se relance pas avant sa levée.
1 bis. **Plafonds.** Le contexte d'une session se lit par `get_session` (`context_usage.used_tokens`), jamais dans ce qu'elle annonce : une session a annoncé 330 000 tokens pour 446 000 relevés. Pour chaque fille du chantier, et pour lui-même, le conducteur compare le contexte relevé par `get_session` (`context_usage.used_tokens`) au seuil de la clé `plafonds` de `.claude/chaine.json` : `contexteFille` pour une fille, `contextePilote` pour lui ; sans la clé, 400 000 tokens pour l'un comme pour l'autre. Le seuil est atteint dès l'égalité. Seul le contexte se juge : le coût se relève dans `## Coût`, il ne déclenche rien. **Un plafond ne coupe rien** : aucune session n'est interrompue, ni une fille ni le conducteur ; elle continue pendant que le produit décide.
   - Une fille au plafond : la ligne dans `## Dépassements` de la carte (session, ticket, mesure, décision du produit « à trancher », date), puis le signalement au produit (dans un programme, à l'architecte, qui prévient le produit), dans la forme de `chaine-de-production.md` § 2 : le besoin en une phrase (le ticket pèse plus que prévu), la mesure, où en est la fille, et ce que le conducteur recommande. Le produit décide ce qu'il veut faire ; sa décision s'applique telle quelle et complète la ligne. Sans ligne, le gate `tickets` refuse la carte.
   - Le conducteur au plafond : la même ligne et le même signalement, puis il finit son réveil. Si le produit décide une session de suite : la passation dans la carte (état, phase, vague en cours, décisions ouvertes), puis la session de suite lancée avec le nom du sujet ; la ligne `Conducteur:` de la fiche la nomme.
   - Une session déjà inscrite dans `## Dépassements` ne se signale pas une seconde fois. Le contrôle a lieu à chaque réveil, soit toutes les 45 minutes : une session peut dépasser un peu avant d'être vue.
2. **Une fille `blocked`** : sa question est à lire dans `list_events` (`kinds: ["assistant"]`) : son `send_message` n'arrive pas toujours. Une demande d'autorisation y apparaît aussi : la remonter au produit (dans un programme, à l'architecte), jamais élargir les permissions.
3. Une PR renvoyée : vérifier que sa fille l'a vue (le capitaine la prévient), sinon `send_message`. Session inactive (`send_message` refusé) : relancer une fille sur la branche de la PR (`source_revision` = la branche) avec, en ligne de situation, le renvoi à lire dans les commentaires de la PR.
4. Une question de fille : y répondre si la carte la tranche ; la trancher soi-même si elle est technique (décision `A-n` dans la carte) ; sinon la **réécrire** dans la forme de `chaine-de-production.md` § 2 (« Une question au produit » : le besoin en une phrase de métier, les options par leurs conséquences, la recommandation d'abord, aucun terme technique) et la remonter au produit par `AskUserQuestion` (dans un programme, à l'architecte par `send_message`). Jamais la question de la fille recopiée telle quelle. Une question en prose est restée 17 h sans réponse : le produit ne savait pas comment répondre ; une question en jargon a reçu « j'ai rien compris ».
5. **La relecture est indépendante : le conducteur ne contre-relit rien et ne relaie aucun constat.** (Régime 8 ; une PR en régime 7 suit `references/regime-7.md`.) Le Relecteur du dépôt lance une session de relecture par PR, qui écrit son verdict sur la PR ; le Relecteur pose `à-reprendre` ou `à-fusionner`. Sur la PR d'une fille, le conducteur ne pose ni ne retire jamais `à-fusionner`, `à-relire` ou `à-reprendre`, hors le cas sans étiquette ci-dessous ; ses propres PR (cadrage, documentation, nettoyage) demandent leur relecture comme celle d'une fille, avec `Conducteur: —`. Une PR de documentation déclare d'abord son périmètre (`docs/agents/chaine-de-production.md` § 5). Ses gestes :
   - **Arbitrer** une contestation de sa fille (`Contesté — <critère, fichier et ligne> — <raison>` sur la PR, et une ligne de la fille) : il lit le constat dans le code, puis écrit sur la PR `Arbitrage — <critère, fichier et ligne> — maintenu`, ou `— écarté — <raison>` ; il le lui écrit en une ligne (`send_message`), et la fille redemande la relecture (maintenu : le bloquant corrigé d'abord) : sans demande, la PR reste `à-reprendre`, hors de la file du Relecteur. Une contestation de ses propres PR va à l'architecte (sans programme, au produit).
   - **Recevoir un plafond** (trois tours refusés : `Plafond — décision attendue` sur la PR, une ligne du Relecteur) : dans un programme, l'architecte décide, il lui donne ce qu'il sait du ticket ; sans programme, il décide lui-même si la cause est technique (ticket récrit ou découpé, désaccord tranché), le produit sinon, et l'écrit sur la PR, `Décision de plafond — …`, avec ses lignes `Arbitrage — … — écarté` quand elle écarte un bloquant, puis informe le produit en une ligne ; la décision écrite, par lui ou par l'architecte, il l'écrit en une ligne à la fille, qui la suit et redemande la relecture.
   - **Une règle haute** (deux verdicts validés exigés) : le message d'information au produit part de lui, par l'architecte dans un programme : la règle, ce qui change, les deux verdicts.
   - **À chaque réveil**, les PR ouvertes de son sujet qui ne portent aucune des quatre étiquettes (`à-relire`, `à-reprendre`, `à-fusionner`, `fusion-bloquée`), hors brouillon (une fille qui code, ou arrêtée avant sa demande) et en régime 8 (ouvertes après `relecture.depuis` de leur base ; une PR en régime 7 sans étiquette attend sa contre-revue, `references/regime-7.md`) : l'écrire à leur fille ; fille finie ou muette, il pose lui-même `à-relire` avec le commentaire `À relire — sommet <sha> — Session: — — Conducteur: <la sienne>` au sommet de la PR. Une ligne `Relecture en panne` ou `PR <n> : …` du Relecteur se lit, et va à l'architecte quand elle le nomme. Une ligne « session de relecture <id> remplacée au plafond de contexte, PR <n> » se note dans `## Dépassements` comme un plafond (point 1 bis ; décision : « remplacée par le Relecteur »), puis une ligne d'information au produit (dans un programme, à l'architecte) : rien n'est à décider.

   **Une sous-PR à la fois par sujet : le capitaine tient cet ordre, pas le conducteur.** Le capitaine met à jour et reteste toute sous-PR en retard sur son sujet, même pour de la documentation (skill `fusionner`, « La règle d'ascendance ») : deux sous-PR prises ensemble se remettraient l'une l'autre en retard. À chaque tour, il ne prend donc qu'une sous-PR étiquetée par sujet : celle qui tient déjà le sujet (sa mise à jour attend sa CI, ou un capitaine est dessus), sinon la plus ancienne (le plus petit numéro, pas la première étiquetée) ; les autres attendent leur tour avec leur étiquette, et `file.sh` les montre « prête » sans qu'elles bougent : ce n'est pas une file arrêtée. Le Relecteur étiquette chaque sous-PR validée sans attendre que la précédente soit entrée, et personne ne retire ni ne repose jamais `à-fusionner` pour régler l'ordre de passage.
6. Vague entièrement fusionnée dans le sujet → `git show --stat` du squash de chaque sous-PR : une PR étiquetée avant que son push aboutisse entre avec son seul commit de réservation. Puis le sujet reçoit develop, **et ce n'est jamais le conducteur qui le fait** : le capitaine reporte develop dans chaque sujet de lui-même, au début de chaque lancement de sa boucle, et à la fin quand la file est vide, dès qu'aucune sous-PR du sujet n'est ouverte ; le conducteur ne lance jamais `sujet.sh rafraichir` (deux sessions ont fait ce geste l'une après l'autre sur un même sujet). Il constate seulement : `git fetch -q origin '+refs/heads/develop:refs/remotes/origin/develop' '+refs/heads/sujet/<nom>:refs/remotes/origin/sujet/<nom>'` (refspecs explicites : le clone `--single-branch` d'une session cloud ne met pas `origin/sujet/<nom>` à jour sur un fetch nu), puis `git merge-base --is-ancestor origin/develop origin/sujet/<nom>`. Sortie 0, sujet à jour : il continue. Sortie 1, sujet en retard : aucune vague ne part (une sous-PR ouverte empêcherait le capitaine de recevoir develop), `send_later` à 45 min ; encore en retard au réveil suivant, il demande à un capitaine actif (tag `role:capitaine`) pourquoi (`send_message`), sans rien lancer. Toute autre sortie que 0 ou 1 (128 compris), ou un fetch en échec, n'est ni « à jour » ni « en retard » (une référence périmée donnerait un faux « à jour ») : aucune vague ne part, il recommence au réveil suivant, et le dit au capitaine s'il échoue deux fois. Le capitaine répond `SUJET EN CONFLIT` (conflit de code avec develop) ou `SUJET NON MIS À JOUR (sortie 3, aucun conflit)` (fusion refusée sans conflit par un hook, par exemple `pnpm check` rouge après la montée d'un formateur dans develop) : le conducteur lance alors une session fille pour ce geste, qui ouvre la PR de mise à jour du sujet, avec ses retouches (en-tête de `sujet.sh`) ; il ne résout jamais lui-même. Toute autre réponse (`PAS PROPRE`, `SUJET NON MIS À JOUR` d'une autre sortie, sujet bougé pendant la mise à jour) : rien à lancer, le capitaine corrige chez lui ou reprend au tour suivant. Trois cas où la boucle ne le reporte pas d'elle-même : la livraison du sujet est ouverte (`livré #<n>` dans `sujet.sh etat`), une livraison intermédiaire vient d'entrer dans develop (`etat` ne liste plus un sujet sans commit propre ni PR ouverte), ou une sous-PR hors vague reste ouverte sur le sujet. Le conducteur demande alors au capitaine de reporter develop à la main, sinon le dit au produit (dans un programme, à l'architecte) ; il ne le fait toujours pas lui-même. Le capitaine fait entrer cette PR de mise à jour avant la vague suivante. Puis, pour chaque fille de la vague dont la PR est fusionnée : `get_session`, sa ligne dans la section `## Coût` de la carte (§ 7), et de même pour chaque session de relecture de sa PR (rôle `relecture`), lues sur les distributions du Relecteur (`Relecture — tour <k> — sommet <sha> — sessions <…>`, remplacées comprises) ; **puis une ligne à l'architecte par session, `à archiver : <session>, <ticket>, <coût>`** (sans programme, au produit). Le conducteur n'archive rien lui-même : la garde du mode « Auto » lui refuse `archive_session`, que l'outil réserve à une session dont un humain a pris acte ; l'architecte archive, sur ces lignes (`P-62`). C'est le conducteur qui relève et nomme ses filles, pas le capitaine : le capitaine ne veille que sur sa file, et quatre filles finies sont restées ouvertes. Une fille qui attend une réponse ou dont la PR est renvoyée ne se nomme pas. Le registre transverse `docs/agents/couts.md` en est régénéré à la fusion suivante (index généré) : il donne à tout moment le coût de production de tous les chantiers. Puis vague suivante (§ 5), `Phase: 4-vague-<k+1>`. Sinon `send_later` à 45 min.
7. Le produit (ou l'architecte) demande l'avancement : la sortie de `node scripts/docs/avancement.mjs sujet/<nom>` (pourcentage de tickets faits, PR, CI, bloqués). Pas de réexamen.

## Arrêter un chantier

Un chantier se gèle d'une ligne : `Gel:` de la fiche de la carte (non vide, gelé). Un plafond ne fait que se signaler (§ 6) et un renvoi n'arrête qu'une PR ; le gel, lui, arrête le chantier. Le gel est demandé par le produit, ou écrit par lui sur GitHub sans ouvrir de session.

1. **Geler** : `bash scripts/chaine/sujet.sh geler <nom> "<raison>"`. Dès lors, plus aucune session ne part du sujet (`demarrer` refuse) et plus aucune de ses PR n'entre (`file.sh` les montre « gelée », `fusionner` et `livrer` refusent). Déjà gelé à la main : passer à l'étape 2.
2. **Interrompre les filles** : `list_sessions` sans `tags`, puis les lignes dont `tags` contient `chantier:<nom>`, puis `interrupt_session` sur chacune qui travaille encore (`status_bucket` working ou blocked). Ne rien archiver : leur travail est intact, la reprise les relancera sur leurs branches.
3. **Supprimer les réveils** : `list_triggers`, puis `delete_trigger` sur chaque `send_later` du chantier, celui du conducteur compris.
4. **Journal** : une ligne `- AAAA-MM-JJ — gel : <raison> ; <n> filles interrompues` dans `## Journal` de la carte, poussée par `sujet.sh carte <nom>` (§ 0), puis s'arrêter.

**Dégeler** : `bash scripts/chaine/sujet.sh degeler <nom>` vide la ligne ; ni le conducteur ni les filles ne se réveillent tout seuls. Celui qui dégèle prévient le conducteur par `send_message` s'il vit encore ; sinon le chantier se relance par ce skill avec le nom du sujet, qui reprend à la phase de la carte (§ 0), relance les filles interrompues sur leurs branches, et écrit une ligne `dégel` au `## Journal`.

## 7. Phase 5 — livraison (`Phase: 5-livraison`), phase 6 — nettoyage (`Phase: 6-nettoyage`, puis `Phase: fini`)

1. Tous les tickets `Fait` : le capitaine livre le sujet (`sujet.sh livrer-prets`), commit de merge vers develop. Échéance proche ou sujet « VIEUX » : proposer au produit `sujet.sh livrer <nom> "<titre>"` ; la PR s'ouvre sans `à-fusionner`, que le conducteur pose aussitôt en régime 8 (en régime 7 : `references/regime-7.md`) : une livraison de sujet n'a pas de relecture propre, ce qui y entre a été relu sous-PR par sous-PR (`P-60`). Une livraison intermédiaire qui échoue à sa preuve redevient une PR ordinaire : en régime 8, il pose alors `à-relire`, et elle est relue en entier.
2. **Coût** : section `## Coût` de la carte (source du registre `docs/agents/couts.md`, index généré, qui donne le total et le coût par ticket), une ligne par session (`get_session` : `external_metadata.usage.cost_usd`, `context_usage.used_tokens`, `last_served_model`) — filles du tag `chantier:<nom>` relevées à chaque fin de vague, puis capitaine, cette session-ci (rôle `conducteur`), les sessions de relecture de ses propres PR (rôle `relecture`, lues sur leurs distributions) et, sans programme, le Relecteur qu'il a lancé (rôle `relecteur`), en fin de chantier. **Aucun bilan de fin de chantier** : un incident (un renvoi, une vague ratée) donne un ticket au moment où il arrive — un gate, un critère de `revue-adversariale` — ou, faute de gate, une ligne de `docs/agents/pieges.md` ; vécu deux fois sans gate, il est signalé au produit.
3. Sessions filles finies : déjà nommées à l'architecte à chaque fin de vague (§ 6.6) ; nommer ici les dernières, et leurs sessions de relecture, avec celles de ses propres PR fusionnées, après relevé de leur coût.
4. **Nettoyage**, une fois le sujet dans develop (`git merge-base --is-ancestor origin/sujet/<nom> origin/develop`) : `Phase: 6-nettoyage` dans la carte de develop (par une PR docs : `clore` lit cette carte), puis `bash scripts/chaine/sujet.sh clore <nom>` supprime `origin/sujet/<nom>` si GitHub ne l'a pas fait (livraison intermédiaire, ou avant le réglage « Automatically delete head branches ») : la commande refuse un sujet pas livré ou qui a une PR ouverte, et le proxy d'une session cloud peut refuser la suppression (sortie 3, branche intacte) : la jouer alors d'un poste local, jamais en poussant à la main ; puis les autres branches du chantier encore sur `origin` (le même réglage les supprime seul à la fusion ; le reste se supprime d'un poste local, **jamais d'une session cloud**, le proxy refuse la suppression) ; les sessions filles du tag encore actives : la ligne « à archiver » après relevé du coût ; les `send_later` restants : `list_triggers`, `delete_trigger` ; `Phase: fini` dans la carte, par une PR docs vers develop.

## Ne jamais

- Coder un ticket, fusionner une PR, remettre à jour la branche d'une fille.
- Contre-relire une PR, relayer ou résumer un constat, poser `à-fusionner` sur une PR en régime 8 (le Relecteur seul la pose ; une livraison de sujet exceptée), ou appeler `archive_session` (`P-62`).
- Lancer une fille avant que les specs et ses `Blocked by:` soient fusionnés dans le sujet, ou lui faire « fusionner localement » une dépendance.
- Recopier les règles dans un prompt de fille : elles vivent dans `chaine-de-production.md` § 5.
- Produire dans cette session un livrable d'un autre rôle.
- Élargir les permissions d'une session : remonter le besoin au produit.
- Interrompre une session pour un plafond, une fille comme soi-même : il se signale, le produit décide.
- Mener un grilling complet : il appartient à l'architecte.
- Dans un programme, s'adresser au produit : tout passe par l'architecte.
