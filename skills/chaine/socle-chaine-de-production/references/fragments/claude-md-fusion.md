## Fusion vers `develop` : une file, un capitaine

`develop` intègre, `main` livre. `develop` exige une PR à jour : chaque fusion remet les autres PR en retard. **Seuls les capitaines fusionnent** (skill `fusionner`) ; plusieurs peuvent tenir la même file, un commentaire marqué réserve à l'un la PR qu'il fait passer. Décision : `{{ADR_CHAINE}}`, `{{ADR_SUJET}}`, `{{ADR_RELECTURE}}`.

- **Réserver le ticket avant de coder** (sessions en parallèle) : `node scripts/docs/ticket-libre.mjs <identifiant>` « LIBRE », puis branche, commit `Status: en cours` et PR brouillon — `docs/agents/issue-tracker.md` § « Réserver un ticket ».
- **Relecture indépendante.** Toute PR, documentation comprise, est relue par une session de relecture que lance le **Relecteur** du dépôt (skill `relecteur`) ; **la session qui code ne se relit pas** et ne pose jamais `à-fusionner`, que le Relecteur pose sur un verdict validé. Une PR ouverte avant la clé `relecture` de `.claude/chaine.json` (son `depuis`) finit sous les règles de sa branche.
- **Session de travail.** Dès la PR poussée et rien d'autre à faire : PR hors brouillon, le commentaire `À relire — sommet <sha> — Session: <id> — Conducteur: <id>`, puis l'étiquette `à-relire` (en session cloud, par l'outil GitHub MCP `issue_write`) ; sur `à-reprendre`, lire le verdict sur la PR, corriger chaque bloquant ou le contester, redemander la relecture. **Ne pas attendre la CI.** Un chemin sensible ne se modifie que sur la branche d'un ticket dont la ligne `Sensibles:` le couvre. `prio:haute` pour une démo, une recette ou un blocage. **Ne jamais fusionner soi-même, ni remettre la branche à jour avec `develop`.**
- **Capitaine.** File dans l'ordre (sous-PR de sujet, livraisons de sujet, `prio:haute`, puis numéro) ; met à jour avec `develop`, régénère les index générés (`scripts/docs/index-generes.json`), attend les checks exigés, squashe, vérifie l'arbre. CI rouge relancée une fois, puis PR renvoyée.
- **`fusion-bloquée`** : PR renvoyée (conflit, CI rouge, refus, verdict absent) avec commentaire → corriger, puis redemander la relecture (`à-relire`, sans retirer `fusion-bloquée`).
- **Capitaine et verdict.** Le capitaine ne relit rien : il fusionne une PR dont un tour de relecture est validé pour le sommet qu'il fusionne, contrôlé à l'éligibilité puis juste avant la fusion.
- **Branches de sujet dès le départ** (skill `sujet`) : un lot qui donnera plusieurs PR liées vit sur `sujet/<nom>` dès sa première PR ; le découpage le déclare (`Sujet: sujet/<nom>` en tête de la spec ou du ticket) et, avant le premier commit, `bash scripts/chaine/sujet.sh demarrer <ticket>` fait partir la branche du sujet. **Jamais de PR empilée sur une autre.** Un correctif isolé qui doit arriver seul en recette reste une PR directe vers `develop`, `hors-sujet` si son ticket déclare un sujet.
- **Hooks d'agent** (`scripts/agent/`) : refusent tout push forcé, `--no-verify` et toute autre façon de sauter les hooks git (`HUSKY=0`, `core.hooksPath`, `git commit -n`), `git commit --amend`, le push direct sur `develop`, `main` ou la branche par défaut, l'écriture d'un sujet, de `develop` ou de `main` par un outil GitHub ou par `gh`, l'édition d'une migration livrée ou d'un index généré, et refusent toute dépendance nouvelle que la ligne `Dépendances:` du ticket, lue sur le sujet, ne prévoit pas (le conducteur l'accorde en complétant cette ligne).
