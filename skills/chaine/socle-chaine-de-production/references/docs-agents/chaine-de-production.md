# Chaîne de production : qui fait quoi, du cadrage à develop

Mode d'emploi des sessions de l'assistant de développement quand plusieurs travaillent en parallèle. Décision et raisons : `{{ADR_CHAINE}}`. Branches de sujet : `{{ADR_SUJET}}`. Contrat du projet : `.claude/chaine.json`.

**Relecture indépendante** (`{{ADR_RELECTURE}}`). Ce document décrit le régime 8 de la chaîne, que la clé `relecture` de `.claude/chaine.json` allume : toute PR est relue par une session que son auteur ne contrôle pas, et la session qui code ne se relit plus. Une PR est en régime 8 quand sa base (`develop` ou `sujet/<nom>`) porte la clé et qu'elle a été ouverte après `relecture.depuis` ; une PR ouverte avant finit sous les règles du document de sa branche (`maj-skills`, `chantier/references/regime-7.md`).

**Pour lancer un chantier : `/maj-skills:chantier <objectif>`** dans une session neuve, celle du conducteur de chantier (un programme de plusieurs chantiers se lance par `/maj-skills:architecte`). Elle pose les questions de setup, écrit la fiche dans la carte et déroule ce fichier phase par phase ; relancée avec le nom du sujet, elle reprend à la phase en cours.

Le principe : **les tokens se dépensent une fois, au cadrage**. Une session fille qui doit chercher où coder, relire les règles en entier, deviner une décision ou réparer son environnement paie ce que le cadrage aurait payé une seule fois pour toutes.

## 1. Les rôles

Une session tient **un seul rôle**. Un travail d'un autre rôle (un deck, une étude, une contre-revue longue) part dans une autre session ou un sous-agent.

| Rôle                 | Combien                      | Fait                                                                                                                                                    | Ne fait jamais                                                      | Modèle conseillé                  |
| -------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------- |
| Produit (personne)   | —                            | tranche les questions du grilling, valide le découpage, décide la livraison en recette                                                                  | —                                                                   | —                                 |
| Architecte           | un par programme             | mène l'amont : questions au produit, décisions, specs validées ; seul à parler au produit ; lance sans demander le conducteur de chaque chantier, le capitaine et le Relecteur de chaque dépôt et la session d'un ticket hors chantier, et répond au conducteur (`send_message`) ; arbitre les contestations des PR du conducteur, décide au plafond d'une PR d'une fille, du conducteur ou de la sienne (le contenu de sa décision : skill `architecte`, § 5), archive les sessions finies | découper un chantier en tickets, lancer la fille d'un chantier qui a son conducteur, coder, fusionner | Opus                              |
| Conducteur de chantier | un par chantier            | à partir d'une spec validée : carte, tickets **prêts pour agent** (§ 3), ouverture du sujet, lancement des filles par vagues, suivi par le tableau d'avancement, arbitrage des contestations de ses filles, plafonds reçus, relevé des coûts et « à archiver » à l'architecte ; sans programme, grilling court avec le produit | contre-relire une PR, relayer un constat, poser `à-fusionner` (une livraison de sujet exceptée) ; grilling complet ; dans un programme, parler au produit (tout passe par l'architecte) ; coder un ticket, produire un livrable hors chantier, fusionner | Opus                              |
| Session fille        | une par ticket               | réserve, code, vérifie, demande la relecture, corrige ou conteste chaque bloquant, s'arrête                                                             | se relire, poser `à-fusionner`, prendre un 2ᵉ ticket, fusionner, partir d'une branche non fusionnée | Sonnet ; Opus si le ticket le dit |
| Capitaine de fusion  | un ou plusieurs par dépôt (un verrou par PR) | file `à-fusionner`, jugée par les verdicts, sous-PR dans les sujets, livraison des sujets, renvois (skill `fusionner`) ; veille la file par `scripts/chaine/veille.sh`, qui relance la boucle dès qu'une PR est prête | résoudre un conflit de code d'une autre session                     | Sonnet                            |
| Relecteur            | un par dépôt                 | aiguille : une session de relecture par PR (deux pour une règle haute), `à-fusionner` sur un tour validé, `à-reprendre` sur un refus, le plafond au troisième tour refusé (skill `relecteur`) | relire, arbitrer, transporter ou résumer un constat                 | effort moyen                      |
| Session de relecture | une par PR et par tour       | relit la PR depuis sa base, un axe par sous-agent en contexte vierge, liste fermée de critères, écrit le verdict sur la PR (skill `relecture`)          | modifier un fichier, pousser, lire le verdict d'une autre session    | `relecture` de `.claude/chaine.json` : Opus, effort moyen ; effort extra pour une PR sensible |

Chaque carte nomme son **responsable** (`Responsable:`), une personne, celle qui répond du chantier ; `Architecte:` nomme la session du programme (ligne absente quand le chantier n'en a pas) et `Conducteur:` la session qui mène le chantier. Une carte d'avant ces rôles, où `Architecte:` nommait la session du chantier, n'est pas réécrite : elle est gelée dans la dette du gate (clé `fiches`).

Le **modèle se choisit par ticket**, pas par chantier : la ligne `Modèle:` du ticket (§ 3) le dit. Sonnet pour un ticket dont le brief nomme les fichiers, les décisions et les surfaces ; Opus pour ce qui reste à concevoir ou à arbitrer (migration délicate, conception d'écran neuve, règle absente ou ambiguë), raison écrite sur la ligne `Modèle:`. Mesuré sur un premier projet : 4 $ par ticket en Sonnet, 7 $ par ticket comparable en Opus, sans écart de qualité visible au passage du capitaine.

## 2. Le cycle d'un chantier

```
cadrage ──► carte + specs ──► tickets prêts ──► PR de specs fusionnée dans le sujet ──► vagues de filles ──► sujet livré
(produit,     (architecte,      (conducteur)          (capitaine)                         (filles)            (capitaine)
architecte)   conducteur)
```

1. **Cadrage.** Grilling avec le produit, mené par l'architecte du programme (`docs/methode/grilling.md`, par les skills de Matt Pocock ; sans programme, le conducteur ne mène qu'un grilling court) : une question à la fois, recherche faite **avant** de poser la question, recommandation à chaque fois. Rien n'est écrit dans le dépôt pendant le grilling.
2. **Carte et specs.** Carte `*.map.md` (décisions, brouillard), specs, tickets. La spec porte `Sujet: sujet/<nom>`. **Après la PR de cadrage, le conducteur met la carte à jour (phase, sessions, coûts, incidents) directement sur le sujet, par `bash scripts/chaine/sujet.sh carte <nom>`** : commit local qui modifie en place **ce seul fichier** `*.map.md` (celui dont la ligne `Sujet:` nomme le sujet, seul ou parmi plusieurs valeurs séparées par des virgules, avant comme après le commit, formaté par Prettier), puis la commande, qui rattrape le sujet par `git merge --ff-only` et pousse sans force le sommet qu'elle a vérifié ; elle refuse (sortie 9) un autre fichier, une carte créée, supprimée, renommée ou changée de mode, la carte d'un autre sujet, un commit de fusion, un historique divergent et toute option de force. Jamais `git push origin HEAD:sujet/<nom>` : le hook le refuse.
3. **Sujet ouvert, specs d'abord.** `sujet.sh ouvrir <nom>`, puis la PR de specs **vise le sujet** et y est fusionnée **avant** le lancement de la première fille. Jamais de fille partie d'une branche de specs : douze PR parties d'une branche de specs sont toutes tombées en conflit au squash des specs.
4. **Vagues.** Une vague = les tickets dont tous les `Blocked by:` sont fusionnés dans le sujet **et** qui ne partagent pas de fichier chaud (§ 4). Un ticket bloqué attend la vague suivante : on ne « fusionne pas localement » la dépendance.
4 bis. **Relecture.** Toute PR, documentation comprise, est relue par une session de relecture que lance le Relecteur du dépôt ; la session qui l'a écrite ne se relit pas. Le verdict s'écrit sur la PR, `validé`, `refusé` ou `incomplet`, avec ses constats, **bloquants** (un écart à un critère écrit : il se corrige, avec son test, ou se conteste) ou **doutes** (une question, sans obligation). Trois tours refusés au plus : au-delà, la décision de plafond (l'architecte ; sans programme, le conducteur pour une cause technique, le produit sinon). Une règle de criticité haute veut deux verdicts validés de deux sessions, et le produit en est informé.
5. **Suivi.** Le conducteur suit le tableau d'avancement (`node scripts/docs/avancement.mjs sujet/<nom>`, ou `<SPEC>` ; `--json` pour une page partagée), pas les messages de chaque fille. Il ne se réveille que sur un renvoi, une question ou une fin de vague.
6. **Livraison.** Le capitaine livre le sujet quand ses tickets sont faits (`sujet.sh livrer-prets`). `boucle.sh` se lance depuis le worktree, sans copie manuelle : à chaque tour elle fait `git fetch origin develop`, recopie `scripts/chaine` d'`origin/develop` dans `<git-common-dir>/boucle-outils` et n'appelle que cette copie ; si `boucle.sh` a changé sur develop, elle se relance dessus (`exec`) ; `origin/develop` introuvable ou fetch en échec trois fois : arrêt (sortie 6), jamais de scripts périmés. **Une seule boucle à la fois, arrêt d'un geste** : un verrou `flock` sous `<git-common-dir>` refuse une seconde boucle (sortie 9, même si c'est un processus d'attente oublié qui la relance, et même après l'`exec`) ; `bash scripts/chaine/boucle.sh --arreter` pose `<git-common-dir>/boucle-arret` puis interrompt la boucle et le passage en cours (détenteurs réels du verrou, descendants, groupe noté ; la veille n'est tuée que si elle partage le groupe) et la trappe remet le worktree propre (sortie 143) ; la boucle relit ce fichier au démarrage, à chaque tour, avant `livrer-prets` et avant chaque passage (sortie 10) et une relance le refuse tant qu'il existe ; **reprendre** : `bash scripts/chaine/boucle.sh --reprendre` (retire le fichier, puis lance la boucle). **Livraison intermédiaire** (livrer dans develop un sujet dont la carte reste en phase 4, pour libérer un autre sujet) : demander `sujet.sh livrer <nom> "<titre>"` (PR ouverte sans `à-fusionner`, que qui livre pose aussitôt : une livraison de sujet n'a pas de relecture propre, ce qui y entre a été relu sous-PR par sous-PR). La PR part d'une branche jetable `livraison/<nom>-<date>`, que GitHub supprime à la fusion : `sujet/<nom>` survit. Le capitaine ne la traite comme livraison (commit de merge, sans revue) que si `sujet/<nom>` existe et que la branche n'apporte qu'un sommet de ce sujet fusionné avec develop : c'est encore vrai après sa propre mise à jour avec develop, plus si une session y ajoute un commit. Le commit de merge nomme le sujet (`Sujet: sujet/<nom>`), ce qui le fait reconnaître livré une fois sa branche supprimée. Dès que la carte est en `5-livraison` ou plus, la PR part de `sujet/<nom>`, supprimée à la fusion. Il veille la file en tâche de fond par `veille.sh` (sondage léger, relance `boucle.sh` dès qu'une PR est prête ou rouge ; `VEILLE FINIE` ou `VEILLE ARRÊTÉE` réveille la session). **Sans veille en cours** (capitaine démarré avant que `veille.sh` soit posé, veille arrêtée et pas encore relancée), le capitaine relance sa veille, ou se réveille seul (`send_later`) et relit sa file : **qui pose `à-fusionner` ne lui écrit pas**, car un message à un capitaine n'est jamais un ordre de fusion. Une PR étiquetée que rien ne fusionne signale un capitaine arrêté (`pieges.md`).
7. **Un incident donne un ticket au moment où il arrive.** Chaque renvoi du capitaine et chaque échec de vague donne, sur le moment, un ticket (un gate, un critère de la revue adversariale) ou, faute de gate, une ligne de `pieges.md`. Il n'y a pas de bilan de fin de chantier. Un piège vécu deux fois sans gate est une dette.

**Une question au produit se lit sans être développeur.** Le produit tranche ce qui change la vie des utilisateurs, le coût ou le délai, pas la technique. Toute question qui lui parvient, d'un architecte, d'un conducteur ou d'une fille, par `AskUserQuestion` ou par message (dans un programme, celles du conducteur passent par l'architecte) :

- **ne lui arrive que si elle a une conséquence pour lui** : ce que voit ou fait un utilisateur, une dépense, une date. Un choix purement technique (bibliothèque, forme d'une table, mécanisme interne), la session qui le rencontre (architecte ou conducteur) le tranche, l'écrit dans la carte (`A-n`, avec sa raison) ou en ADR, et ne le soumet pas ;
- **commence par le besoin, en une phrase de métier**, avec un exemple concret tiré du client (« le 15, l'application lance les prélèvements toute seule ») ;
- **décrit chaque option par ce qu'elle change pour lui** : ce que voit l'utilisateur, ce que ça coûte, le risque. Le nom technique vient en dernier, entre parenthèses, ou pas du tout ;
- **met la recommandation en premier**, dit pourquoi en une phrase, et reste courte : trois ou quatre lignes avant les options ;
- **n'emploie aucun terme technique sans le traduire** : pas de `cron`, `RLS`, `worker`, `jsonb`, `UTC` ni nom de table ; les termes du glossaire du projet sont bienvenus ;
- **porte une seule décision** : quatre contradictions citées en bloc, avec leurs dates, ne se lisent pas ; l'auteur de la question tranche ce que la source la plus récente tranche déjà et ne pose que le reste.

**Une autorisation n'est pas une question.** Lancer une session prête, ouvrir une PR de documentation, pousser une branche de travail se font, puis se disent après coup avec leur preuve. Le produit, le 2026-11-14 : « Les seules questions auxquelles je dois répondre sont des décisions techniques ou métier pas des autorisations que je ne fais qu'accepter de toute façon. » Une décision technique au sens de cette phrase est celle qui passe le filtre ci-dessus ; le sens d'une règle métier en est une aussi. La question qui passe se pose **une à la fois**, formulée pour qu'un oui ou un non suffise (« Je recommande X, parce que Y. On y va ? ») ; les options, s'il y en a, viennent après. La validation d'un découpage suit la même forme : le tableau, la recommandation, et la réponse attendue « Lancer » ; sinon le produit dit quoi changer. On vouvoie le produit, même quand il tutoie.

Une question qui ne passe pas ce filtre revient à son auteur. Cas vécu : « tick du planificateur, registre, table `scheduled_job_run` sous clé unique et verrou PostgreSQL » ; le produit a répondu « j'ai rien compris ». La vraie question était : « une alerte d'intervenant non pointé peut-elle arriver avec 10 à 20 minutes de retard, pour ne pas payer un serveur de plus ? ».

## 3. Un ticket prêt pour agent

`Status: ready-for-agent` veut dire qu'une session neuve peut le coder **sans exploration large ni question**. En tête du ticket :

```markdown
Status: ready-for-agent
Sujet: sujet/<nom> # si différent de la spec
Blocked by: 01, 03 # tickets du même chantier, fusionnés dans le sujet avant de commencer
Modèle: sonnet # ou opus, avec la raison
Fichiers chauds: src/db/migrations/* # fichiers que d'autres tickets touchent aussi (§ 4)
Sensibles: scripts/chaine/passer.sh, apps/api/src/auth/** — accord de <nom>, <AAAA-MM-JJ> # chemins sensibles que le ticket modifie, puis l'accord du produit ; ou — ; sans elle, le hook d'édition refuse
Relecture: double # exigée par le gate tickets d'un ticket ouvert qui cite une règle de criticité haute : deux sessions de relecture
Dépendances: `leaflet`, `@types/leaflet` # paquets que le ticket ajoute, nom sans version, validés au découpage, ou — ; une dépendance hors de cette ligne est un blocage (§ 5)
Maquette: <fichier du dépôt : maquette HTML et section, ou planche recopiée sous docs/design/planches/> # dès que le ticket touche un écran ; sans planche validée, le ticket reste needs-info ; jamais un artefact seul : une fille ne peut pas l'ouvrir
```

La ligne `Dépendances:` fait foi telle qu'elle est sur la branche du sujet (`origin/sujet/<nom>`), jamais dans l'arbre de travail ni sur la branche de la fille : le hook d'agent laisse passer `pnpm add` (ou `pnpm install <paquet>`) quand chacun des paquets ajoutés y figure. Seule compte une copie du sujet dont le sommet est celui d'`origin` (`git ls-remote`) ; un ticket présent sur plusieurs sujets ne laisse passer que les paquets que toutes ses copies prévoient. Un paquet absent de la ligne, une option ou un préfixe qui change la source (`--registry`, `--config.*`, `--global`, `-C`, `npm_config_*=…`), un ticket hors sujet ou un `origin` injoignable est refusé par le hook, qui ne demande jamais rien à un humain. Une dépendance hors de la ligne est un blocage de la fille (`send_message` au conducteur), jamais un contournement. Un sujet ne se pousse jamais à la main : le hook refuse tout `git push` vers `sujet/*`, quelle que soit la branche courante et la forme de la commande (guillemets, `git -C`, chemin de git, préfixe comme `timeout`, sous-shell, `--repo`, `HEAD` ou push nu depuis une branche `sujet/…`), et seul `sujet.sh` y écrit, la carte comprise (`sujet.sh carte <nom>`) ; sans ce refus, une session écrirait elle-même la ligne qui l'autorise. Une destination illisible (variable, substitution, motif, `--all`, `--mirror`) est refusée. Le même hook refuse le push vers `develop`, `main` ou la branche par défaut sous toutes leurs graphies (`HEAD:refs/heads/develop`, majuscules, push nu depuis l'une d'elles) et `gh` en écriture vers une branche, un fichier ou une règle de branche (`gh pr merge`, `gh api` vers `git/refs`, `contents`, `pulls/<n>/merge`…) ; le hook `garde-github` refuse l'écriture d'un sujet, de `develop`, de `main` ou de la branche par défaut par un outil GitHub (`push_files`, `create_or_update_file`, `delete_file`, `create_branch` d'un sujet), la fusion par outil d'une PR dont la base est gardée et la mise à jour par outil d'une PR dont la tête est gardée. Un `.npmrc` ou un `pnpm-workspace.yaml` modifié par rapport à `develop` (ou créé hors de l'index) suspend le laissez-passer : le hook refuse. Ce hook est une garde, pas une frontière : un script lancé par la session n'est pas lu, et seule une protection de `sujet/*` côté GitHub en ferait une.

**Fichiers sensibles : l'accord avant le code.** Un chemin sensible (`cheminsSensibles` de `.claude/chaine.json`) ne se modifie que sur la branche d'un ticket dont la ligne `Sensibles:` le couvre ; la ligne se lit sur `origin/sujet/<nom>` (sur `origin/develop` pour un ticket sans sujet), jamais dans l'arbre de travail. Le hook d'édition refuse l'écriture d'un chemin sensible que la ligne ne couvre pas, et le capitaine renvoie une PR dont le diff en touche un, comme une PR sans ticket qui en touche un. La demande d'accord est un tableau de la carte, section `## Fichiers sensibles`, une ligne par fichier (ticket, chemin, pourquoi, ce qui y change) : le conducteur l'écrit au découpage, le produit l'accorde une fois, avec le découpage (dans un programme, l'architecte la lui soumet), et les lignes `Sensibles:` ne se remplissent qu'après, dans la PR de cadrage. Un fichier découvert en route : la fille s'arrête et l'écrit au conducteur, qui obtient l'accord par la même voie, puis ajoute le chemin au ticket par une PR de documentation vers le sujet. Un ticket qui crée un module d'authentification, de droits, de chiffrement, de paiement ou d'export fait ajouter son dossier à `cheminsSensibles` par un ticket du chantier, le premier quand d'autres en dépendent, et jamais par la PR de cadrage ; la relecture (critère S14) relève un tel code hors de la liste.

Puis, dans le corps, quatre sections que la fille lit au lieu de chercher :

| Section           | Contenu                                                                                                                                                                      | Ce que ça évite                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `## Où`           | fichiers à créer ou modifier, `fichier:ligne` du modèle à imiter, l'appelant réel de toute fonction citée (route, listener, cron), règles à lire (deux au plus)              | l'exploration du dépôt, la lecture de toutes les règles |
| `## Décisions`    | ce qui est tranché (renvoi à la carte ou à l'ADR), et ce que la fille tranche seule par défaut prudent                                                                       | les questions à l'humain, les allers-retours            |
| `## Surfaces`     | table surface → test qui la prouve                                                                                                                                           | la couverture rouge découverte au push                  |
| `## Vérification` | commandes ciblées avant `pnpm check` (typecheck du paquet, specs nommées), index à régénérer, specs de garde à compléter                                                     | trois `pnpm check` complets pour un typecheck rouge     |

Le gate `tickets` (`pnpm check:tickets`, `scripts/verify/tickets.mjs`) refuse un ticket `ready-for-agent` sans `Modèle:`, sans l'une de ces quatre sections, ou qui cite sur sa ligne `Règles:` une règle de criticité haute sans `Relecture: double` (un ticket ouvert, gelé dans la dette ou non) ; il juge la forme des lignes `Sensibles:` et `Relecture:`, sans exiger la première, et n'exige plus `Label: contre-revue`, qui reste lisible sur les tickets d'avant ; les tickets prêts d'avant l'installation du gate sont gelés dans `scripts/verify/tickets-dette.json`, qui ne reçoit jamais d'entrée nouvelle. Gabarit : `docs/agents/gabarits/ticket.issue.md`.

Taille : un jour au plus, une quinzaine de fichiers. Une fille qui atteint 400 k tokens de contexte est signalée (contrôlé par le conducteur à chaque réveil), jamais interrompue : c'est le signe d'un ticket mal découpé, le signalement remonte au produit (par l'architecte dans un programme), qui décide ce qu'il veut faire, et la ligne va dans `## Dépassements` de la carte.

## 4. Branches et fichiers chauds

Les règles de branche (sujet dès la première PR, jamais de PR empilée, seuls les capitaines fusionnent) sont celles de `CLAUDE.md` § « Fusion vers `develop` : une file, un capitaine ». S'y ajoute **l'ordonnancement des fichiers chauds** : deux tickets d'une même vague ne touchent pas le même fichier parmi ceux que les tickets déclarent. Candidats habituels : le dossier des migrations (une migration à la fois par sujet, horodatages réservés par le conducteur dans le brief), les seeds, les contrats partagés de `packages/contracts`, les fichiers de registre.

`node scripts/docs/vagues.mjs <spec>` applique ces règles aux tickets (`Blocked by:` faits, `Fichiers chauds:` disjoints) et propose les vagues ; le conducteur décide.

**Migrations : l'ordre d'arrivée dans develop fait foi.** Les horodatages réservés dans la carte (ligne `Migrations:` de la fiche, un horodatage jamais réservé par deux cartes ouvertes : `check:tickets`) sont un point de départ. Juste avant la livraison, une migration non livrée prend un horodatage strictement postérieur à la dernière migration de develop ; `scripts/chaine/migrations-ordre.mjs` le vérifie à la livraison d'un sujet (`sujet.sh livrer`), au passage d'une PR vers develop (`passer.sh`, refus = renvoi avec le fichier à renommer et l'horodatage libre suivant) et en CI (job `qualite`, étape « Ordre des migrations » ; `pnpm check:migrations-ordre` en local). Une sous-PR vers un sujet n'est pas concernée. Le dossier est la clé `migrations` de `.claude/chaine.json`.

Les index générés (`scripts/docs/index-generes.json`) ne comptent pas : ils se régénèrent après chaque merge.

## 5. Session fille : les consignes communes

Le prompt de lancement **renvoie à cette section** au lieu de la recopier. Gabarit du prompt, tout le reste est dans le ticket :

```text
Session fille du chantier <nom>, conducteur : <session_id>.
Ticket : <chemin du .issue.md>. Base : origin/sujet/<nom>.
Outils : ton premier geste, avant tout autre, est de charger send_message par ToolSearch, requête « select:mcp__claude-code-remote__send_message ». S'il ne se charge pas, écris « send_message absent » dans ta première réponse et arrête-toi : ton conducteur le verra à son relevé.
Suis docs/agents/chaine-de-production.md § 5, puis le ticket. Écris-moi (send_message) si tu es bloqué, et dès ta PR livrée, sans attendre ni les contrôles ni la fusion ; un choix non tranché se décide prudemment et se note sous ## Comments. Hors programme, une question à l'humain suit § 2 (« Une question au produit ») ; dans un programme, une question part au conducteur par `send_message`, qui la relaie à l'architecte.
Le produit : « arrête de me demander des autorisations fais tout ce qu'il faut pour avancer » et « Les seules questions auxquelles je dois répondre sont des décisions techniques ou métier pas des autorisations que je ne fais qu'accepter de toute façon. »
Intangibles : jamais --no-verify ; jamais de push forcé ni de réécriture d'historique ; jamais de fusion avec un contrôle exigé rouge ; jamais de test sauté ou assoupli ; jamais de push sur la branche par défaut ; une dépendance nouvelle attend l'accord humain.
Commits : jamais `git commit --amend` ; une correction est un commit de plus.
<une ligne de situation particulière, s'il y en a une>
```

_Cette ligne ne redit jamais une règle de ce document. Les deux lignes du produit sont la seule exception : elles se citent telles quelles, à sa demande (2026-11-14) ; la ligne « Commits : » qui les suit vient de l'architecte (`A-30`, `A-41`), comme dans `lancement.md`, et se recopie elle aussi. Le régime se lit dans la sortie de `sujet.sh demarrer` (la ligne `régime 8 : relecture indépendante ; …`), jamais sur le prompt._

_Le prompt d'une fille ne commence jamais par « / » (ni par une balise `<system-reminder>`) : `create_session` refuse un tel prompt, qui pourrait être lu comme une commande (cas vécu le 2026-11-23). Il s'ouvre par des mots, comme le gabarit ci-dessus ; un skill marqué `disable-model-invocation` que la fille doit suivre se lit dans son fichier sous `~/.claude/plugins/marketplaces/maj/skills/`, jamais par une commande en tête._

Déroulé :

1. **Environnement.** `git fetch origin develop sujet/<nom>` ; `pnpm install --frozen-lockfile --prefer-offline` ; la base locale (`compose.yaml`) si le ticket touche la persistance.
2. **Réserver** depuis `origin/sujet/<nom>` : `docs/agents/issue-tracker.md` § « Réserver un ticket » (PR brouillon vers le sujet).
3. **Lire** le ticket, les deux règles qu'il nomme et le modèle qu'il cite. Pas d'exploration au-delà ; un besoin de lecture large passe par un sous-agent `Explore`, qui rend une conclusion et pas des fichiers.
   **Un écran se code sur sa planche** (ligne `Maquette:`), jamais de mémoire. **La planche est dans le dépôt** : une session fille ne peut pas ouvrir un artefact (Claude Design ou autre outil de maquette en ligne). Le conducteur la lit et la recopie sous `docs/design/planches/<id>.html` avant de lancer la fille, ou la décrit précisément dans le ticket ; la ligne `Maquette:` désigne ce fichier. Cas vécu : deux écrans codés sans leur planche, un ticket de retouches. Un doute sur le design — un geste, un état, un libellé, une place — ne se tranche pas seul. **Hors programme**, il se pose au produit par `AskUserQuestion`, dans la forme de § 2 (« Une question au produit »), avec deux ou trois options et une recommandation, et le design peut évoluer dans la session avec lui. **Dans un programme**, une fille n'a personne devant elle : elle écrit son doute à son conducteur (`send_message`), qui le relaie à l'architecte, lequel le pose au produit dans la forme de § 2 ; le produit reste libre d'ouvrir lui-même la session d'une fille pour faire évoluer un écran avec elle. Les sources de design du projet et leur ordre de priorité sont dans son programme ou dans la carte du chantier.
4. **Coder** (une règle que la session crée ou réénonce en codant passe d'abord par le skill `criticite`, avant d'être codée), puis les vérifications ciblées du ticket, puis `pnpm check` **une fois**. Après tout merge du sujet dans la branche : régénérer les index avant le check.
   **Jamais d'amend.** Une correction est un commit de plus, jamais `git commit --amend`, même sur un commit pas encore poussé : le sommet annoncé, contre-relu ou étiqueté doit rester dans l'historique, et un amend déjà poussé ne repart que par un push forcé. La garde (`garde-commandes`) refuse l'un et l'autre.
   **Un fichier que les gardes chargent s'écrit d'un seul coup.** `scripts/agent/*.mjs` est importé par les hooks d'agent, qui refusent tout outil quand il ne se charge pas : écrit à moitié, il bloque la session, sa réparation comprise. La nouvelle version se prépare dans une copie hors du dépôt (scratchpad), se vérifie (`node --check <copie>`, puis l'import qui réussit et rend chaque export de la version en place : `node -e "import('<copie>').then((m) => console.log(Object.keys(m).sort().join(' ')))"`, comparé à la même commande sur `scripts/agent/<fichier>`, aucun nom ne manque), puis se pose en une opération, toujours la même : `cp <copie> scripts/agent/<fichier>` ; jamais une suite d'`Edit` sur le vrai fichier. Session déjà bloquée : elle s'arrête et le dit à qui l'a lancée, qui fait restaurer `scripts/agent/` par un humain depuis le dernier commit où les gardes se chargent (`git checkout origin/develop -- scripts/agent/` si develop est sain, sinon `git checkout <commit> -- scripts/agent/`) ; jamais en contournant la garde.
5. **Demander la relecture.** La fille ne se relit pas et ne lance aucun relecteur : une session de relecture, que le Relecteur du dépôt lance, relit sa PR. `Status: Fait — PR #<n>` dans le ticket, poussé ; vérifier que « titre (#n) » tient en 120 caractères et passe commitlint : `printf '%s\n' "<titre> (#<n>)" | pnpm exec commitlint` ; la PR sort du brouillon **après le dernier push** (`git ls-remote origin <branche>` = `HEAD`) : un brouillon ne lance aucun job, une PR prête relance toute la CI à chaque push. Puis, sur la PR, la ligne que rend `node scripts/chaine/demande.mjs --session <la sienne> --conducteur <celle du conducteur>`, copiée telle quelle, seule dans son commentaire. Sa forme, citée ici seulement, pour la lire : `À relire — sommet <sha> — Session: <id ou —> — Conducteur: <id ou —>`, le sha entier du dernier push, que le script lit dans git et refuse non poussé. Le script absent (un projet qui n'a pas reposé `fusionner`) : `node ~/.claude/plugins/marketplaces/maj/skills/chaine/fusionner/scripts/demande.mjs`, mêmes arguments (dans le dépôt `skills`, `node skills/chaine/fusionner/scripts/demande.mjs`) ; la demande ne se modifie jamais ; une erreur (un sha faux) se corrige par une demande neuve, que rend le script (une demande modifiée est écartée, le Relecteur le dit sur la PR) ; puis l'étiquette `à-relire`, par la liste entière des étiquettes (`issue_write`). **Jamais `à-fusionner`** : le Relecteur la pose sur un verdict validé, puis le capitaine fusionne. Une règle que le ticket fait passer à haute, ou une ligne `Relecture: double`, demande deux sessions : le Relecteur les lance. Périmètre, règle 1 : **Déclaration.** Avant sa première demande de relecture, l'auteur écrit un commentaire dont la première ligne est `Périmètre — <objet en une ligne>`, suivie de trois lignes : `Fichiers:` (chemins ou dossiers), `Décisions:` (identifiants des décisions et des ADR que la PR écrit, ou « aucune ») et `Sujets:`. Seul le premier commentaire de cette forme compte, et il n'est jamais modifié. Au tour 1, tout fichier du diff est couvert par la ligne `Fichiers:`. Sans elle, sur une PR de documentation, le Relecteur écrit `Périmètre absent` et ne distribue rien.
6. **Sur `à-reprendre`** (verdict `refusé`) : lire le verdict sur la PR, jamais un résumé ; corriger chaque bloquant avec le test qui l'aurait attrapé, ou le contester sur la PR, `Contesté — <critère, fichier et ligne> — <raison>`, et l'écrire en une ligne au conducteur, qui arbitre (`Arbitrage — … — maintenu` ou `écarté`) et le lui écrit. Un doute n'oblige à rien. Puis pousser, et redemander la relecture : une demande neuve, par le script (étape 5), au nouveau sommet, puis `à-relire` posée avant de retirer `à-reprendre` (une PR ne reste jamais sans étiquette). **Un bloquant contesté attend son arbitrage** : la relecture se redemande une fois l'arbitrage écrit (maintenu : le bloquant corrigé d'abord), au même sommet si rien n'a été poussé, jamais avant (le Relecteur remettrait `à-reprendre`). Trois tours refusés : le plafond, que l'architecte décide (sans programme, le conducteur ou le produit) ; la fille attend la décision, qu'on lui écrit, la suit, puis redemande la relecture : sans demande, la PR reste `à-reprendre`, hors de la file du Relecteur. Un trou du ticket révélé par un verdict (surface oubliée, règle non citée) se corrige dans le ticket aussi. Périmètre, règle 2 : **Corrections.** Entre deux tours, les fichiers que l'auteur modifie sont ceux de la ligne `Fichiers:` et ceux que nomme un bloquant du dernier verdict refusé. Dans ces fichiers, il ne corrige que les constats de ce verdict. Il peut aussi clarifier un passage que le verdict nomme sous « Écartés au tri » avec le motif « faux », sans en changer le sens : par exemple citer la règle qui justifie une définition, ou écrire le résultat attendu d'une commande de preuve. Périmètre, règle 3 : une décision, un fait ou une ADR que la déclaration ne nomme pas est un bloquant. Sa correction est le retrait, jamais l'ajout de ce qui manque autour. Périmètre, règle 4 : **Suite.** Ce qui est retiré, ou ce qu'un constat révèle hors du périmètre, s'écrit dans un ticket ou dans une autre PR. L'auteur le cite sur la PR courante par un commentaire `Suite — <objet> — <ticket ou PR>`. Un fichier de plus, et le Relecteur écrit `Périmètre dépassé — <fichiers>` sans compter de tour.
7. **Rendre la main** en cinq lignes, qui partent par `send_message` au conducteur dès la relecture demandée. Toute décision attendue de lui (ADR proposée, dépendance, règle à trancher) est écrite sous `## Comments` et dans le corps de la PR, puis nommée dans ce message : PR, fait, reste, décision prise par défaut (aussi notée sous `## Comments` du ticket), question. Puis armer **le réveil de secours**, un `send_later` à 120 minutes (le second réveil, à quatre heures, voit le cas des trois heures), à chaque demande de relecture et à chaque contestation : au réveil, si la PR porte `à-reprendre`, lire le verdict et corriger (étape 6) ; `fusion-bloquée` sans `à-relire`, lire le renvoi du capitaine, corriger, redemander la relecture ; aucune des quatre étiquettes (`à-relire`, `à-reprendre`, `à-fusionner`, `fusion-bloquée`), reposer `à-relire` ; `à-relire` depuis plus de trois heures sans distribution du Relecteur pour son sommet (`Relecture — tour <k> — sommet <sha> — …`), l'écrire au conducteur (un Relecteur arrêté) ; sinon rien, et le réarmer une fois. Puis s'arrêter : une session fille ne prend pas de second ticket. **Skill absent de la session** : le plugin `maj-skills` est installé par le script de l'environnement ; s'il manque, le hook de démarrage le signale : la fille l'installe elle-même (si `claude plugin marketplace list` ne rend pas `maj`, `claude plugin marketplace add MAJ-agency/skills` ; puis `claude plugin install maj-skills@maj`) et lit le skill qu'elle doit suivre sous `~/.claude/plugins/marketplaces/maj/skills/chaine/<nom>/SKILL.md` ; si l'installation échoue, elle l'écrit à son conducteur et s'arrête.

Une dépendance hors de la ligne `Dépendances:` du ticket est un blocage : `send_message` au conducteur, jamais un contournement.

Renvoyée par le capitaine (`fusion-bloquée`) : lire son commentaire, corriger, pousser, puis redemander la relecture (une demande neuve par le script (étape 5) au nouveau sommet, puis `à-relire`, sans retirer `fusion-bloquée`, que le Relecteur retire en posant `à-fusionner`) ; jamais `à-fusionner`.

## 6. Économie de tokens : les règles

| Règle                                                                                                                                                       | Pourquoi (mesuré sur un premier projet)                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Une session, un rôle ; un livrable hors rôle part ailleurs                                                                                                  | un conducteur a produit un deck de 25 slides dans son contexte d'orchestration : 788 k tokens, compaction forcée |
| Le conducteur tient son état dans la carte et le tableau d'avancement, et compacte (`/compact`) entre deux vagues                                           | un conducteur relisait 610 à 640 k tokens à chaque notification de fille : 99 $ pour la journée                 |
| Prompt de fille = gabarit de trois lignes, le reste dans le ticket et ce fichier                                                                            | 3 k caractères de règles recopiés dans chacun de 30 prompts                                                      |
| Ticket prêt = `Où` / `Décisions` / `Surfaces` / `Vérification` remplis                                                                                      | exploration, questions et `pnpm check` répétés chez les filles                                                   |
| Specs fusionnées dans le sujet avant la première fille ; dépendance fusionnée avant le ticket qui en dépend                                                  | 12 PR en conflit à remettre à jour une par une, deux doublons fermés                                              |
| Aucune attente active : ni sonde de CI, ni « j'attends » ; une fille qui a livré s'arrête                                                                   | chaque réveil d'un gros contexte coûte 0,4 à 0,7 $                                                               |
| Avancement demandé = tableau lu, pas un tour du conducteur                                                                                                   | cinq demandes « en % ? » dans la journée, chacune sur un contexte de plus de 600 k tokens                        |
| Plafond du conducteur : à 400 k tokens de contexte, il se signale ; il prévient l'architecte, qui prévient le produit, et le produit décide ; aucune session n'est interrompue ; s'il décide une session de suite, la passation est écrite dans la carte (`Conducteur:` mis à jour) ; `/compact` entre deux vagues reste permis. L'architecte n'a pas de plafond : le produit décide seul quand on en change | 31 $ la suite de chantier contre 99 $                                                                            |
| `.claude/settings.json` et `scripts/agent/` se modifient par une PR, jamais dans l'éditeur GitHub ; une session n'y élargit rien                              | un `settings.json` retouché quatre fois dans l'éditeur GitHub, une seule fois juste                              |
| Sonnet par défaut pour une fille, Opus sur raison écrite                                                                                                    | 4 $ contre 7 $ par ticket comparable                                                                             |

**Relevé des coûts.** Le coût d'une session se lit par `get_session` (`external_metadata.usage.cost_usd`) ; c'est le conducteur qui le relève, dans la section `## Coût` de la carte : les filles d'une vague dès qu'elle est fusionnée, puis le capitaine et le conducteur (rôle `conducteur`) en fin de chantier. Les **sessions de relecture** d'une PR (lues sur ses distributions, `Relecture — tour <k> — sommet <sha> — sessions <…>`) se relèvent avec la fille qui l'a écrite, rôle `relecture`. **Le conducteur nomme ensuite ses filles et leurs sessions de relecture à l'architecte**, dans le même réveil, une ligne par session : `à archiver : <session>, <ticket>, <coût>` (sans programme, au produit). Il n'archive pas lui-même : la garde du mode « Auto » refuse `archive_session` à une session dont aucun humain n'a pris acte ; l'architecte archive (`P-62`). Une fille dont la PR est fusionnée n'a plus rien à faire, et le capitaine, qui ne veille que sur sa file, en a laissé quatre ouvertes sur un chantier. L'archivage se défait (`unarchive_session`) et le coût reste lisible. Un dépassement des plafonds (§ 3 « Taille » et tableau ci-dessus ; une PR renvoyée trois fois attend un humain) s'écrit dans `## Dépassements` : session, ticket, mesure, décision du produit, date. Chaque session lancée porte le tag `chantier:<nom>`. Le coût moyen par ticket, comparé d'un chantier à l'autre, dit si les règles ci-dessus font baisser la dépense. Le registre transverse, `docs/agents/couts.md`, agrège ces sections pour tous les chantiers (total, par chantier, par session). C'est un index généré (`node scripts/docs/couts.mjs`, déclaré dans `scripts/docs/index-generes.json`) : on corrige la carte, jamais le registre, et le capitaine le régénère après chaque fusion. Relever les filles à chaque fin de vague, et non en fin de chantier seulement, garde ce registre à jour en continu ; le capitaine et le conducteur s'y ajoutent en fin de chantier.
