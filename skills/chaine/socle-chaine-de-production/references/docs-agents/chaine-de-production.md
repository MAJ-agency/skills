# Chaîne de production : qui fait quoi, du cadrage à develop

Mode d'emploi des sessions de l'assistant de développement quand plusieurs travaillent en parallèle. Décision et raisons : `{{ADR_CHAINE}}`. Branches de sujet : `{{ADR_SUJET}}`. Contrat du projet : `.claude/chaine.json`.

**Pour lancer un chantier : `/maj-skills:chantier <objectif>`** dans une session neuve, celle du conducteur de chantier. Elle pose les questions de setup, écrit la fiche dans la carte et déroule ce fichier phase par phase ; relancée avec le nom du sujet, elle reprend à la phase en cours.

Le principe : **les tokens se dépensent une fois, au cadrage**. Une session fille qui doit chercher où coder, relire les règles en entier, deviner une décision ou réparer son environnement paie ce que le cadrage aurait payé une seule fois pour toutes.

## 1. Les rôles

Une session tient **un seul rôle**. Un travail d'un autre rôle (un deck, une étude, une contre-revue longue) part dans une autre session ou un sous-agent.

| Rôle                 | Combien                      | Fait                                                                                                                                                    | Ne fait jamais                                                      | Modèle conseillé                  |
| -------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------- |
| Produit (personne)   | —                            | tranche les questions du grilling, valide le découpage, décide la livraison en recette                                                                  | —                                                                   | —                                 |
| Architecte           | un par programme             | mène l'amont : questions au produit, décisions, specs validées ; seul à parler au produit ; lance le conducteur de chaque chantier et lui répond (`send_message`) | découper un chantier en tickets, lancer des filles, coder, fusionner | Opus                              |
| Conducteur de chantier | un par chantier            | à partir d'une spec validée : carte, tickets **prêts pour agent** (§ 3), ouverture du sujet, lancement des filles par vagues, suivi par le tableau d'avancement, contre-revue ciblée, archivage des filles finies ; sans programme, grilling court avec le produit | grilling complet ; dans un programme, parler au produit (tout passe par l'architecte) ; coder un ticket, produire un livrable hors chantier, fusionner | Opus                              |
| Session fille        | une par ticket               | réserve, code, vérifie, revue adversariale, livre, s'arrête                                                                                             | prendre un 2ᵉ ticket, fusionner, partir d'une branche non fusionnée | Sonnet ; Opus si le ticket le dit |
| Capitaine de fusion  | un pour le dépôt             | file `à-fusionner`, sous-PR dans les sujets, livraison des sujets, renvois (skill `fusionner`) ; veille la file par `scripts/chaine/veille.sh`, qui relance la boucle dès qu'une PR est prête | résoudre un conflit de code d'une autre session                     | Sonnet                            |
| Relecteur adversaire | un sous-agent par PR de code | lit le diff seul, liste fermée de critères (skill `revue-adversariale`)                                                                                 | proposer des améliorations                                          | celui de la session               |

Chaque carte nomme son **responsable** (`Responsable:`), une personne, celle qui répond du chantier ; `Architecte:` nomme la session du programme (ligne absente quand le chantier n'en a pas) et `Conducteur:` la session qui mène le chantier. Une carte d'avant ces rôles, où `Architecte:` nommait la session du chantier, n'est pas réécrite : elle est gelée dans la dette du gate (clé `fiches`).

Le **modèle se choisit par ticket**, pas par chantier : la ligne `Modèle:` du ticket (§ 3) le dit. Sonnet pour un ticket dont le brief nomme les fichiers, les décisions et les surfaces ; Opus pour ce qui reste à concevoir ou à arbitrer (migration délicate, conception d'écran neuve, règle absente ou ambiguë), raison écrite sur la ligne `Modèle:`. Mesuré sur un premier projet : 4 $ par ticket en Sonnet, 7 $ par ticket comparable en Opus, sans écart de qualité visible au passage du capitaine.

## 2. Le cycle d'un chantier

```
cadrage ──► carte + specs ──► tickets prêts ──► PR de specs fusionnée dans le sujet ──► vagues de filles ──► sujet livré ──► rétro
(produit,     (architecte,      (conducteur)          (capitaine)                         (filles)            (capitaine)   (conducteur)
architecte)   conducteur)
```

1. **Cadrage.** Grilling avec le produit, mené par l'architecte du programme (`docs/methode/grilling.md`, par les skills de Matt Pocock ; sans programme, le conducteur ne mène qu'un grilling court) : une question à la fois, recherche faite **avant** de poser la question, recommandation à chaque fois. Rien n'est écrit dans le dépôt pendant le grilling.
2. **Carte et specs.** Carte `*.map.md` (décisions, brouillard), specs, tickets. La spec porte `Sujet: sujet/<nom>`. **Après la PR de cadrage, le conducteur met la carte à jour (phase, sessions, coûts, incidents, rétro) directement sur le sujet, par `bash scripts/chaine/sujet.sh carte <nom>`** : commit local qui modifie en place **ce seul fichier** `*.map.md` (celui dont la ligne `Sujet:` nomme exactement le sujet, avant comme après le commit, formaté par Prettier), puis la commande, qui rattrape le sujet par `git merge --ff-only` et pousse sans force le sommet qu'elle a vérifié ; elle refuse (sortie 9) un autre fichier, une carte créée, supprimée, renommée ou changée de mode, la carte d'un autre sujet, un commit de fusion, un historique divergent et toute option de force. Jamais `git push origin HEAD:sujet/<nom>` : le hook le refuse.
3. **Sujet ouvert, specs d'abord.** `sujet.sh ouvrir <nom>`, puis la PR de specs **vise le sujet** et y est fusionnée **avant** le lancement de la première fille. Jamais de fille partie d'une branche de specs : douze PR parties d'une branche de specs sont toutes tombées en conflit au squash des specs.
4. **Vagues.** Une vague = les tickets dont tous les `Blocked by:` sont fusionnés dans le sujet **et** qui ne partagent pas de fichier chaud (§ 4). Un ticket bloqué attend la vague suivante : on ne « fusionne pas localement » la dépendance.
5. **Suivi.** Le conducteur suit le tableau d'avancement (`node scripts/docs/avancement.mjs sujet/<nom>`, ou `<SPEC>` ; `--json` pour une page partagée), pas les messages de chaque fille. Il ne se réveille que sur un renvoi, une question ou une fin de vague.
6. **Livraison.** Le capitaine livre le sujet quand ses tickets sont faits (`sujet.sh livrer-prets`). `boucle.sh` se lance depuis le worktree, sans copie manuelle : à chaque tour elle fait `git fetch origin develop`, recopie `scripts/chaine` d'`origin/develop` dans `<git-common-dir>/boucle-outils` et n'appelle que cette copie ; si `boucle.sh` a changé sur develop, elle se relance dessus (`exec`) ; `origin/develop` introuvable ou fetch en échec trois fois : arrêt (sortie 6), jamais de scripts périmés. **Une seule boucle à la fois, arrêt d'un geste** : un verrou `flock` sous `<git-common-dir>` refuse une seconde boucle (sortie 9, même si c'est un processus d'attente oublié qui la relance, et même après l'`exec`) ; `bash scripts/chaine/boucle.sh --arreter` pose `<git-common-dir>/boucle-arret` puis interrompt la boucle et le passage en cours (détenteurs réels du verrou, descendants, groupe noté ; la veille n'est tuée que si elle partage le groupe) et la trappe remet le worktree propre (sortie 143) ; la boucle relit ce fichier au démarrage, à chaque tour, avant `livrer-prets` et avant chaque passage (sortie 10) et une relance le refuse tant qu'il existe ; **reprendre** : `bash scripts/chaine/boucle.sh --reprendre` (retire le fichier, puis lance la boucle). **Livraison intermédiaire** (livrer dans develop un sujet dont la carte reste en phase 4, pour libérer un autre sujet) : demander `sujet.sh livrer <nom> "<titre>"`. La PR part d'une branche jetable `livraison/<nom>-<date>`, que GitHub supprime à la fusion : `sujet/<nom>` survit. Le capitaine ne la traite comme livraison (commit de merge, sans revue) que si `sujet/<nom>` existe et que la branche n'apporte qu'un sommet de ce sujet fusionné avec develop : c'est encore vrai après sa propre mise à jour avec develop, plus si une session y ajoute un commit. Le commit de merge nomme le sujet (`Sujet: sujet/<nom>`), ce qui le fait reconnaître livré une fois sa branche supprimée. Dès que la carte est en `5-livraison` ou plus, la PR part de `sujet/<nom>`, supprimée à la fusion. Il veille la file en tâche de fond par `veille.sh` (sondage léger, relance `boucle.sh` dès qu'une PR est prête ou rouge ; `VEILLE FINIE` ou `VEILLE ARRÊTÉE` réveille la session). **Sans veille en cours** (capitaine démarré avant que `veille.sh` soit posé, veille arrêtée et pas encore relancée), **qui pose `à-fusionner` prévient le capitaine par `send_message`** (fille, architecte ou conducteur) : une file que personne ne regarde une fois vide ne reprend pas d'elle-même.
7. **Rétro.** Chaque renvoi du capitaine et chaque échec de vague donne une ligne : un piège documenté, un critère de la revue adversariale, ou un gate. Un piège vécu deux fois sans gate est une dette.

**Une question au produit se lit sans être développeur.** Le produit tranche ce qui change la vie des utilisateurs, le coût ou le délai, pas la technique. Toute question qui lui parvient, d'un architecte, d'un conducteur ou d'une fille, par `AskUserQuestion` ou par message (dans un programme, celles du conducteur passent par l'architecte) :

- **ne lui arrive que si elle a une conséquence pour lui** : ce que voit ou fait un utilisateur, une dépense, une date. Un choix purement technique (bibliothèque, forme d'une table, mécanisme interne), la session qui le rencontre (architecte ou conducteur) le tranche, l'écrit dans la carte (`A-n`, avec sa raison) ou en ADR, et ne le soumet pas ;
- **commence par le besoin, en une phrase de métier**, avec un exemple concret tiré du client (« le 15, l'application lance les prélèvements toute seule ») ;
- **décrit chaque option par ce qu'elle change pour lui** : ce que voit l'utilisateur, ce que ça coûte, le risque. Le nom technique vient en dernier, entre parenthèses, ou pas du tout ;
- **met la recommandation en premier**, dit pourquoi en une phrase, et reste courte : trois ou quatre lignes avant les options ;
- **n'emploie aucun terme technique sans le traduire** : pas de `cron`, `RLS`, `worker`, `jsonb`, `UTC` ni nom de table ; les termes du glossaire du projet sont bienvenus ;
- **porte une seule décision** : quatre contradictions citées en bloc, avec leurs dates, ne se lisent pas ; l'auteur de la question tranche ce que la source la plus récente tranche déjà et ne pose que le reste.

Une question qui ne passe pas ce filtre revient à son auteur. Cas vécu : « tick du planificateur, registre, table `scheduled_job_run` sous clé unique et verrou PostgreSQL » ; le produit a répondu « j'ai rien compris ». La vraie question était : « une alerte d'intervenant non pointé peut-elle arriver avec 10 à 20 minutes de retard, pour ne pas payer un serveur de plus ? ».

## 3. Un ticket prêt pour agent

`Status: ready-for-agent` veut dire qu'une session neuve peut le coder **sans exploration large ni question**. En tête du ticket :

```markdown
Status: ready-for-agent
Sujet: sujet/<nom> # si différent de la spec
Blocked by: 01, 03 # tickets du même chantier, fusionnés dans le sujet avant de commencer
Modèle: sonnet # ou opus, avec la raison
Fichiers chauds: src/db/migrations/* # fichiers que d'autres tickets touchent aussi (§ 4)
Label: contre-revue # obligatoire quand Fichiers chauds touche cheminsSensibles (le gate tickets le vérifie) : le conducteur contre-relit, puis pose lui-même à-fusionner (§ 5, étape 6)
Dépendances: `leaflet`, `@types/leaflet` # paquets que le ticket ajoute, nom sans version, validés au découpage, ou — ; une dépendance hors de cette ligne est un blocage (§ 5)
Maquette: <fichier du dépôt : maquette HTML et section, ou planche recopiée sous docs/design/planches/> # dès que le ticket touche un écran ; sans planche validée, le ticket reste needs-info ; jamais un artefact seul : une fille ne peut pas l'ouvrir
```

La ligne `Dépendances:` fait foi telle qu'elle est sur la branche du sujet (`origin/sujet/<nom>`), jamais dans l'arbre de travail ni sur la branche de la fille : le hook d'agent laisse passer `pnpm add` (ou `pnpm install <paquet>`) quand chacun des paquets ajoutés y figure. Seule compte une copie du sujet dont le sommet est celui d'`origin` (`git ls-remote`) ; un ticket présent sur plusieurs sujets ne laisse passer que les paquets que toutes ses copies prévoient. Un paquet absent de la ligne, une option ou un préfixe qui change la source (`--registry`, `--config.*`, `--global`, `-C`, `npm_config_*=…`), un ticket hors sujet ou un `origin` injoignable demande l'accord d'un humain. Une dépendance hors de la ligne est un blocage de la fille (`send_message` au conducteur), jamais un contournement. Un sujet ne se pousse jamais à la main : le hook refuse tout `git push` vers `sujet/*`, quelle que soit la branche courante et la forme de la commande (guillemets, `git -C`, chemin de git, préfixe comme `timeout`, sous-shell, `--repo`, `HEAD` ou push nu depuis une branche `sujet/…`), et seul `sujet.sh` y écrit, la carte comprise (`sujet.sh carte <nom>`) ; sans ce refus, une session écrirait elle-même la ligne qui l'autorise. Une destination illisible (variable, substitution, motif, `--all`, `--mirror`) demande l'accord d'un humain. Un `.npmrc` ou un `pnpm-workspace.yaml` modifié par rapport à `develop` (ou créé hors de l'index) suspend le laissez-passer : on demande. Ce hook est une garde, pas une frontière : un script lancé par la session n'est pas lu, et seule une protection de `sujet/*` côté GitHub en ferait une.

Un ticket qui crée un module d'authentification, de droits, de chiffrement, de paiement ou d'export ajoute son dossier à `cheminsSensibles` (`.claude/chaine.json`) dans la PR de cadrage ; la revue adversariale (critère S14) relève un tel code hors de la liste.

Puis, dans le corps, quatre sections que la fille lit au lieu de chercher :

| Section           | Contenu                                                                                                                                                                      | Ce que ça évite                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `## Où`           | fichiers à créer ou modifier, `fichier:ligne` du modèle à imiter, l'appelant réel de toute fonction citée (route, listener, cron), règles à lire (deux au plus)              | l'exploration du dépôt, la lecture de toutes les règles |
| `## Décisions`    | ce qui est tranché (renvoi à la carte ou à l'ADR), et ce que la fille tranche seule par défaut prudent                                                                       | les questions à l'humain, les allers-retours            |
| `## Surfaces`     | table surface → test qui la prouve                                                                                                                                           | la couverture rouge découverte au push                  |
| `## Vérification` | commandes ciblées avant `pnpm check` (typecheck du paquet, specs nommées), index à régénérer, specs de garde à compléter                                                     | trois `pnpm check` complets pour un typecheck rouge     |

Le gate `tickets` (`pnpm check:tickets`, `scripts/verify/tickets.mjs`) refuse un ticket `ready-for-agent` sans `Modèle:`, sans l'une de ces quatre sections, ou dont `Fichiers chauds:` touche un motif de `cheminsSensibles` sans `Label: contre-revue` (l'ancienne valeur `Label: architecte` a le même effet et reste acceptée) ; les tickets prêts d'avant l'installation du gate sont gelés dans `scripts/verify/tickets-dette.json`, qui ne reçoit jamais d'entrée nouvelle. Gabarit : `docs/agents/gabarits/ticket.issue.md`.

Taille : un jour au plus, une quinzaine de fichiers. Une fille est interrompue à 300 k tokens de contexte ou à 20 $ (`plafonds.mjs`, contrôlé par le conducteur à chaque réveil) : c'est le signe d'un ticket mal découpé, la question revient au produit (découper, relancer, ou accepter par écrit), et la ligne va dans `## Dépassements` de la carte.

## 4. Branches et fichiers chauds

Les règles de branche (sujet dès la première PR, jamais de PR empilée, un seul capitaine) sont celles de `CLAUDE.md` § « Fusion vers `develop` : une file, un capitaine ». S'y ajoute **l'ordonnancement des fichiers chauds** : deux tickets d'une même vague ne touchent pas le même fichier parmi ceux que les tickets déclarent. Candidats habituels : le dossier des migrations (une migration à la fois par sujet, horodatages réservés par le conducteur dans le brief), les seeds, les contrats partagés de `packages/contracts`, les fichiers de registre.

`node scripts/docs/vagues.mjs <spec>` applique ces règles aux tickets (`Blocked by:` faits, `Fichiers chauds:` disjoints) et propose les vagues ; le conducteur décide.

**Migrations : l'ordre d'arrivée dans develop fait foi.** Les horodatages réservés dans la carte (ligne `Migrations:` de la fiche, un horodatage jamais réservé par deux cartes ouvertes : `check:tickets`) sont un point de départ. Juste avant la livraison, une migration non livrée prend un horodatage strictement postérieur à la dernière migration de develop ; `scripts/chaine/migrations-ordre.mjs` le vérifie à la livraison d'un sujet (`sujet.sh livrer`), au passage d'une PR vers develop (`passer.sh`, refus = renvoi avec le fichier à renommer et l'horodatage libre suivant) et en CI (job `qualite`, étape « Ordre des migrations » ; `pnpm check:migrations-ordre` en local). Une sous-PR vers un sujet n'est pas concernée. Le dossier est la clé `migrations` de `.claude/chaine.json`.

Les index générés (`scripts/docs/index-generes.json`) ne comptent pas : ils se régénèrent après chaque merge.

## 5. Session fille : les consignes communes

Le prompt de lancement **renvoie à cette section** au lieu de la recopier. Gabarit du prompt, tout le reste est dans le ticket :

```text
Session fille du chantier <nom>, conducteur : <session_id>.
Ticket : <chemin du .issue.md>. Base : origin/sujet/<nom>.
Suis docs/agents/chaine-de-production.md § 5, puis le ticket. Écris-moi (send_message) si tu es bloqué, et une fois à la fin ; un choix non tranché se décide prudemment et se note sous ## Comments. Une question à l'humain suit § 2 (« Une question au produit »).
<une ligne de situation particulière, s'il y en a une>
```

_Cette ligne ne redit jamais une règle de ce document. Le régime de livraison se lit sur l'en-tête du ticket (`Label:`), jamais sur le prompt._

Déroulé :

1. **Environnement.** `git fetch origin develop sujet/<nom>` ; `pnpm install --frozen-lockfile --prefer-offline` ; la base locale (`compose.yaml`) si le ticket touche la persistance.
2. **Réserver** depuis `origin/sujet/<nom>` : `docs/agents/issue-tracker.md` § « Réserver un ticket » (PR brouillon vers le sujet).
3. **Lire** le ticket, les deux règles qu'il nomme et le modèle qu'il cite. Pas d'exploration au-delà ; un besoin de lecture large passe par un sous-agent `Explore`, qui rend une conclusion et pas des fichiers.
   **Un écran se code sur sa planche** (ligne `Maquette:`), jamais de mémoire. **La planche est dans le dépôt** : une session fille ne peut pas ouvrir un artefact (Claude Design ou autre outil de maquette en ligne). Le conducteur la lit et la recopie sous `docs/design/planches/<id>.html` avant de lancer la fille, ou la décrit précisément dans le ticket ; la ligne `Maquette:` désigne ce fichier. Cas vécu : deux écrans codés sans leur planche, un ticket de retouches. Un doute sur le design — un geste, un état, un libellé, une place — ne se tranche pas seul : il se pose au produit par `AskUserQuestion`, dans la forme de § 2 (« Une question au produit »), avec deux ou trois options et une recommandation, et le design peut évoluer dans la session avec lui. Les sources de design du projet et leur ordre de priorité sont dans son programme ou dans la carte du chantier.
4. **Coder**, puis les vérifications ciblées du ticket, puis `pnpm check` **une fois**. Après tout merge du sujet dans la branche : régénérer les index avant le check.
5. **Revue de ticket** (skill `revue-de-ticket` : trois sous-agents — règles, ticket, documentation), corriger les bloquants, deux tours au plus. La section `## Revue de ticket` va **dans le corps de la PR** : le capitaine la lit là. Un trou du ticket révélé par la revue (surface oubliée, règle non citée) se corrige dans le ticket aussi. **Skill absent de la session** : une fille ne reçoit que le dépôt du projet, et les skills MAJ ne s'installent qu'avec le dépôt `skills` cloné à côté. Elle attache alors ce dépôt par `add_repo` (`MAJ-agency/skills`), le clone comme l'outil l'indique, puis lit et suit `skills/chaine/revue-de-ticket/SKILL.md` du clone, ses références comprises. Si l'attache échoue, la PR sort du brouillon **sans** `à-fusionner` et la revue est demandée au conducteur : jamais de PR livrée sans revue. Cas vécu : cinq filles d'une même journée livrées sans revue de ticket.
6. **Livrer.** `Status: Fait — PR #<n>`, PR hors brouillon, label `à-fusionner` : `CLAUDE.md` § « Fusion vers `develop` ». La PR sort du brouillon **après le dernier push** : un brouillon ne lance aucun job, une PR prête relance toute la CI à chaque push. Avant de poser `à-fusionner`, vérifier que « titre (#n) » tient en 120 caractères et passe commitlint : `printf '%s\n' "<titre> (#<n>)" | pnpm exec commitlint`. Le label se pose **après le push du dernier commit** (`git ls-remote origin <branche>` = `HEAD`) : le capitaine squashe la tête qu'il trouve. Pour un ticket `Label: contre-revue` (ou l'ancien `Label: architecte`), la fille livre **sans** `à-fusionner` ; le conducteur contre-relit, puis pose le label lui-même.
7. **Rendre la main** en cinq lignes, qui partent par `send_message` au conducteur. Toute décision attendue de lui (ADR proposée, dépendance, règle à trancher) est écrite sous `## Comments` et dans la section de PR, puis nommée dans ce message : PR, fait, reste, décision prise par défaut (aussi notée sous `## Comments` du ticket), question. Puis armer **un** `send_later` à 90 min — « si ma PR porte `fusion-bloquée`, lire les commentaires du capitaine et corriger ; sinon rien ». Puis s'arrêter : une session fille ne prend pas de second ticket.

Une dépendance hors de la ligne `Dépendances:` du ticket est un blocage : `send_message` au conducteur, jamais un contournement.

Renvoyée par le capitaine (`fusion-bloquée`) : corriger, retirer le label, remettre `à-fusionner`, relire les labels.

## 6. Économie de tokens : les règles

| Règle                                                                                                                                                       | Pourquoi (mesuré sur un premier projet)                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Une session, un rôle ; un livrable hors rôle part ailleurs                                                                                                  | un conducteur a produit un deck de 25 slides dans son contexte d'orchestration : 788 k tokens, compaction forcée |
| Le conducteur tient son état dans la carte et le tableau d'avancement, et compacte (`/compact`) entre deux vagues                                           | un conducteur relisait 610 à 640 k tokens à chaque notification de fille : 99 $ pour la journée                 |
| Prompt de fille = gabarit de trois lignes, le reste dans le ticket et ce fichier                                                                            | 3 k caractères de règles recopiés dans chacun de 30 prompts                                                      |
| Ticket prêt = `Où` / `Décisions` / `Surfaces` / `Vérification` remplis                                                                                      | exploration, questions et `pnpm check` répétés chez les filles                                                   |
| Specs fusionnées dans le sujet avant la première fille ; dépendance fusionnée avant le ticket qui en dépend                                                  | 12 PR en conflit à remettre à jour une par une, deux doublons fermés                                              |
| Aucune attente active : ni sonde de CI, ni « j'attends » ; une fille qui a livré s'arrête                                                                   | chaque réveil d'un gros contexte coûte 0,4 à 0,7 $                                                               |
| Avancement demandé = tableau lu, pas un tour du conducteur                                                                                                   | cinq demandes « en % ? » dans la journée, chacune sur un contexte de plus de 600 k tokens                        |
| Plafond du conducteur et de l'architecte : à 400 k tokens de contexte, `plafonds.mjs` dit `passer-la-main` ; la passation est écrite dans la carte et une session de suite reprend (`Conducteur:` mis à jour) ; `/compact` entre deux vagues reste permis en deçà | 31 $ la suite de chantier contre 99 $                                                                            |
| `.claude/settings.json` et `scripts/agent/` se modifient par une PR, jamais dans l'éditeur GitHub ; une session n'y élargit rien                              | un `settings.json` retouché quatre fois dans l'éditeur GitHub, une seule fois juste                              |
| Sonnet par défaut pour une fille, Opus sur raison écrite                                                                                                    | 4 $ contre 7 $ par ticket comparable                                                                             |

**Relevé des coûts.** Le coût d'une session se lit par `get_session` (`external_metadata.usage.cost_usd`) ; c'est le conducteur qui le relève, dans la section `## Coût` de la carte : les filles d'une vague dès qu'elle est fusionnée, puis le capitaine et le conducteur (rôle `conducteur`) en fin de chantier. **Le conducteur archive ensuite ses filles** (`archive_session`), dans le même réveil : une fille dont la PR est fusionnée n'a plus rien à faire, et le capitaine, qui ne veille que sur sa file, en a laissé quatre ouvertes sur un chantier. L'archivage se défait (`unarchive_session`) et le coût reste lisible. Un dépassement des plafonds (§ 3 « Taille » et tableau ci-dessus ; une PR renvoyée trois fois attend un humain) s'écrit dans `## Dépassements` : session, ticket, mesure, décision du produit, date. Chaque session lancée porte le tag `chantier:<nom>`. Le coût moyen par ticket, comparé d'un chantier à l'autre, dit si les règles ci-dessus font baisser la dépense. Le registre transverse, `docs/agents/couts.md`, agrège ces sections pour tous les chantiers (total, par chantier, par session). C'est un index généré (`node scripts/docs/couts.mjs`, déclaré dans `scripts/docs/index-generes.json`) : on corrige la carte, jamais le registre, et le capitaine le régénère après chaque fusion. Relever les filles à chaque fin de vague, et non en fin de chantier seulement, garde ce registre à jour en continu ; le capitaine et le conducteur s'y ajoutent en fin de chantier.
