# Ce que contient le socle des tests, et pourquoi

## Le lint des tests — `racine/eslint.tests.mjs`

Un bloc ESLint pour les specs, chargé par `eslint.config.mjs` de la racine quand le fichier existe. Chaque règle ferme un cas vu sur un premier projet : un `it` sans assertion (`expect-expect`, helpers maison reconnus par leur nom), une assertion sous `if`/`try` qui ne s'exécute jamais (`no-conditional-expect`), un `it.skip` sans ticket (`no-disabled-tests`, désactivable ligne à ligne avec la mention du ticket), un `.only` oublié, un `expect` hors d'un cas, un `setTimeout` qui parie sur la vitesse de la machine.

## Le gate `tests-creux` — `scripts/verify/tests-creux.mjs`

ESLint garantit qu'un `it` contient une assertion, pas qu'elle contraint quelque chose : `expect(r).toBeDefined()` est vert sur `{}`. Ce gate lit l'AST TypeScript de chaque spec et refuse un cas dont toutes les assertions sont `toBeDefined` ou `toBeTruthy`. Échappatoire motivée sur la ligne au-dessus. Un cas désactivé (`it.skip`, `it.todo`, `describe.skip`) porte une spec ou un ticket (`SPEC_ALL_SOC-1.07`) dans son titre ou dans le commentaire au-dessus, lu par la grammaire du socle (`scripts/docs/identifiants.mjs`, posée par `socle-monorepo`) : sans elle, le gate sort en 2. Dans `pnpm check`, après lint : quelques centaines de millisecondes.

## Le gate `coverage-diff` — `scripts/verify/coverage-diff.mjs` et `coverage-diff-regles.mjs`

Un plancher global de couverture ne voit pas un fichier neuf à 0 % : 10 % du dépôt l'absorbent. Ce gate regarde le diff : chaque fichier de code modifié ou ajouté par rapport à la base est exécuté par au moins un test, et assez (80 % de lignes, 70 % de branches ; 90 % de lignes pour un fichier neuf). Par paquet, `vitest related <fichiers>` sous couverture v8, rapport istanbul ; si le paquet a un `vitest.db.config.ts` et que `DATABASE_URL` est définie, les suites sur base sont jouées aussi et les deux rapports additionnés — un repository n'est prouvé que contre Postgres. Les règles (périmètre, lecture du rapport, fusion, décision quand la base manque, verdict) sont pures et testées ; le script orchestre git et Vitest. Au pre-push et dans le job CI qui a la base. Sur un distant vide (premier push d'un dépôt neuf, `git ls-remote --heads origin` sans aucune branche), le gate ne compare rien et passe : la base naîtra avec la chaîne. Tout autre distant est un refus (sortie 2) qui dit où la base manque : listée sur le distant, `git fetch origin develop` ; des branches mais pas elle, la créer depuis `main` (`scripts/github/develop.sh` du socle de la chaîne, qui pousse sous le hook, dont le pre-push du socle ne joue rien quand rien de neuf ne part : la commande à la main reste à éviter) ; distant muet. Le gate ne cherche jamais à deviner que le push en cours est celui qui crée la base.

**La base est ce sur quoi le travail sera fusionné, pas develop par défaut.** La CI nomme la cible de la PR (`--base origin/$BASE`). Le pre-push passe `--base-auto` et lit l'entrée du hook (`PRE_PUSH_REFS`, exportée par `.husky/pre-push` avant que `pnpm run check` ne la consomme) : pousser vers `refs/heads/sujet/<nom>` mesure contre `origin/sujet/<nom>` (`baseDepuisPush`) ; sinon, parmi `origin/develop` et les `origin/sujet/*`, le candidat auquel il manque le moins de commits de HEAD, sans exiger l'ascendance (une branche dont le sujet a avancé garde son sujet), develop à égalité (`choisirBase`). Cas vécu : un commit de documentation poussé sur un sujet voyait, contre develop, tout le code déjà fusionné dans le sujet, ses repositories à 0 % sans `DATABASE_URL`, et le push était refusé. Aucun seuil ne baisse, aucun fichier n'est exempté. **Sur une PR de mise à jour d'un sujet** (la fusion de develop dans le sujet, son premier commit, puis des retouches), seul compte l'écart du sommet à la fusion recalculée (`git merge-tree --write-tree` du sommet du sujet et du commit de develop), jamais ce que develop apporte : les conflits résolus et chaque retouche, jugée comme une sous-PR, formatage compris (aucune dispense par le formateur), aux seuils habituels ; la sortie le dit (« la fusion recalculée de develop dans … ») ; toute autre forme (pas de fusion, trois parents, sujet qui a avancé, fusion d'essai de GitHub) se mesure comme avant, contre la base entière. Le journal s'écrit de façon synchrone (`writeSync`) : un tube lu lentement ne le coupe plus. En CI, le job qui joue `coverage-diff` fait le checkout de `github.event.pull_request.head.sha` avec `fetch-depth: 0` (jamais la fusion d'essai que GitHub met par défaut en `HEAD`, qui masque la forme d'une PR de mise à jour : la mesure retombe alors sur la base entière) et dispose d'`origin/develop` (`fetch-depth: 0` rapatrie toutes les branches ; sinon `git fetch origin develop`) ; il passe `--base origin/<cible de la PR>`.

## Les gabarits — `gabarits/`

`exemple.property.spec.ts` : la forme d'un test de propriétés `fast-check`, oracle indépendant en entiers, budget de tirages. `stryker.config.mjs` : la mutation du noyau critique sous Vitest, périmètre vide et plancher à zéro jusqu'à la première mesure.

## La mutation des règles prouvées — `scripts/verify/mutation-regles.mjs`, `gabarits/stryker.regles.config.mjs`, `ci/mutation.yml`

Le noyau critique se liste à la main (`mutate` de `stryker.config.mjs`) ; les règles métier prouvées se listent d'elles-mêmes. Dans un projet suivi par Anchorpost, l'index commis `anchorpost/anchorpost.json` (schéma `"2"`) dit, pour chaque règle, sa réalisation (`realisation.status`) et les fichiers de code qui la réalisent (`code`, champ facultatif du standard, écrit dans l'en-tête du fichier de règle). Le périmètre est l'union des `code` des règles `proven` : les fichiers dont des tests sont censés prouver une exigence du métier, donc ceux dont la force vaut d'être mesurée.

- **`mutation-regles.mjs`** : `perimetre(index, existe)` est pure et testée sur un index jouet ; le point d'entrée lit le JSON lui-même (il n'importe pas le paquet `@maj-agency/anchorpost`, qui n'a pas besoin d'être installé). `--list` imprime le périmètre, un fichier par ligne ; `--lancer`, depuis un paquet, joue Stryker sur les fichiers de ce paquet. Un chemin de `code` absent du dépôt, hors du dépôt, ou hors périmètre de la mutation (test, déclaration, contrôleur, module, dto, gabarit, migration, types générés, `main.ts`, autre langage) est signalé et écarté — un lien symbolique qui sort du dépôt compris ; les chemins passés à Stryker sont échappés, car il les lit comme des globs (`[id].ts` d'une route Next) : le refuser est le travail de `anchorpost check`, pas de la mutation. Une clé de règle est portée telle que l'index l'écrit, zéros de tête compris ; aucun identifiant n'est analysé.
- **`mutation-regles-synthese.mjs`** : le rapport des survivants par règle (règle → fichiers → mutants survivants, puis le hors périmètre), en Markdown, lu dans `reports/mutation/mutation.json`. Le workflow le joue dans une étape `always()` vers `$GITHUB_STEP_SUMMARY` : un passage interrompu (délai dépassé) dit « Pas de rapport de mutation », un périmètre vide dit qu'il est vide. Une clé de règle ou un nom de mutant est ramené à une ligne sans accent grave avant d'entrer dans le Markdown.
- **Sans index** (projet qui ne suit pas Anchorpost, index illisible ou d'un autre schéma) : périmètre vide, raison dite, sortie 0 — le workflow reste vert et ne mute rien.
- **Pas de plancher en V1** : une première mesure par règle n'existe pas encore ; poser un chiffre serait l'inventer. Le plancher reste celui du noyau.
- **`stryker.regles.config.mjs`** hérite de la configuration du noyau (`break: 0` : le plancher du noyau ne s'applique pas, fichier incrémental séparé, reporter `json`) et importe `perimetreDuPaquet()` : une configuration par paquet qui teste, parce que les configurations Vitest sont par paquet et que chaque mutant rejoue les suites de son paquet. Les fichiers d'une règle qui vivent dans un autre paquet se mutent par la configuration de cet autre paquet : `--lancer` et la synthèse les nomment (« Dans un autre paquet ») plutôt que de les taire.
- **`mutation.yml`** : le dimanche, heure creuse, sur `regles` ; à la demande, `noyau` (par défaut) ou `regles`. Le noyau n'est jamais planifié.

## Les ADR — `adr/`

Trois gabarits numérotés à la pose : les suites sans infrastructure dans la porte de qualité et les suites sur base en CI avec le service ; les invariants métier testés par propriétés ; le score de mutation plancher sur le noyau critique, mesuré à la demande, et la mutation hebdomadaire des règles prouvées, sans plancher. Ils portent les faits mesurés sur un premier projet qui ont fondé chaque décision.
