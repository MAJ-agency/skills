# Ce que contient le socle des tests, et pourquoi

## Le lint des tests — `racine/eslint.tests.mjs`

Un bloc ESLint pour les specs, chargé par `eslint.config.mjs` de la racine quand le fichier existe. Chaque règle ferme un cas vu sur un premier projet : un `it` sans assertion (`expect-expect`, helpers maison reconnus par leur nom), une assertion sous `if`/`try` qui ne s'exécute jamais (`no-conditional-expect`), un `it.skip` sans ticket (`no-disabled-tests`, désactivable ligne à ligne avec la mention du ticket), un `.only` oublié, un `expect` hors d'un cas, un `setTimeout` qui parie sur la vitesse de la machine.

## Le gate `tests-creux` — `scripts/verify/tests-creux.mjs`

ESLint garantit qu'un `it` contient une assertion, pas qu'elle contraint quelque chose : `expect(r).toBeDefined()` est vert sur `{}`. Ce gate lit l'AST TypeScript de chaque spec et refuse un cas dont toutes les assertions sont `toBeDefined` ou `toBeTruthy`. Échappatoire motivée sur la ligne au-dessus. Un cas désactivé (`it.skip`, `it.todo`, `describe.skip`) porte une spec ou un ticket (`SPEC_ALL_SOC-1.07`) dans son titre ou dans le commentaire au-dessus, lu par la grammaire du socle (`scripts/docs/identifiants.mjs`, posée par `socle-monorepo`) : sans elle, le gate sort en 2. Dans `pnpm check`, après lint : quelques centaines de millisecondes.

## Le gate `coverage-diff` — `scripts/verify/coverage-diff.mjs` et `coverage-diff-regles.mjs`

Un plancher global de couverture ne voit pas un fichier neuf à 0 % : 10 % du dépôt l'absorbent. Ce gate regarde le diff : chaque fichier de code modifié ou ajouté par rapport à la base est exécuté par au moins un test, et assez (80 % de lignes, 70 % de branches ; 90 % de lignes pour un fichier neuf). Par paquet, `vitest related <fichiers>` sous couverture v8, rapport istanbul ; si le paquet a un `vitest.db.config.ts` et que `DATABASE_URL` est définie, les suites sur base sont jouées aussi et les deux rapports additionnés — un repository n'est prouvé que contre Postgres. Les règles (périmètre, lecture du rapport, fusion, décision quand la base manque, verdict) sont pures et testées ; le script orchestre git et Vitest. Au pre-push et dans le job CI qui a la base. Sur un distant vide (premier push d'un dépôt neuf, `git ls-remote --heads origin` sans aucune branche), le gate ne compare rien et passe : la base naîtra avec la chaîne. Tout autre distant est un refus (sortie 2) qui dit où la base manque : listée sur le distant, `git fetch origin develop` ; des branches mais pas elle, la créer depuis `main` (`scripts/github/develop.sh` du socle de la chaîne, qui pousse sous le hook, dont le pre-push du socle ne joue rien quand rien de neuf ne part : la commande à la main reste à éviter) ; distant muet. Le gate ne cherche jamais à deviner que le push en cours est celui qui crée la base.

**La base est ce sur quoi le travail sera fusionné, pas develop par défaut.** La CI nomme la cible de la PR (`--base origin/$BASE`). Le pre-push passe `--base-auto` et lit l'entrée du hook (`PRE_PUSH_REFS`, exportée par `.husky/pre-push` avant que `pnpm run check` ne la consomme) : pousser vers `refs/heads/sujet/<nom>` mesure contre `origin/sujet/<nom>` (`baseDepuisPush`) ; sinon, parmi `origin/develop` et les `origin/sujet/*`, le candidat auquel il manque le moins de commits de HEAD, sans exiger l'ascendance (une branche dont le sujet a avancé garde son sujet), develop à égalité (`choisirBase`). Cas vécu : un commit de documentation poussé sur un sujet voyait, contre develop, tout le code déjà fusionné dans le sujet, ses repositories à 0 % sans `DATABASE_URL`, et le push était refusé. Aucun seuil ne baisse, aucun fichier n'est exempté. **Sur une PR de mise à jour d'un sujet** (la fusion de develop dans le sujet, son premier commit, puis des retouches), seul compte l'écart du sommet à la fusion recalculée (`git merge-tree --write-tree` du sommet du sujet et du commit de develop), jamais ce que develop apporte : les conflits résolus et chaque retouche, jugée comme une sous-PR, formatage compris (aucune dispense par le formateur), aux seuils habituels ; la sortie le dit (« la fusion recalculée de develop dans … ») ; toute autre forme de réception de develop (fusion dont le premier parent est develop, retouche avant la fusion, sujet qui a avancé, fusion d'essai de GitHub) se lit contre `origin/develop` dès que HEAD le contient et que la base non (`referenceDuDiff`), et la sortie le dit : le code que develop apporte n'est pas remesuré. Limite connue : dans ce repli, le travail propre du sujet qui n'est pas dans develop est remesuré, c'est plus que l'écart à la fusion, jamais moins. Sans l'une de ces formes (pas de fusion de develop dans HEAD), la mesure est celle de la base entière. **Sans `DATABASE_URL`** (jamais sous GitHub Actions), les suites `*.db.spec.ts` ne sont pas jouées : un fichier en échec qu'une de ces suites du paquet cible, par un import relatif ou un alias du `tsconfig.json` lu dans les sources (`suiteSurBaseCible`), passe en avertissement (`⚠`, ligne `AVERTISSEMENT`, sortie 0 s'il n'y a pas d'autre échec) et la CI, qui a Postgres, le juge ; avec `DATABASE_URL`, rien ne change. Le journal s'écrit de façon synchrone (`writeSync`) : un tube lu lentement ne le coupe plus. En CI, le job qui joue `coverage-diff` fait le checkout de `github.event.pull_request.head.sha` avec `fetch-depth: 0` (jamais la fusion d'essai que GitHub met par défaut en `HEAD`, qui masque la forme d'une PR de mise à jour : la mesure retombe alors sur la base entière) et dispose d'`origin/develop` (`fetch-depth: 0` rapatrie toutes les branches ; sinon `git fetch origin develop`) ; il passe `--base origin/<cible de la PR>`.

## Le gate `preuves` — `scripts/verify/preuves.mjs`

La preuve suffisante d'Anchorpost (`SPEC_ALL_ANC-5` § 5) : pour les règles que le travail touche, leur criticité, leurs cas prouvés et ce qui manque. Le jugement vit dans la CLI (`anchorpost compare`, ≥ 2.0.0) ; ce fichier est un relais. Il ne fait rien sans index commis au pivot 3 (un projet qui ne suit pas Anchorpost, ou pas encore au pivot 3, garde le régime d'avant) ; il choisit la base comme `coverage-diff --base-auto` (`BASE_DEFAUT`, `baseDepuisPush`, `choisirBase` et `decisionSansBase` de `coverage-diff-regles.mjs`), joue `compare --json`, en écrit un résumé d'une ligne par écart et rend la sortie de la CLI : 1 sur un écart en `enforce`, 0 en `observe`. Sous GitHub Actions, il ajoute le rapport entier au résumé du job. Au pre-push après `check:coverage`, en fin de tour par `gatesRapides`, et en CI sur la cible de la PR. Au pre-push et en fin de tour, une branche de mise à jour d'un sujet se compare à la plus proche de ses deux bases, jamais à la fusion recalculée : contre le sujet (il a plus de commits que develop n'en apporte), ce que la mise à jour défait de develop ne se voit pas, ni en CI, qui compare au même sujet, et la livraison du sujet le juge ; contre develop (il en apporte autant ou plus), ce qu'elle défait du sujet ne se voit pas, et la CI le juge.

## Les gabarits — `gabarits/`

`exemple.property.spec.ts` : la forme d'un test de propriétés `fast-check`, oracle indépendant en entiers, budget de tirages. `exemple.jour-metier.spec.ts` : le jour et l'heure d'un test, en trois points (le jour du fuseau du métier par une horloge injectée, des données créées par le test, un banc à horloge posée aux instants qui cassent), pour que la règle « Le jour et l'heure » de la fiche des tests se lise sur un exemple ; son fuseau est un fuseau d'exemple à remplacer. `stryker.config.mjs` : la mutation du noyau critique sous Vitest, périmètre vide et plancher à zéro jusqu'à la première mesure.

## La mutation des règles qui ont des preuves — `scripts/verify/mutation-regles.mjs`, `gabarits/stryker.regles.config.mjs`, `ci/mutation.yml`

Le noyau critique se liste à la main (`mutate` de `stryker.config.mjs`) ; les règles métier prouvées se listent d'elles-mêmes. Dans un projet suivi par Anchorpost, l'index commis `anchorpost/anchorpost.json` (schéma `"2"` ou `"3"`) dit, pour chaque règle, sa réalisation (`realisation.status`), sa criticité et les fichiers de code qui la réalisent (`code`, champ facultatif du standard, écrit dans l'en-tête du fichier de règle). Le périmètre est l'union des `code` des règles qui ont des preuves : `proven` au schéma 2, `proven` et `partial` au schéma 3 (où « prouvée » exige chaque cas attendu prouvé, et une règle qui a des preuves sans l'être est « partielle ») : les fichiers dont des tests sont censés prouver une exigence du métier, donc ceux dont la force vaut d'être mesurée (`SPEC_ALL_ANC-5` § 7).

- **`mutation-regles.mjs`** : `perimetre(index, existe)` est pure et testée sur un index jouet ; le point d'entrée lit le JSON lui-même (il n'importe pas le paquet `@maj-agency/anchorpost`, qui n'a pas besoin d'être installé). `--list` imprime le périmètre, un fichier par ligne ; `--lancer`, depuis un paquet, joue Stryker sur les fichiers de ce paquet. Un chemin de `code` absent du dépôt, hors du dépôt, ou hors périmètre de la mutation (test, déclaration, contrôleur, module, dto, gabarit, migration, types générés, `main.ts`, autre langage) est signalé et écarté — un lien symbolique qui sort du dépôt compris ; les chemins passés à Stryker sont échappés, car il les lit comme des globs (`[id].ts` d'une route Next) : le refuser est le travail de `anchorpost check`, pas de la mutation. Une clé de règle est portée telle que l'index l'écrit, zéros de tête compris ; aucun identifiant n'est analysé.
- **`mutation-regles-synthese.mjs`** : le rapport des survivants par règle (règle → fichiers → mutants survivants, puis le hors périmètre), en Markdown, lu dans `reports/mutation/mutation.json`, avec la date de la mesure et, par règle, sa criticité et son score ; une règle dont aucun mutant n'est atteint par un test rejoué (preuves sur base, ou hors de Stryker) est « non mesurée », jamais « 0 % » (`RULE_ALL_ANC-29` d'Anchorpost). `--mesure` écrit la mesure datée en JSON ; `--precedente` lit celle du passage précédent et dit chaque baisse de score d'une règle moyenne, sans rien refuser. La mesure ne vit ni dans l'index ni dans le dépôt : le workflow la publie en artefact (`mesure-regles`, 90 jours) et relit, au passage suivant, le dernier artefact de ce nom sur la branche par défaut. Le workflow le joue dans une étape `always()` vers `$GITHUB_STEP_SUMMARY` : un passage interrompu (délai dépassé) dit « Pas de rapport de mutation », un périmètre vide dit qu'il est vide. Une clé de règle ou un nom de mutant est ramené à une ligne sans accent grave avant d'entrer dans le Markdown.
- **Sans `apps/api/`** (un projet sans API, ou une API ailleurs) : ni configuration Stryker, ni script `mutation`, ni `mutation.yml` ; le banc `mutation-regles.test.mjs` saute ses deux tests de configuration, avec leur raison dans la sortie (`# SKIP`).
- **Sans index** (projet qui ne suit pas Anchorpost, index illisible ou d'un autre schéma) : périmètre vide, raison dite, sortie 0 — le workflow reste vert et ne mute rien.
- **Pas de plancher en V1** : une première mesure par règle n'existe pas encore ; poser un chiffre serait l'inventer. Le plancher reste celui du noyau.
- **`stryker.regles.config.mjs`** hérite de la configuration du noyau (`break: 0` : le plancher du noyau ne s'applique pas, fichier incrémental séparé, reporter `json`) et importe `perimetreDuPaquet()` : une configuration par paquet qui teste, parce que les configurations Vitest sont par paquet et que chaque mutant rejoue les suites de son paquet. Les fichiers d'une règle qui vivent dans un autre paquet se mutent par la configuration de cet autre paquet : `--lancer` et la synthèse les nomment (« Dans un autre paquet ») plutôt que de les taire.
- **`mutation.yml`** : le dimanche, heure creuse, sur `regles` ; à la demande, `noyau` (par défaut) ou `regles`. Le noyau n'est jamais planifié.

## Les ADR — `adr/`

Trois gabarits numérotés à la pose : les suites sans infrastructure dans la porte de qualité et les suites sur base en CI avec le service ; les invariants métier testés par propriétés ; le score de mutation plancher sur le noyau critique, mesuré à la demande, et la mutation hebdomadaire des règles prouvées, sans plancher. Ils portent les faits mesurés sur un premier projet qui ont fondé chaque décision.
