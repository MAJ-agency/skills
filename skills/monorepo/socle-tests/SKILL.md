# Socle des tests

La fiche `.claude/rules/tests.md` du socle monorepo écrit les règles — tests creux interdits, couverture du diff, propriétés, plancher daté — et promet les machines qui les tiennent. Ce skill les pose. **Il n'écrit aucun test** : il pose ce qui refuse un mauvais test et ce qui mesure l'absence de test.

Tous les gabarits vivent dans [`references/`](references/). Les copier **verbatim** puis substituer `{{PROJET}}`, `{{SCOPE}}`, `{{DATE}}`, `{{N}}`. Ce que chaque pièce fait et pourquoi : [`references/CONTENU.md`](references/CONTENU.md).

## Avant de commencer — vérifier le terrain

1. **La racine est posée** (`pnpm-workspace.yaml`, `scripts/check.mjs`, `.claude/rules/tests.md`, `scripts/docs/identifiants.mjs` que `tests-creux` importe, `scripts/docs/environnement-de-banc.mjs` que `coverage-diff.test.mjs` importe) ; sinon `/maj-skills:socle-monorepo` d'abord.
2. **Les paquets testent par Vitest** (`"test": "vitest …"` dans chaque `package.json`). Un paquet sous Jest n'est pas mesuré par `coverage-diff` : le dire, ne pas l'adapter.
3. Si `scripts/verify/coverage-diff.mjs` existe, le socle est posé : **s'arrêter et demander** ; une mise à jour se fait pièce par pièce.
4. La chaîne de production (`.claude/chaine.json`) n'est pas requise, mais si elle est là, `coverage-diff` compare à `origin/develop` par défaut, et au pre-push (`--base-auto`) au sujet visé par le push ou au plus proche de develop et des `origin/sujet/*` (une branche de mise à jour d'un sujet choisit ce sujet). Sur une PR de mise à jour d'un sujet, seul l'écart du sommet à la fusion recalculée de develop compte, retouches et conflits résolus compris ; toute autre réception de develop se lit contre `origin/develop` dès que HEAD le contient et que la base non. Sans `DATABASE_URL`, un fichier en échec que seule une suite `*.db.spec.ts` cible passe en avertissement, la CI le juge. En CI, le job qui joue `coverage-diff` fait le checkout de `github.event.pull_request.head.sha` avec `fetch-depth: 0` (jamais la fusion d'essai que GitHub met par défaut en `HEAD`, qui masque la forme d'une PR de mise à jour : la mesure retombe alors sur la base entière) et dispose d'`origin/develop` (`fetch-depth: 0` rapatrie toutes les branches ; sinon `git fetch origin develop`) ; il passe `--base origin/<cible de la PR>`.

## Étape 1 — les questions

Une seule, avec sa recommandation : **les seuils de couverture du diff**. _(Recommandé : 80 % de lignes et 70 % de branches pour un fichier modifié, 90 % de lignes pour un fichier nouveau — les valeurs de `coverage-diff-regles.mjs`, mesurées sur un premier projet comme le point où les PR cessent de laisser des surfaces sans test.)_ Rien d'autre : le périmètre (le code des apps et des paquets, hors specs, routes, migrations, types générés, ui vendored) est dans le script et se corrige par PR, pas par question.

## Étape 2 — poser

1. **Dépendances** (les prévoir sur la ligne `Dépendances:` du ticket : le hook d'agent refuse le reste) : `pnpm add -D @vitest/eslint-plugin -w`, puis `pnpm add -D @vitest/coverage-v8@<version de vitest> --filter <chaque paquet qui teste>`. `fast-check` et Stryker s'installent au premier usage, pas ici.
2. **Le lint des tests** : `references/racine/eslint.tests.mjs` → `eslint.tests.mjs` à la racine. Le `eslint.config.mjs` du socle monorepo le charge s'il existe ; sur un dépôt antérieur, ajouter avant `...brickRules` :
   ```js
   ...(existsSync(join(root, "eslint.tests.mjs")) ? (await import(pathToFileURL(join(root, "eslint.tests.mjs")).href)).default : []),
   ```
   et `"eslint.tests.mjs"` dans `ignores`.
3. **Les gates** : `references/scripts/verify/*` → `scripts/verify/` (tests compris). Dans `package.json` : `check:tests-creux` (`node scripts/verify/tests-creux.mjs`), `check:coverage` (`node scripts/verify/coverage-diff.mjs`) et `check:preuves` (`node scripts/verify/preuves.mjs`, le gate de la preuve suffisante : il joue `anchorpost compare` quand l'index commis est au pivot 3, CLI Anchorpost ≥ 2.0.0, et ne fait rien sinon). Dans `scripts/check.mjs`, une étape `check:tests-creux` après `lint`, avec son message. Dans `.husky/pre-push`, qui lit lui-même son entrée (`PRE_PUSH_REFS=$(cat)` puis `export PRE_PUSH_REFS`, que `coverage-diff --base-auto` relit : n'ajouter aucune seconde lecture, elle rendrait une entrée vide), seulement `pnpm run check:coverage --base-auto` après `pnpm run check`, puis `pnpm run check:preuves --base-auto` : la couverture et les preuves se mesurent contre ce sur quoi le travail sera fusionné, pas contre develop (pousser vers `sujet/<nom>` → `origin/sujet/<nom>`). Si la chaîne est posée, `scripts/verify/preuves.mjs` entre dans `gatesRapides` de `.claude/chaine.json` : la fin de tour le joue sans option, la base choisie de même (13 à 17 s par passage, mesurés sur Anchorpost à une charge de 14 à 18 : la CLI construit l'index de la base et celui de l'arbre). Le gate juge l'arbre de travail, non commis et non suivi compris, pas le commit poussé : au pre-push, une preuve restée hors du commit le fait passer, un travail en cours peut le bloquer ; la CI juge le commit. Au pre-push et en fin de tour, une branche de mise à jour d'un sujet se compare à la plus proche de ses deux bases, jamais à la fusion recalculée de `coverage-diff` : le sujet quand il a plus de commits que develop n'en apporte (plus large, jamais plus lâche) ; sinon develop, qui ne voit pas ce que la mise à jour défait du sujet (une règle, un cas, une criticité remis comme sur develop) : la CI, qui compare à la cible de la PR, le juge. Le relais lance `node_modules/.bin/anchorpost` à la racine : dans un dépôt où la CLI est un paquet de l'espace de travail et non une dépendance installée (le dépôt de la CLI elle-même), ce fichier n'existe pas et le relais sort en 2, au pre-push comme en fin de tour ; ce dépôt l'adapte à la pose, comme son relais `anchorpost.mjs`.
4. **La CI** : dans le job qui a Postgres (`test-db` du socle de la chaîne, ou le job de tests), après `test:db`, une étape sur `pull_request` : `pnpm check:coverage --base "origin/$BASE"` avec `env: BASE: ${{ github.event.pull_request.base.ref }}` (jamais le gabarit dans le `run:`, `zizmor` le refuse) et `DATABASE_URL` — les suites sur base comptent. Le job a `fetch-depth: 0` ou fait `git fetch origin <base>` avant. Dans le job de qualité, sur `pull_request`, le rapport de preuves : `node scripts/verify/preuves.mjs --base "origin/$BASE"` (même `env:`, `fetch-depth: 0`) ; il écrit le rapport entier de `anchorpost compare` dans le résumé du job, et ne refuse qu'en `enforce`. Puis le workflow de mutation : `references/ci/mutation.yml` → `.github/workflows/mutation.yml`, `{{SCOPE}}` et `{{PROJET}}` substitués — un `workflow_dispatch` au choix `noyau | regles` (défaut : `noyau`) et un `schedule` hebdomadaire (dimanche, heure creuse) sur `regles`, dont la synthèse va dans le résumé du job (étape `always()` : un passage interrompu dit « pas de rapport ») ; la mesure datée est publiée en artefact (`mesure-regles`) et relue au passage suivant, par le `gh` du runner et la permission `actions: read`, pour dire une baisse sur une règle moyenne ; la saisie passe par `env:`, aucune expression `${{ }}` dans un `run:`, actions épinglées par empreinte comme `ci.yml` de la chaîne. Le noyau garde sa configuration et son plancher, à la demande seulement.
5. **Les gabarits** : `references/gabarits/exemple.property.spec.ts` et `references/gabarits/exemple.jour-metier.spec.ts` → `docs/agents/gabarits/` ; `references/gabarits/stryker.config.mjs` → `apps/api/stryker.config.mjs` (placeholders substitués, `mutate` vide, `break: 0`), et un script `mutation` (`stryker run`) dans le `package.json` de l'API ; `reports/` et `.stryker-tmp/` dans `.gitignore`. Puis la mutation des règles qui ont des preuves : `references/gabarits/stryker.regles.config.mjs` → `apps/api/stryker.regles.config.mjs` (placeholders substitués ; elle hérite de `stryker.config.mjs`, avec `break: 0` ; son `mutate` n'est pas à remplir, il vient de l'index ; `STRYKER_MUTATE` le remplace pour un essai local), et dans le `package.json` de l'API `"mutation:regles": "node ../../scripts/verify/mutation-regles.mjs --lancer && node ../../scripts/verify/mutation-regles-synthese.mjs"`. Le script (`scripts/verify/mutation-regles.mjs`, posé à l'étape 3) lit l'index commis `anchorpost/anchorpost.json` — schéma `"2"` (règles `proven`) ou `"3"` (règles `proven` et `partial`), leurs fichiers `code` — et ne mute que ceux du paquet ; **sans index, ou d'un autre schéma, il ne lance rien, dit pourquoi et sort 0** : le standard vaut pour tous les projets, Anchorpost est une option. Il ne refuse rien (pas de plancher en V1) ; `mutation-regles-synthese.mjs` écrit le rapport des survivants par règle, daté, avec la criticité et le score de chaque règle (« non mesurée » quand aucun test rejoué n'atteint son code), et la baisse d'une règle moyenne depuis la mesure précédente.
6. **La fiche** `.claude/rules/tests.md` : les phrases « à poser par le ticket … » deviennent les commandes réelles (le gabarit du socle monorepo ≥ 3.1 les a déjà) ; `pnpm check:coverage`, `mutation` (le noyau, à la demande) et `mutation:regles` (les règles prouvées, chaque dimanche par le workflow) dans la section Commandes ; `docs/methode/pare-feu-ci.md` reçoit les deux gates dans son catalogue, avec la base de `coverage-diff` : la cible de la PR en CI (`--base origin/$BASE`), `--base-auto` au pre-push. Si la chaîne est posée, deux critères de projet dans le fichier de critères de la revue (`criteresRevue` de `.claude/chaine.json`) : une fonction pure nouvelle qui porte un invariant chiffré a son `*.property.spec.ts` (ADR propriétés) ; un fichier du périmètre `mutate` de `stryker.config.mjs` modifié vient avec sa mesure de mutation dans la PR (ADR mutation).
7. **Les ADR** : `node scripts/docs/next-id.mjs ADR ALL ARC` trois fois, chaque ADR copiée avant l'appel suivant ; `references/adr/ADR_ALL_ARC-N-tests-sans-infrastructure.md`, `ADR_ALL_ARC-N-tests-de-proprietes.md`, `ADR_ALL_ARC-N-score-de-mutation.md` → `docs/adr/`, `{{N}}` et `{{DATE}}` substitués, une ligne `Décideurs`.
8. **Le ticket** du pare-feu CI, s'il existe : un commentaire daté qui dit ce que ce skill a fermé, et ce qui reste (secrets, E2E, gates propres aux invariants).

## Étape 3 — vérifier, puis seulement conclure

```bash
pnpm lint                      # le plugin vitest charge, zéro erreur
pnpm check:tests-creux         # « tests-creux: N cas analysés » puis OK
node --test scripts/verify/*.test.mjs
node scripts/verify/coverage-diff.mjs --dry-run
node scripts/verify/mutation-regles.mjs --list   # le périmètre « règles » ; sans index Anchorpost : vide, la raison sur stderr, sortie 0
node scripts/verify/preuves.mjs                  # sans index au pivot 3 : « rien à comparer », sortie 0 ; sinon le résumé de anchorpost compare
```

Puis **une preuve que le gate mord** : ajouter une ligne vide à un fichier de code sans test, `pnpm check:coverage` doit le refuser « aucun test n'exécute ce fichier » ; retirer la ligne. Et `pnpm check` complet, vert.

## Étape 4 — l'historique

Invoqué seul : `chore(tests): pose les gates de qualité des tests`, puis `docs(adr): consigne les tests sans infrastructure, les propriétés et le score de mutation`. Invoqué par `socle-monorepo` (sa question **tests**), c'est lui qui écrit l'historique.

## Ce que ce skill ne fait pas

- **Aucun test, aucune propriété, aucun périmètre de mutation écrit à la main** : il pose les machines ; les tests viennent avec le code, la propriété avec la première fonction pure. Le `mutate` du noyau (`stryker.config.mjs`) se remplit avec le premier fichier d'argent ; celui des règles ne se remplit jamais, il se lit dans l'index.
- **Aucun plancher global de couverture** : un plancher se pose sous une mesure du jour ; sans mesure, c'est un chiffre inventé. Le diff, lui, se mesure dès la première PR.
- **Pas d'E2E** : Playwright et le bundle mobile sont posés par les socles de service ; leur cadence (au passage du capitaine) est celle de la chaîne.

## Anti-patterns

| Tentation                                                          | Pourquoi c'est faux                                                                                                                                               |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| « Je baisse le seuil pour faire passer cette PR »                  | Un seuil est un plancher daté : il monte quand la mesure progresse, jamais ne baisse. Une PR sous le seuil écrit ses tests ou exempte le fichier avec une raison. |
| « `// coverage-diff: ignore` sur ce service, il est dur à tester » | L'exemption est pour ce qui n'est pas testable en unitaire (amorçage, câblage). Un service dur à tester est un service à découper : c'est le signal du gate.      |
| « Je mets `toBeDefined()` en attendant »                           | C'est exactement le test creux que le gate refuse : il passe sur `{}`. Contraindre le résultat, ou ne pas écrire le cas.                                          |
| « La mutation à chaque PR, pour être sûr »                         | Plusieurs minutes de runner par PR pour un signal qui bouge peu. À la demande, après un changement du périmètre.                                                  |
| « Jest mesurait mieux »                                            | `vitest related` + `@vitest/coverage-v8` donnent le même rapport istanbul ; le gate lit le rapport, pas l'outil.                                                  |
